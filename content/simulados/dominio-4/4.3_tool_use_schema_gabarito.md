# Gabarito — 4.3 Enforce structured output using tool use and JSON schemas (CCA-F, Domínio 4)

**Tópico:** `tool_use` com JSON schema como via confiável de saída estruturada — elimina erro de sintaxe, não de semântica (K1); os três regimes de `tool_choice` — `auto`/`any`/forçado — e o preço de cada um em capacidade de recusa (K2/S2/S3); design de schema — `required`→nullable para dado ausente, enum fechado→extensível (`"other"` + detalhe, `"unclear"`) (K4/S4/S5); validação semântica como código, fora do schema, para relações entre campos que JSON schema não expressa (K3)
Explicações em PT-BR. Todas as questões exercitam o **TS 4.3**.

> **O eixo deste tópico tem duas metades.** Nas Q1, Q2, Q4 e Q5 a correta é sempre um AJUSTE ESTRUTURAL — `tool_choice`, `required`/nullable, design de enum — porque o sintoma é uma GARANTIA que falta (roteamento, dado ausente, ordem de chamada), e prompt/few-shot/retry ficam como distratores probabilísticos, no mesmo enquadramento do Domínio 3 (hook/gate > prosa quando o requisito é determinístico). A Q3 é a dobradiça: mostra que o próprio schema estrito tem um limite — garante sintaxe, nunca relação entre campos — e que "reforçar o schema" ali é tão inútil quanto reforçar o prompt seria nas outras. A Q6 é o **quebra-automatismo**: depois de cinco questões em que a resposta certa era sempre "ajuste a camada de extração/schema", aqui a extração está certa e é a FONTE que está errada — e a resposta certa migra para fora do pipeline inteiramente, para revisão humana. Reflexo automático (afrouxar o gate, reescrever o prompt, repetir a chamada) é exatamente o erro que o guia testa.

## Q1 — Resposta correta: **C** · (4.3)

O sintoma é ausência de GARANTIA de chamada — `tool_choice: "auto"` deixa o modelo livre para responder em texto, e 12% dos casos exercem essa liberdade, com o documento saindo do pipeline sem erro visível. O guia descreve exatamente três regimes e o que cada um garante: `auto` pode devolver texto; `any` obriga a chamar ALGUMA tool, mas deixa o modelo escolher QUAL; forçado obriga a chamar AQUELA tool específica. Como o tipo do documento (nota ou recibo) não é conhecido antes da chamada e as duas tools estão registradas, `any` é o único regime que fecha a lacuna sem introduzir um erro novo: ele torna a chamada de tool obrigatória e ainda deixa o modelo decidir, pela própria descrição de cada tool, qual delas descreve o documento à sua frente.

- **A — errada:** forçar `extrair_nota_fiscal` garante QUE uma tool seja chamada, mas crava QUAL — quando o documento é na verdade um recibo, o modelo é obrigado a preencher campos de nota fiscal que não existem na fonte. Isso resolve os 12% de texto trocando-os por extrações erradas do tipo certo (arquétipo: **camada/alvo errado** — garante a chamada, não a correção).
- **B — errada:** manter `auto` e reforçar a instrução em prosa pede ao modelo, de novo, o mesmo comportamento que ele já deveria ter — e o sintoma É que a instrução em prosa não é suficiente para eliminar o desvio; mais uma frase sobre a mesma regra não fecha uma lacuna que é estrutural (arquétipo: **probabilístico onde precisa ser determinístico**).
- **C — correta.**
- **D — errada:** classificar o tipo do documento numa chamada separada antes de extrair introduz um componente novo — outra chamada de API, outra chance de erro — para resolver um problema que a própria tool call, sob `any`, já resolve na mesma chamada. É complexidade que não compra nada que `any` não entregasse de graça (arquétipo: **over-engineering**).

## Q2 — Resposta correta: **A** · (4.3)

O sintoma tem uma causa estrutural nomeada no próprio enunciado: `ordem_compra` é `required` num schema `strict: true`, e um terço dos documentos genuinamente não tem esse dado. Com `strict: true`, o modelo não tem a opção de omitir um campo `required` — a única saída que satisfaz o schema é preencher ALGO, e 40% das vezes esse algo é um número plausível inventado. A correção precisa mudar a REGRA do schema, não o comportamento do modelo dentro da regra: tirar o campo de `required` e ampliar seu tipo para aceitar `null` (`{"type": ["string", "null"]}`) dá ao modelo uma saída legal para "este dado não existe na fonte" sem abrir a chave inteira como opcional.

- **A — correta.**
- **B — errada:** pedir em prosa que o modelo não invente valores tenta combater, com uma instrução probabilística, a pressão que o próprio schema cria de forma determinística — o campo continua `required`, então "não inventar" e "preencher algo" continuam sendo instruções contraditórias no mesmo prompt (arquétipo: **probabilístico onde precisa ser determinístico**).
- **C — errada:** exemplos few-shot com `null` são a técnica certa do task statement 4.2 para reduzir alucinação — mas aqui o schema segue exigindo um valor não nulo no campo `required`; qualquer exemplo que mostre `null` estaria mostrando uma saída que o próprio schema rejeitaria. É o "quase certo" da questão: uma técnica real, do task statement errado para esta causa (arquétipo: **probabilístico onde precisa ser determinístico**, cruzando com o 4.2).
- **D — errada:** um retry quando o campo não bate um padrão é validação pós-hoc (task statement 4.4) sobre um valor que já foi inventado — ele reprocessa a mesma pergunta com a mesma pressão estrutural e provavelmente inventa outro número plausível, sem nunca abrir a jogada legal de `null` (arquétipo: **camada/alvo errado**).

**Tópicos:** Tool Use Schema

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Aplicar
- Dificuldade: Médio
- Rubrica: 6 = Bloom 2 + integração 1 + cenário 1 + distratores 2 (distratores 2 porque C é um "quase certo": few-shot com `null` é uma correção real no 4.2, só que para um schema que já aceita `null`)
- Cenário: S6 — Structured Data Extraction
- Princípio testado: campo `required` num schema estrito não deixa jogada legal para dado ausente; tirar de `required` e aceitar `null` é a correção estrutural (K4/S4)

## Q3 — Resposta correta: **D** · (4.3)

Cem por cento de validação de schema sobre 300 notas mostra que a garantia que `strict: true` oferece está funcionando exatamente como prometido: todo campo tem o tipo certo e toda chave `required` está presente. E é justamente por isso que o achado do time contábil — itens que não somam o total, CNPJ do emitente e do destinatário trocados entre os campos — é possível: nenhuma das duas coisas é um erro de SINTAXE. "Itens somam o total" é uma relação ENTRE campos, e a doc de structured outputs é explícita: não existe forma de escrever essa relação em JSON schema. "CNPJ no campo trocado" é um valor do TIPO certo, na CHAVE certa, só que semanticamente errado — nenhum `type: string` detecta isso. A única camada que resta é código, fora do schema, comparando os valores da própria saída (soma dos itens contra o total) e contra o gabarito de origem quando disponível.

- **A — errada:** `minimum`, `maximum` e `multipleOf` são constraints NUMÉRICAS, e a razão principal de elas não servirem aqui não depende de nenhum detalhe de SDK: a checagem pedida é uma relação ENTRE dois campos (a soma dos itens contra o total), e JSON schema não expressa relação entre campos com constraint nenhuma, suportada ou não. Há ainda um segundo problema, e a doc é precisa sobre ele: structured outputs não suporta essas constraints, e os SDKs Python e TypeScript as removem do schema enviado à API "and validating them client-side". Ou seja, `minimum: 0` não some — ele vira uma verificação LOCAL, executada DEPOIS da geração. O que se perde é justamente o que se queria: como a constraint não chega à API, ela não participa da decodificação e não impede o modelo de gerar o valor. Quem escreve `minimum: 0` sai da revisão achando que travou a geração, quando comprou uma verificação a posteriori — que ele poderia ter escrito em código, com a vantagem de decidir o que fazer quando ela falha (arquétipo: **camada/alvo errado** — schema é a camada errada para relação entre campos, e a constraint que sobrevive é local, não generativa).
- **B — errada:** `strict: true` já está ligado — é o que produz os 100% de validação de schema no enunciado. Confirmar de novo uma configuração que já está correta não adiciona nenhuma garantia nova sobre a pergunta que falta responder, que é semântica, não estrutural (arquétipo: **camada/alvo errado** — mesma camada da opção A, aplicada ao controle errado).
- **C — errada:** aumentar `max_tokens` evita que a resposta seja truncada antes do bloco `tool_use` seja completo — é uma correção real para OUTRO sintoma (braço que parece falho por corte no meio da geração), não para itens que somam errado num JSON já completo e válido. Presumir que "mais espaço" produz "mais correção aritmética" é tratar geração de texto como se fosse capacidade de cálculo garantido (arquétipo: **equívoco de capacidade**).
- **D — correta.**

**Tópicos:** Tool Use Schema

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Difícil
- Rubrica: 7 = Bloom 3 + integração 0 + cenário 2 + distratores 2 (distratores 2 porque B é um "quase certo": parece uma checagem de configuração razoável, só que sobre o controle que já está correto)
- Cenário: S6 — Structured Data Extraction
- Princípio testado: schema estrito elimina erro de sintaxe, nunca de semântica; relação entre campos não é expressável em JSON schema e precisa de validação em código (K3)

## Q4 — Resposta correta: **B** · (4.3)

Um enum fechado de quatro valores encontra, previsivelmente, categorias que nenhum dos quatro descreve — e forçar cada caso novo no valor mais próximo corrompe silenciosamente o relatório de gastos, sem nenhum erro que avise disso. O guia nomeia duas saídas específicas para esse limite estrutural do vocabulário fechado: um valor `"other"` acompanhado de um campo de detalhe em texto livre (para a categoria legítima que só não estava na lista) e um valor `"unclear"` separado (para o caso em que a ambiguidade é do próprio documento, não da cobertura do enum). As duas saídas preservam a estrutura do enum para os casos que ele já cobre bem, e dão ao modelo uma jogada honesta para os dois jeitos diferentes de "não sei classificar" — sem depender de redeploy a cada categoria nova.

- **A — errada:** ampliar o enum a cada categoria nova parece a correção mais direta, mas troca um problema recorrente por uma rotina de manutenção que nunca termina — cada trimestre traz categoria nova, cada categoria nova pede redeploy. É enumerar caso a caso quando o que falta é uma estrutura que absorva o caso ainda não visto (arquétipo: **equívoco de capacidade** — enumerar mais não substitui um design que generaliza).
- **B — correta.**
- **C — errada:** trocar o enum por string livre resolve a rigidez do vocabulário abrindo mão de exatamente a estrutura que motivou usar um enum: relatórios de gasto voltam a depender de como cada chamada decide escrever a categoria, com a mesma despesa podendo aparecer sob grafias diferentes em execuções diferentes — o problema estrutural muda de "categoria forçada errada" para "categoria escrita de um jeito novo a cada vez" (arquétipo: **probabilístico onde precisa ser determinístico** — a saída deixa de ser um valor fechado e passa a depender de como o modelo formula o texto).
- **D — errada:** um score de confiança é auto-reportado pelo próprio modelo — não mede se a categoria escolhida é a certa, mede o quanto o modelo diz confiar na escolha que já fez dentro do vocabulário fechado. Uma categoria nova classificada erroneamente com confiança alta (porque, dentre as quatro opções, uma delas realmente parece a mais próxima) passa pelo corte sem ser sinalizada (arquétipo: **proxy plausível não confiável**).

**Tópicos:** Tool Use Schema

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Difícil
- Rubrica: 7 = Bloom 3 + integração 1 + cenário 1 + distratores 2 (distratores 2 porque D repete o proxy de confiança auto-reportada do 4.1, e um candidato que só lembra "confiança é sempre suspeita" pode aplicá-lo aqui sem entender por quê)
- Cenário: S6 — Structured Data Extraction
- Princípio testado: enum extensível (`"other"` + detalhe, `"unclear"`) resolve categoria fora do vocabulário sem sacrificar a estrutura do enum nem exigir redeploy por categoria nova (K4/S5)

## Q5 — Resposta correta: **A** · (4.3)

O requisito aqui não é escolher a tool certa (as três estão registradas por bons motivos e todas devem rodar) — é garantir uma ORDEM entre chamadas dentro do mesmo turno, porque `enrich_vendor` e `extract_line_items` dependem de um valor que só `extract_metadata` produz. `tool_choice` não tem um regime nativo de "sequência"; a forma de obter sequenciamento é usar o regime FORÇADO para cravar qual tool roda no primeiro turno, e então liberar `auto` ou `any` para os turnos seguintes, quando o `document_id` já existe e a ordem de dependência não importa mais. É o mesmo mecanismo do 2.3 aplicado a dependência entre tools: forçado não serve para desambiguar qual tool é a certa quando várias servem — serve para SEQUENCIAR quando uma precisa rodar antes da outra.

- **A — correta.**
- **B — errada:** `tool_choice: "any"` garante que ALGUMA tool seja chamada no turno, mas não define QUAL — nada nesse regime impede o modelo de escolher `enrich_vendor` primeiro, que é exatamente o desvio já observado em 1 de cada 5 documentos (arquétipo: **camada/alvo errado** — `any` resolve ausência de chamada, não ordem entre chamadas).
- **C — errada:** a posição de uma tool dentro do array `tools` passado à API não influencia qual o modelo escolhe chamar primeiro — não existe essa relação documentada, e depender dela seria depender de um comportamento que a plataforma nunca prometeu (arquétipo: **feature inexistente porém verossímil**).
- **D — errada:** descrever a ordem de dependência na `description` da tool é uma instrução em prosa sobre um requisito que precisa ser garantia — o modelo pode seguir a instrução na maioria das vezes e ainda assim ser o desvio residual que gera a falha 1 em 5 vezes já observada, porque nada no mecanismo IMPEDE a ordem errada (arquétipo: **probabilístico onde precisa ser determinístico**).

**Tópicos:** Tool Use Schema

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 9 = Bloom 4 + integração 2 + cenário 1 + distratores 2 (distratores 2 porque B é um "quase certo": `any` de fato garante uma chamada, só que não a ordem entre chamadas — a mesma distinção que separa a Q1)
- Cenário: S6 — Structured Data Extraction
- Princípio testado: `tool_choice` forçado sequencia (garante QUAL tool roda no turno), não desambigua; é a ferramenta certa para dependência de ordem entre tools, não para ambiguidade de tipo de documento (K2, contraste com a Q1)

## Q6 — Resposta correta: **C** · (4.3)

Este é o **quebra-automatismo do simulado inteiro.** As cinco questões anteriores treinaram o reflexo "ache o ajuste estrutural — no schema, no `tool_choice`, no design do enum — e a garantia melhora". Aqui esse reflexo aponta para o lugar errado: a extração já é fiel, campo a campo, ao que está impresso no documento — o auditor confirmou isso manualmente contra a nota original. O que não fecha é a PRÓPRIA nota: o fornecedor cometeu um erro de soma no papel, e a extração, corretamente, reproduziu esse erro. Ajustar o gate, o prompt ou repetir a chamada tentaria fazer o pipeline produzir um número que não está no documento — trocando fidelidade por conformidade artificial. A resposta correta está fora do pipeline: encaminhar para revisão humana, ou devolver ao fornecedor para correção, mantendo a extração e o gate exatamente como estão, porque os dois estão fazendo o trabalho certo.

- **A — errada:** afrouxar a tolerância do validador esconde o próprio sinal que o gate existe para capturar — outras notas com o mesmo tipo de erro de soma, real e sistemático, passariam a ser aceitas sem revisão. Resolve este caso comprometendo a capacidade do gate de pegar o PRÓXIMO caso genuíno (arquétipo: **camada/alvo errado** — afrouxa o instrumento de detecção em vez de agir sobre o que ele detectou corretamente).
- **B — errada:** instruir o modelo a "corrigir" o total quando os itens não somam pede à extração para deixar de ser fiel ao documento-fonte e passar a computar um valor que substitui o que está impresso — contradiz o próprio propósito de uma extração (reproduzir a fonte) e, pior, silencia justamente o sinal de que o documento original tem um problema que precisa ser resolvido a montante, com o fornecedor (arquétipo: **camada/alvo errado** — pede à camada de extração para absorver um problema de qualidade de dados que é da fonte).
- **C — correta.**
- **D — errada:** repetir a chamada até a soma fechar não muda o documento nem a extração — se a extração já está correta (como o áudito confirmou), repetir produz o mesmo resultado correto indefinidamente, e qualquer tentativa de aceitar uma repetição que "por acaso" fechou estaria aceitando uma extração diferente da fonte real, isto é, uma extração errada. É rodar de novo até o sinal desaparecer, não até o problema ser resolvido (arquétipo: **voto/consenso que suprime sinal**).

**Tópicos:** Tool Use Schema

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 10 = Bloom 4 + integração 2 + cenário 2 + distratores 2 (distratores 2 porque as três opções erradas são o automatismo natural do simulado inteiro travestido de resposta razoável, e a virada do julgamento é perceber que o pipeline, aqui, está certo)
- Cenário: S5 — Claude Code for CI
- Princípio testado: schema válido e extração fiel não implicam fonte correta; quando a auditoria confirma que o pipeline reproduz fielmente uma fonte inconsistente, a resposta certa escala para revisão humana em vez de ajustar gate, prompt ou repetir a chamada — contraste com o automatismo treinado nas Q1–Q5
