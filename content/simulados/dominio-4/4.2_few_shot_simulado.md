**Tópico:** instrução detalhada sem exemplo produz saída inconsistente (K1), exemplos que ensinam o porquê de um caso ambíguo (K2/S1), exemplos que fixam o critério em vez de enumerar casos para generalizar (K3), exemplos que corrigem `null` explícito em campo ausente (K4/S5), exemplos que contrastam padrão aceitável × defeito genuíno (S3), e o limite do few-shot quando o requisito é garantia determinística

## Q1
A CI review job's prompt tells Claude, in prose, to post each finding as one line with a fixed shape: file path, line number, a severity tag, and a fix suggestion, always in that order. Over the last 40 pull requests, a human spot-check finds the *content* of every finding accurate, but only 71% of the postings match that shape — some put the severity tag first, some drop the fix suggestion onto its own line, some write "L42" where others write "line 42". The next pull request should not add a fifth way to write it. What is the most effective next step?

- **A)** Expand the prose instruction into a longer, more explicit paragraph that spells out the exact field order for every case already observed, including the ones this batch got wrong.
- **B)** Add 2–4 worked examples, each pairing a finding with the exact comment string it should produce, covering the range of severities and files the job already reports.
- **C)** Add a step after posting that re-parses each comment with a regex and asks the model to reformat any comment that doesn't match.
- **D)** Add a self-reported confidence field to the finding, and only post comments the job scores above 0.8.

## Q2
A different CI review job includes three worked examples of correctly formatted findings, and its comments already post in a consistent shape. Its trouble is judgment on one recurring case: a broad `except Exception:` block. Across 50 pull requests containing one, the job's verdict — bug or acceptable — agrees with a senior reviewer only 54% of the time, with no pattern the team can name. What is the most effective way to raise that agreement?

- **A)** Add one line per example naming why that verdict beat the alternative — e.g., discards the exception without logging it, versus an accepted case that re-raises it.
- **B)** Add three more `except Exception:` snippets, each paired directly with its verdict, without further comment.
- **C)** Add one prose sentence to the criteria stating when broad exception handling counts as a bug versus acceptable style.
- **D)** Route every diff containing `except Exception:` to a dedicated classifier trained specifically on this one recurring judgment call, and let the review job's existing criteria continue handling everything else in the diff.

## Q3
An extraction pipeline for maintenance field reports uses three few-shot examples, one per vendor template, to fill six fields per report. On reports from those three templates, accuracy is 98%. On a fourth vendor's reports — a template none of the examples came from — accuracy drops to 61%, mostly on `nivel_combustivel_litros`, which that vendor states inline in a sentence instead of in a labeled row. What is the most effective way to close that gap?

- **A)** Add three more examples, one per additional vendor template the team happens to have already seen in past batches of reports.
- **B)** Feed the model the entire batch of reports at once instead of one at a time, so it can infer the new vendor's layout from the others.
- **C)** Switch the extraction step to a more capable underlying model, since the failures cluster on the cases that need more inference to resolve.
- **D)** Keep the same three examples, but rewrite each to show the rule for locating the value, not a template-specific pattern.

## Q4
An extraction pipeline pulls fields from field reports whose `nivel_combustivel_litros` is missing from about 15% of the source documents — the technician simply didn't check the tank that visit. On a spot check of 100 extracted records, 15 of those absent-field cases came back with an invented number instead of an empty value, plausible enough that reviewers only caught it by opening the source document. The few-shot examples currently in the prompt only show documents where every field has a value. Which change is most effective?

- **A)** Mark the field as `required` in the tool's input schema, so the model cannot submit a record without a value for it.
- **B)** Add a prose sentence to the instructions telling the model not to invent values for fields the document doesn't mention.
- **C)** Add one example whose source document never mentions the field, with the expected output showing an explicit `null` for it.
- **D)** Add a validation step after extraction that rejects any record and sends it back for manual entry whenever this field is empty.

## Q5
A CI review job flags "magic numbers" — numeric literals with no visible explanation. Across 200 pull requests, 74% of these findings are closed as not-a-problem: a literal `404` next to an HTTP call, a `0` used as a starting index, a fixture value in a test that is deliberately arbitrary. A developer has started skimming past the whole category. The team wants a fix this week, before the next sprint's rewrite is ready. Which change is most effective right now?

- **A)** Add two examples for the same kind of literal — one flagged because its meaning isn't named nearby, one skipped as idiomatic — so the criterion is the reason, not the number.
- **B)** Remove the magic-number category from the criteria for this sprint, and bring it back once its criteria have a boundary.
- **C)** Replace the criterion with a fixed list of literals the job should always skip — `0`, `1`, `-1`, `100`, `404`, and any others the team decides to add later as they come up.
- **D)** Raise the minimum severity the job reports for this category, so only literals it scores as high-impact still post.

## Q6
The same extraction pipeline's `equipamento_id` field feeds a nightly join against an inventory database, keyed on the exact string `GER-####`. Few-shot examples covering that format already lifted format compliance to 97% across recent runs, but the remaining 3% ships as slight variants — `ger 1187`, `GER 1187` — and each one fails the join silently, leaving that equipment unlinked with no error raised anywhere. Which next step best matches what the join actually needs?

- **A)** Add more few-shot examples spanning a wider range of source documents, so the canonical format is demonstrated more often.
- **B)** Add an emphatic line to the prompt stating that `equipamento_id` must always be written as `GER-` followed by exactly four digits.
- **C)** Run the extraction three times per report and keep the `equipamento_id` string only when at least two of the three runs agree on it exactly.
- **D)** Add a deterministic check after extraction that rejects or holds any record whose `equipamento_id` does not match `GER-####`, before it reaches the join.
