# Simulado — 4.3 Enforce structured output using tool use and JSON schemas (CCA-F, Domínio 4)

**Tópico:** `tool_use` com JSON schema como via confiável de saída estruturada — elimina erro de sintaxe, não de semântica (K1); os três regimes de `tool_choice` — `auto`/`any`/forçado — e o preço de cada um em capacidade de recusa (K2/S2/S3); design de schema — `required`→nullable para dado ausente, enum fechado→extensível (`"other"` + detalhe, `"unclear"`) (K4/S4/S5); validação semântica como código, fora do schema, para relações entre campos que JSON schema não expressa (K3)

## Q1
A structured-extraction pipeline ingests a mixed stream of invoices and receipts; the document type is unknown until the model reads the content. Both `extrair_nota_fiscal` and `extrair_recibo` are registered as tools, and `tool_choice` is set to `"auto"`. Over the last 500 documents, 12% of responses come back as plain text describing the document instead of a tool call, and each of those documents silently skips extraction with no error raised anywhere downstream. What is the most effective change to guarantee that every document produces a structured record?

- **A)** Force `tool_choice` to `{"type": "tool", "name": "extrair_nota_fiscal"}` on every call, since most documents in the stream are invoices.
- **B)** Keep `tool_choice` set to `"auto"` and add an instruction to the prompt telling the model it must always call one of the two tools.
- **C)** Set `tool_choice` to `"any"` so the model is required to call one of the two registered tools, choosing whichever matches the document.
- **D)** Add a preliminary call that classifies each document as invoice or receipt, then route it to the matching forced `tool_choice`.

## Q2
An invoice-extraction tool defines `ordem_compra` (purchase order number) as a `required` field in its `input_schema`, with `strict: true` enabled. Roughly a third of source invoices never print a purchase order at all — the field simply isn't on the document. A weekly audit finds that 40% of those invoices come back with a purchase-order number that is well-formed but doesn't appear anywhere in the source text. What is the most effective fix?

- **A)** Remove `ordem_compra` from `required` and widen its type to accept `null`, giving the model a legitimate way to report absence.
- **B)** Add a line to the prompt instructing the model to never invent a purchase-order number that isn't printed anywhere on the source document.
- **C)** Add two or three few-shot examples pairing an invoice that has no purchase order with an output that fills the field with an explicit `null`.
- **D)** Add a post-extraction check that retries the call whenever `ordem_compra` doesn't match the expected purchase-order numbering pattern used elsewhere.

## Q3
An invoice-extraction pipeline uses `strict: true` and validates every response's tool input against the schema with `jsonschema.validate` before accepting it. Schema validation passes on 100% of the last 300 invoices — every field has the right type and every required key is present. The accounts-payable team, spot-checking a sample by hand, still finds invoices whose line-item totals don't add up to the printed grand total, plus a few where the emitter's and recipient's CNPJ ended up swapped between fields. Both extractions were schema-valid the entire time. What is the most effective way to catch cases like these going forward?

- **A)** Add `minimum`, `maximum`, and `multipleOf` constraints to the numeric fields in the schema so out-of-range or mismatched values fail validation.
- **B)** Double-check that `strict: true` is set on the tool definition, since that is what guarantees the model can't skip a required numeric field.
- **C)** Increase `max_tokens` so the model has enough room to compute the correct sum before returning the tool call.
- **D)** Add a validation step in code, after extraction, that checks the arithmetic and cross-field relationships no JSON schema can express.

## Q4
A `categoria_despesa` field in an invoice-extraction schema is constrained to a four-value `enum`: `material`, `servico`, `frete`, `aluguel`. Finance keeps surfacing new expense categories every quarter — training courses, software subscriptions, insurance premiums — and each one gets forced into whichever of the four values seems closest, quietly corrupting spend reports. Every schema change to add a category currently requires a code review and a redeploy of the extraction service. Which design change most effectively handles this recurring pattern?

- **A)** Add each newly discovered category to the enum as it comes up, keeping the list current with a small schema update and a fresh service redeploy each time.
- **B)** Add an `"outro"` enum value with a free-text `categoria_detalhe` field, plus an `"indefinido"` value for genuinely ambiguous cases.
- **C)** Replace the enum with a free-text string field entirely, so the model can describe the expense category however it sees fit.
- **D)** Ask the model to report a confidence score alongside its category choice, and route anything scored below a fixed threshold to manual review.

## Q5
A pipeline registers `extract_metadata`, `extract_line_items`, and `enrich_vendor` as tools available to the model within a single turn. Both `enrich_vendor` and `extract_line_items` need a `document_id` value that only `extract_metadata` produces. Logs show that on roughly 1 in 5 documents the model calls `enrich_vendor` before `extract_metadata` has run at all, and that call fails because `document_id` doesn't exist yet. `tool_choice` is currently `"auto"`. What is the most effective way to guarantee the correct order every time?

- **A)** Force `tool_choice` to `extract_metadata` on the first turn, then switch to `"auto"` or `"any"` once `document_id` exists.
- **B)** Set `tool_choice` to `"any"`, so the model is required to call some tool on every turn and the pipeline never stalls waiting on text.
- **C)** List `extract_metadata` first in the `tools` array passed to the API, on the theory that the model considers earlier entries first.
- **D)** Add a line to `extract_metadata`'s tool description stating plainly that it must run before `enrich_vendor` or `extract_line_items`.

## Q6
A validation gate runs after extraction and rejects any invoice batch where the sum of line-item totals doesn't match the printed grand total; the extraction itself is schema-valid on every record in the batch. One rejected batch gets a manual audit: the auditor pulls the original scanned invoice and confirms the extraction reproduces every printed number exactly, item by item — the vendor's own invoice has an arithmetic mistake, and the printed total itself is wrong, not the extraction. The team wants this batch to stop being blocked. What is the most effective next step?

- **A)** Loosen the validation gate's tolerance for how much the item sum and the printed total are allowed to differ, so smaller mismatches pass.
- **B)** Rewrite the extraction prompt to instruct the model to recompute and correct the total whenever the line items don't add up to it.
- **C)** Route the batch to human review, or return it to the vendor for correction, leaving the extraction and the gate exactly as they are.
- **D)** Re-run the extraction call on the batch a few more times until the numbers happen to line up with the printed total.
