# Simulado — 4.5 Design efficient batch processing strategies (CCA-F, Domínio 4)

**Tópico:** roteamento batch × síncrono pelo sinal observável "alguém fica bloqueado esperando", não pelo volume nem pelo custo (K2/S1); aritmética de submissão a partir do SLA — janela de até 24h **sem SLA de latência**, mais o tempo a jusante, que também consome o SLA (S2); `custom_id` como única correlação confiável, porque os resultados voltam em qualquer ordem (K4); tratamento de falha por classe — corrigir e chunkar o que estourou o contexto, reenviar sem modificação o erro de servidor (S3); tool use em batch — server tools rodam o loop server-side **dentro** do lote, tool definida pelo cliente exige uma **segunda** requisição (K3); dry run de uma requisição antes do lote quando a causa é o template compartilhado (S4)
**Exercício relacionado:** `exercicios/dominio-4/4.5_batch_processing.py`
**Formato:** múltipla escolha — 1 correta + 3 distratores (formato oficial da prova; questões em inglês)

6 questões. Uma única melhor resposta por questão.

## Q1
A CI pipeline runs two Claude-powered jobs: a weekly audit of dependency licenses across every manifest in the monorepo, whose report is read on Monday morning, and a static-analysis review that has to pass before a pull request can merge. Three weeks ago the team moved **both** jobs to the Message Batches API to capture the 50% discount. The weekly audit is unaffected. The pre-merge review now returns after a median of 6h11, once after 19h, and 34 pull requests are sitting in the queue waiting on it. What is the most effective correction?

- **A)** Shorten the processing window on the pre-merge batch to 15 minutes when the batch is created, so results arrive inside the review cycle.
- **B)** Return the pre-merge review to synchronous Messages API calls and leave the weekly license audit on the Batches API.
- **C)** Keep the pre-merge review on the Batches API but submit each pull request as its own one-request batch, since a smaller batch clears faster.
- **D)** Return both jobs to synchronous Messages API calls, so the whole CI pipeline runs on a single predictable latency profile.

## Q2
A structured-extraction service ingests supplier documents that arrive continuously through the day. The contract commits to delivering every document's extracted record to the client's warehouse within 30 hours of that document arriving. Documents are accumulated and submitted to the Message Batches API, which guarantees only that a batch completes within 24 hours. Downloading the results, validating them and loading them into the warehouse consistently takes another 2 hours after the batch finishes. Which submission schedule keeps the worst case inside the contract?

- **A)** Accumulate for 6 hours and submit 4 batches per day: the 30 hours of SLA minus the 24-hour batch window.
- **B)** Accumulate for 12 hours and submit 2 batches per day: half a day of arrivals per submission.
- **C)** Accumulate for 24 hours and submit 1 batch per day: one submission per arrival cycle.
- **D)** Accumulate for 4 hours and submit 6 batches per day: 30 hours minus 24 of batch and 2 of loading.

## Q3
A batch of 2,000 contracts comes back from the Message Batches API with 1,947 results of type `succeeded`. Of the 53 that did not succeed, 41 are `errored` with an `invalid_request_error` saying the request exceeds the model's context window — all 41 are scanned contracts over 300 pages — and 12 are `errored` with a server-side error and no further detail. The 53 missing records are due to the client tomorrow. What is the most effective recovery?

- **A)** Resubmit only the 53 failed requests, matched by `custom_id`: chunk each of the 41 oversized contracts into several requests, and resend the 12 server errors unmodified.
- **B)** Resubmit only the 53 failed requests with `max_tokens` raised on all of them, since the 41 that overflowed clearly need more room than the current ceiling allows.
- **C)** Resubmit the whole 2,000-contract batch with the request shape corrected, since reprocessing only part of it risks attaching returned results to the wrong contract.
- **D)** Add a classifier ahead of the batch that scores each contract and predicts which ones will fail, and submit only the contracts it predicts will succeed.

## Q4
An extraction pipeline submits 500 invoices per batch, each request carrying a `custom_id` derived from the invoice's file name. When the results come back, the pipeline iterates over them and writes the Nth result into the Nth row of its output table, where row N was reserved for the Nth invoice submitted. QA sampling finds that about 8% of the sampled rows are internally consistent — supplier, date and total all agree with one another — but belong to a different invoice than the one the row is labelled with. What is the most effective fix?

- **A)** Have each request's prompt echo back the row number it was given, and place the result into whichever row the model reports.
- **B)** Move the extraction to synchronous Messages API calls, since the ordering of results in a batch cannot be relied upon.
- **C)** Look up each result's `custom_id` and write the row it identifies, instead of writing by position in the result stream.
- **D)** Submit one invoice per batch, so that each batch returns exactly one result that cannot land in the wrong row.

## Q5
A weekly compliance pipeline extracts structured fields from 8,000 supplier certificates through the Message Batches API; nothing downstream reads the output before Monday. Two requirements are added. Each certificate must be checked against the currently effective version of a published technical standard, which is only available on the web. And the supplier's tax id must be validated against the company's ERP through `consultar_erp`, a tool the pipeline implements in its own code. Which assessment of what fits inside the batch is correct?

- **A)** Neither requirement fits: the Batches API does not support tool use, so the weekly pipeline has to move to synchronous Messages API calls.
- **B)** Both fit if each certificate is split into two requests in the same batch, one carrying the web lookup and one carrying the `consultar_erp` call.
- **C)** Both fit if `tool_choice` is set to `"any"`, which guarantees a tool call and lets the batch worker run both tools before the request ends.
- **D)** The web lookup fits — `web_search` is a server tool and the batch runs the same server-side loop — but `consultar_erp` needs a second request carrying its result.

## Q6
A nightly CI job builds 1,400 Claude requests from one shared template — one per changed file — and submits them as a single batch; the results have to be in the dashboard before the next morning's standup. This morning 1,358 of the 1,400 came back `errored`, every one an `invalid_request_error` naming the same parameter, which the template sets on every request it builds. The 42 that succeeded come from an older code path that builds its own request and never picked up the template. Nothing surfaced when the batch was created; the errors appeared only at retrieval. What is the most effective response?

- **A)** Fix the parameter in the template and resubmit only the 1,358 failed requests, matched by `custom_id`, keeping the 42 that already succeeded.
- **B)** Fix the parameter in the template, dry-run a single request through the synchronous Messages API to confirm it validates, then resubmit the whole batch.
- **C)** Fix the parameter, then submit three copies of the corrected batch and keep, for each `custom_id`, the result that agrees in at least two of the three.
- **D)** Fix the parameter and split the work into 14 batches of 100 requests, so that a validation error can only take down one batch instead of all of them.
