# Simulado — 4.1 Design prompts with explicit criteria to improve precision and reduce false positives (CCA-F, Domínio 4)

**Tópico:** critérios explícitos × instrução vaga, hedge de confiança que não move precisão, falso positivo como dívida de confiança, critério report/skip, desligar temporariamente uma categoria ruidosa, e severidade calibrada por exemplo de código

**Formato:** múltipla escolha — 1 correta + 3 distratores (formato oficial da prova; questões em inglês)

6 questões. Uma única melhor resposta por questão.

## Q1
A CI review job posts inline comments on every pull request. One of its criteria reads, in full: "check that new code is tested". Over the last sprint the job raised 47 coverage findings, and 31 were closed by the authors with some variation of "this branch is covered — the integration suite exercises it end to end". The 9 findings that pointed at a new branch no test reaches at all were accepted. Which change to that criterion is most effective at removing the rejected class?

- **A)** Narrow the criterion by path, raising coverage findings only for files under `src/`, so that helpers, fixtures and the integration suite itself stop being reviewed.
- **B)** Replace it with a longer, more emphatic paragraph stressing that coverage findings must be accurate, well-founded and genuinely worth the author's review time.
- **C)** Replace it with a boundary condition — raise a finding only when a new branch is reached by no test in the repository, unit or integration — plus a skip list.
- **D)** Keep the criterion and add a deterministic post-filter that discards any coverage finding whose line was not added by the diff under review, so that only newly added lines can be flagged.

## Q2
The comment criterion of the same CI review job was changed once: the line "be conservative; only report high-confidence findings" was appended, leaving the original wording — "check that comments are accurate" — in place. Across the next 60 pull requests the volume of comment findings fell from 3.1 to 2.4 per pull request, and the share closed as not-a-problem moved from 66% to 62%. The findings that survive are the same kind that were being rejected before. What best explains why precision barely moved, and what is the right correction?

- **A)** The criteria still name no condition about the code that makes a comment reportable, so filtering on self-reported confidence only thins the same set; state the condition — the comment contradicts actual behavior.
- **B)** The instruction landed at the end of the prompt, where it competes with the earlier wording; moving it above the review request and repeating it per category would let it take effect.
- **C)** The reviewer's confidence estimates are miscalibrated for this repository; adding a numeric `confidence` field to the tool schema and dropping every finding scored below 0.8 would enforce deterministically what the appended sentence merely requests.
- **D)** The run does not see enough of the repository to judge a comment, so its confidence is uniformly low; giving the job the whole module tree instead of the diff would let it discriminate.

## Q3
A structured extraction pipeline pulls 22 fields per contract, and a QA pass flags mismatches against the source document in five categories. Over 300 contracts, `payment_terms` flags are wrong 71% of the time, while the other four categories stay between 9% and 12%, unchanged since launch. Reviewers used to clear flagged records within a day. Last month three `bank_account` flags sat untouched for two weeks, and two of those records shipped wrong. Which analysis best accounts for this, and what follows from it?

- **A)** The review queue is the bottleneck: flagged records now outgrow what one reviewer clears in a day, so adding a second reviewer to the rotation would drain the backlog and get `bank_account` picked up again.
- **B)** Reviewers need the measured per-category precision printed in the report header, so that they can discount `payment_terms` on their own and keep acting on the other four categories.
- **C)** Set a `min_precision` threshold per category in the QA tool's `input_schema`, so that the platform withholds flags from any category measured below it and `payment_terms` stops reaching the report.
- **D)** A noisy category's false positives are not contained in it: they set the reader's expectation for the whole report, so the fix must target `payment_terms` itself.

## Q4
An extraction QA agent compares 300 extracted invoice records against their source PDFs. Its instruction is "report anything that looks off, but only when you are confident". Last week it raised 240 issues, each tagged with a severity the agent picks itself: 180 were formatting variants the target schema already accepts (`USD 1,200.00` versus `1200.00`) or conventions of one vendor's own template; among the rest, four real mismatches — including a wrong tax ID — were reported and then lost in the pile. Which rewrite of the instruction is most effective?

- **A)** Raise the bar of the existing hedge, so that an issue is reported only when the agent is more than 90% confident that what it found is a genuine mismatch against the source.
- **B)** Replace it with two explicit lists — REPORT: the value contradicts the source document, or a required field is missing; SKIP: formatting variants the schema accepts, and vendor-template conventions.
- **C)** Keep the instruction and add a second model pass that reads every issue the first pass produced and keeps only the ones it independently agrees are genuine mismatches.
- **D)** Replace the hedge with a gate that discards every issue the agent labels `minor`, so that only `important` or `blocker` issues reach the human triage queue.

## Q5
A CI review bot posts findings in four categories. Over three weeks, `comment_accuracy` was wrong in 68% of the findings it raised; `bug` and `security` were wrong in 11%. Five of the team's eight developers now dismiss the bot's whole comment thread without opening it, and two real `security` findings were dismissed that way last week. Rewriting the comment criteria and measuring the rewrite will take roughly a sprint. Which is the best move for that sprint?

- **A)** Keep all four categories and add a line to the criteria asking the bot to be conservative about comment findings until the rewritten criteria are ready to ship.
- **B)** Keep posting comment findings but mark them as low-confidence and collapse them by default, so developers can skip past them without losing the rest of the thread.
- **C)** Replace the comment criteria with a gate that drops a comment finding unless the diff under review touches the function the comment documents, while a rewrite is prepared.
- **D)** Drop `comment_accuracy` from the review criteria while it is rewritten and measured, leaving `bug` and `security` posting; the category returns once its criteria carry a boundary.

## Q6
An extraction QA pipeline assigns every mismatch a severity that routes it to a triage lane. The criteria read: "blocker = critical issues; important = significant issues; minor = small issues". Re-running the same 300 documents produced a different severity for 41% of the mismatches. In the current queue, a trailing space in a company name sits in the blocker lane, while a payee bank account that differs from the source document sits in minor. Which change most effectively produces consistent severity?

- **A)** Run the severity classification three times for each mismatch and keep the label that at least two of the three runs assign, discarding the minority label as sampling noise.
- **B)** Replace the adjectives with one worked example per level — blocker: a payee account that differs from the source; minor: a label naming three fields where the record has four.
- **C)** Have the pipeline emit its own confidence in each severity label and route only the high-confidence ones into the lanes, holding everything else for a human to classify.
- **D)** Split severity into a second pass that sees only the mismatch and the three level names, so that the label is chosen without the extraction task competing for the model's attention.
