# Simulado — Task Statement 4.6: Design multi-instance and multi-pass review architectures

> Domínio 4 · 6 questões · escolha a **única melhor** resposta.

## Q1
A CI pipeline uses Claude Code to generate database migration modules, then — in the same session, immediately after generation — asks it to review its own implementation critically before opening the pull request. Over six weeks, 34 defects reached the main branch. The post-mortem found that 29 of them were plainly visible in the generated diff. Which change is most likely to raise the capture rate?

- **A)** Strengthen the self-review instruction, enumerating the defect categories the model must check for before it opens the PR.
- **B)** Raise the reasoning effort on the review turn so the model spends more thinking tokens questioning the implementation.
- **C)** Send the generated diff to a second Claude instance that carries none of the generation context, and use its findings as the review.
- **D)** Widen the context window for the review turn so the entire diff, including the full migration history and prior pull requests, fits comfortably with plenty of room to spare.

## Q2
A structured-extraction service spans 22 modules. Its review step sends every changed file in one prompt and asks for a single list of findings. Over three sprints the reports have contradicted themselves — the same function flagged as a defect in one entry and accepted in another — while four defects caused by two modules disagreeing about a dictionary key shipped to production. Which restructuring is most effective?

- **A)** Run one focused pass per file for local issues, plus a separate integration pass over the module interfaces and call sites.
- **B)** Keep the single prompt but raise `max_tokens`, so the findings list is never truncated.
- **C)** Run the single prompt three times and report only the findings that appear in at least two of the runs.
- **D)** Order the files in the prompt by change frequency and recent commit volume, so the riskiest and most actively edited ones are reviewed while attention is freshest.

## Q3
A CI review step runs one Claude pass per changed file, roughly five files per pull request. Across 11 sprints those passes have produced zero findings of the form "one module writes a field under one name and another reads it under a different name" — even though four production incidents in the same period had exactly that cause. The team concludes the reviewer model is too weak for subtle issues. What is the most likely root cause?

- **A)** The task genuinely exceeds the model's capability, so a more capable model is required for this class of issue.
- **B)** No pass ever receives both sides of the contract, so the architecture has no place where this class of defect can be found.
- **C)** The reported findings are being filtered out by the confidence threshold before they reach the report.
- **D)** `max_tokens` truncates the findings list before the cross-file issues are reached.

## Q4
A team building a structured-data-extraction pipeline changed its review step to avoid re-sending the whole codebase: instead of starting a new session, the reviewer now resumes the generator's session with `--resume`, reasoning that the relevant context is already loaded. Capture rate of subtle defects fell from 71% to 43% over the following month, with no other change. What best explains the drop?

- **A)** The resumed session accumulated the generation transcript, so `/compact` should run before the review to reduce dilution.
- **B)** The resumed session lost the tool permissions the review step depends on, so parts of the review silently did not run.
- **C)** The reviewer needs `fork_session` when resuming, so that its findings do not mutate the generator's session state.
- **D)** Resuming carries the generator's reasoning into the review, so the reviewer conditions on the very decisions it is supposed to question.

## Q5
An independent review instance in CI produces about 40 findings per pull request, and spot checks show roughly 9 out of 10 are real. Engineers have started ignoring the report, because reading 40 findings takes longer than the change itself. There is no budget for a different model or for training anything. Which is the most effective next step?

- **A)** Block the merge whenever any finding carries a self-reported confidence above 0.8, so the important ones cannot be ignored.
- **B)** Train a classifier on six months of accepted and rejected findings, and use it to rank the report.
- **C)** Have each finding carry a self-reported confidence, auto-apply the high-confidence ones, route the rest to a human queue, and publish the hit rate per confidence band so the routing is calibrated rather than assumed.
- **D)** Drop the low-confidence findings from the report, so what engineers do read is the part most likely to be real.

## Q6
A pull-request review budget allows exactly six Claude calls per PR, and a typical PR touches five modules. Of nine production incidents last quarter, seven were caused by two modules disagreeing about the shape or meaning of the data crossing between them, and two were contained inside a single file. Which allocation of the six calls is best?

- **A)** Five passes, one per module, plus one integration pass over the module interfaces and call sites.
- **B)** Six independent passes over all five modules at once, reporting the union of their findings.
- **C)** Six per-file passes: one per module, with the largest module reviewed twice.
- **D)** One pass over all five modules at once, spending the remaining budget on higher reasoning effort for that single pass.
