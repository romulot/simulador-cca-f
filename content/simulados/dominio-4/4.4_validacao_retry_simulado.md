# Simulado — 4.4 Implement validation, retry, and feedback loops for extraction quality (CCA-F, Domínio 4)

**Tópico:** retry com feedback de erro específico guia a correção, retry cego repete a mecânica sem o sinal (K1); o retry tem limite — quando o dado só existe numa fonte não fornecida, retry não cria o dado, e a resposta é escalar (K2); uma taxa global de resolução esconde o limite do retry — a leitura correta separa por classe de erro antes de agir (S2); campos de auto-verificação no schema (`calculated_total`/`stated_total`/`conflict_detected`) deixam o modelo sinalizar divergência antes de gastar retry (S4); `detected_pattern` nos achados mostra em que construto o descarte se concentra (K3, S3), e descarte por `wont_fix` não é falso positivo — não some com `nao_e_defeito` na leitura de concentração

**Formato:** múltipla escolha — 1 correta + 3 distratores (formato oficial da prova; questões em inglês)

## Q1
A structured-extraction agent calls `extrair_registro` against a scanned maintenance log, and `pydantic` validation rejects the result: the `data_leitura` field came back as `"14.07.2026"`, while the schema requires ISO `YYYY-MM-DD`. The harness has exactly one retry left for this document, and the validator already reports the exact field and the exact rule that failed. What is the most effective way to spend that retry?

- **A)** Send a brand-new turn with the same document and the plain instruction "please try again," without referencing the prior tool call or the validation failure.
- **B)** Return the failure as a `tool_result` with `is_error: true`, naming the field and rule violated, keeping the document and failed extraction in context.
- **C)** Discard the conversation and start over from a rewritten system prompt, since the first extraction attempt already failed once.
- **D)** Add two or three new few-shot examples showing date fields converted to ISO format to the prompt, then restart the extraction from scratch with the revised prompt.

## Q2
An invoice-extraction pipeline validates `numero_ordem_compra` against a fixed numbering pattern. On one invoice, the purchase order never appears anywhere in the pages the pipeline ingested — it only exists in a separate attachment that ingestion never captured. After 3 retries, each fed the validator's exact pattern-mismatch error, the field still fails: two attempts return a plausible but wrong number, one returns an empty string the validator also rejects. What is the most effective next step?

- **A)** Raise the retry ceiling from 3 to 6 attempts, since each retry so far has carried the same specific validation signal back to the model.
- **B)** Relax the validator so it accepts an empty string for `numero_ordem_compra`, since that at least lets the field through without failing the batch.
- **C)** Add a line to the prompt instructing the model to never invent a purchase-order number that isn't printed anywhere in the text it was given.
- **D)** Escalate the document for human review, or re-ingest it with the attachment included; no number of retries manufactures a value that was never in the pipeline's input.

## Q3
Across a batch of 200 documents, an extraction pipeline retries up to 3 times per document, feeding back the validator's specific error each time, and lands on 60% overall resolution — 40% of documents still fail after exhausting the retry budget. A team lead, looking only at that single aggregate number, proposes raising `max_tokens` pipeline-wide to close the remaining gap. Before changing anything, what is the most effective first step?

- **A)** Break the remaining 40% down by error class before deciding what to change: fixable by retry, absent from the source, or malformed and truncated.
- **B)** Increase `max_tokens` for every call in the pipeline, on the reasoning that a higher ceiling helps borderline cases and leaves calls that already pass unaffected.
- **C)** Add a lightweight document-quality classifier upstream that scores each document and flags the ones likely to fail before extraction even starts, routing them for separate handling.
- **D)** Ask the model to report a confidence score with each attempt, and treat any attempt scoring below a fixed threshold as a failure to be retried.

## Q4
A CI code-review gate uses Claude to flag risky patterns before merge. Looking at `detected_pattern × desfecho` over the last window of findings, the construct `comentario-desatualizado` (stale comment) has 9 of 11 flags discarded by reviewers as `nao_e_defeito` — reviewers note the flagged comment sits above the function while the team treats the module-level docstring, not the inline comment, as the actual contract. Every other construct in the same window gets accepted well over 80% of the time. What is the most effective fix?

- **A)** Turn off the CI gate for this repository until the false-positive rate on `comentario-desatualizado` improves.
- **B)** Add a post-hoc classifier that reviews each `comentario-desatualizado` finding and filters out the ones likely to be discarded before a reviewer ever sees them.
- **C)** Narrow the criterion so it flags a comment only when its claimed behavior contradicts the code directly below it, not cases already covered by module-level docs.
- **D)** Instruct the model to only report a `comentario-desatualizado` finding when its own self-reported confidence in that particular finding is high, quietly suppressing the rest.

## Q5
An invoice-extraction schema captures line items and a single `valor_total` field. In about 8% of invoices, a downstream check finds that the recomputed line-item sum disagrees with `valor_total` — but only after the extraction call has already returned and been accepted, forcing a full retry cycle to resolve it. The team wants the model to surface a mismatch during the same call it's already making, not after. What is the most effective schema change?

- **A)** Add `minimum` and `multipleOf` constraints on `valor_total`, mirrored on each line item, so any out-of-range or misaligned value fails schema validation before the response is ever accepted.
- **B)** Add `calculated_total` and `stated_total` alongside a boolean `conflict_detected`, so a mismatch is visible in the response instead of only surfacing downstream.
- **C)** Add a line to the prompt asking the model to double-check that the line items add up to the total before answering.
- **D)** Keep the schema as it is, and retry the extraction call repeatedly until the recomputed sum happens to match the stated total.

## Q6
A CI code-review gate flags every direct floating-point equality comparison (`if valor == 0.30:`) as risky. Looking at `detected_pattern × desfecho`, the construct `comparacao-float-igualdade` shows 2 of 2 flags discarded, both logged as `wont_fix` — both notes read "defeito real de ponto flutuante, mas o script legado será substituído no próximo trimestre." No other construct in the same review window is discarded at 100%. A teammate proposes narrowing the detection criterion for `comparacao-float-igualdade` so this file stops being flagged. What is the most effective response?

- **A)** Narrow the criterion so it no longer flags floating-point equality comparisons in these specific functions, since 100% of its flags here get discarded.
- **B)** Turn off the `comparacao-float-igualdade` construct entirely, since it hasn't produced a single accepted finding in this review window.
- **C)** Lower the severity assigned to `comparacao-float-igualdade` findings, so they stop competing for reviewer attention with higher-priority flags.
- **D)** Leave the criterion, the construct, and the severity as they are — the findings are correct, and `wont_fix` reflects a scheduling decision, not a flaw in detection.
