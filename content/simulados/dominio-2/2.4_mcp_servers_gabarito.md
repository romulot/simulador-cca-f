## Q1 — Resposta correta: **B** · (2.4)

Este é o item de **quebra-automatismo** (§10) deste tópico: nas Q2 e Q5 seguintes,
"para compartilhar uma ferramenta com o time, commite em `.mcp.json`" é o
comportamento correto. Aqui esse mesmo reflexo está **invertido**:
`ticket-summarizer` é um experimento pessoal, ainda não revisado, e commitá-lo em
qualquer `.mcp.json` do time — mesmo com um aviso informal — expõe um servidor não
vetado a quem clonar o repositório. O scope certo para "meu, em qualquer
repositório que eu abrir, sem tocar no que o time compartilha" é o **user scope**
(`~/.claude.json`): uma única entrada, válida para o engenheiro em qualquer um dos
repositórios testados, sem aparecer para ninguém que clone o projeto.

- **A — errada:** local scope funciona tecnicamente (fica fora do `.mcp.json`
  versionado), mas exige recriar a mesma entrada em cada um dos 6 repositórios
  testados — granularidade errada para algo pessoal ao engenheiro, não
  pessoal-e-específico-de-um-repositório. (Camada/alvo errado.)
- **B — correta.**
- **C — errada:** commitar em `.mcp.json` e pedir por Slack que o time ignore o
  servidor é exatamente o reflexo que as Q2/Q5 deste tópico ensinam como correto
  para *ferramentas já vetadas do time* — aqui ele expõe um servidor não revisado
  a todo mundo que clonar o repositório, e depende de um aviso informal
  (não determinístico) em vez do mecanismo de scope. (Probabilístico onde
  precisa ser determinístico.)
- **D — errada:** não existe um quarto scope "staging" em `.mcp.json` — os três
  únicos scopes são local, project e user (local > project > user).
  (Feature inexistente porém verossímil.)

## Q2 — Resposta correta: **C** · (2.4)

**Scope decide compartilhamento.** `linter-rules` precisa chegar a todo
desenvolvedor que clona o repositório — isso é exatamente o que o `.mcp.json`
versionado no git entrega automaticamente. `scratch-notes` é pessoal e não deve
ir para um arquivo que todo o time recebe ao clonar — pertence a `~/.claude.json`
(user scope), fora do repositório.

- **A — errada:** `~/.claude.json` não é compartilhado por clonagem do repo; um
  novo desenvolvedor não receberia `linter-rules` automaticamente — é exatamente
  a falha que já está ocorrendo (3 de 5 contratações perderam o passo manual).
  (Camada/alvo errado.)
- **B — errada:** colocar `scratch-notes` (pessoal) no `.mcp.json` versionado
  expõe a configuração pessoal de cada desenvolvedor a todo o time que clonar o
  repo — usa o scope compartilhado para algo que deveria ser privado.
  (Camada/alvo errado.)
- **C — correta.**
- **D — errada:** encurtar o bloco manual reduz o atrito, mas não resolve a causa
  raiz (dependência de um passo humano lembrado); o requisito é automático e
  determinístico ao clonar — só o `.mcp.json` versionado garante isso.
  (Probabilístico onde precisa ser determinístico.)

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Aplicar
- Dificuldade: Médio
- Rubrica: 5 = Bloom 2 + integração 1 + cenário 1 + distratores 1
- Cenário: S4 — Developer Productivity
- Princípio testado: scope decide compartilhamento — `.mcp.json` versionado (time) vs `~/.claude.json` (pessoal)

O enunciado já afirma que **nem `SEARCH_API_URL` nem `SEARCH_API_KEY`** foi

ausente. `SEARCH_API_KEY`, porém, **não tem default** e é obrigatória: sua

- **B — errada:** uma variável obrigatória sem default não vira silenciosamente
  uma string vazia — o comportamento real é falha de parsing, não conexão com
  credencial em branco; e o log já diz que não é erro de conexão.
  (Equívoco de capacidade.)
- **C — errada:** não existe "avaliação só na primeira leitura após clone" para
- **D — correta.**
  `${VAR:-default}` — cada carregamento do config resolve as expansões de novo;

## Q4 — Resposta correta: **A** · (2.4)

A regra central do 2.4: **não há merge de campos entre scopes**. O scope de
maior precedência (local, neste caso) vence com a **entry inteira**, inclusive
nos campos que ela não define. Como o override local não tem `timeout`, o
cliente aplica seu próprio default genérico — o valor de 30s do `.mcp.json`
(project) simplesmente não é considerado, porque o project scope perdeu por
completo, não parcialmente.

- **A — correta.**
- **B — errada:** não existe precedência "por tipo de campo" (numérico vs
  string) — a precedência é por **scope inteiro**, não por campo.
  (Feature inexistente porém verossímil.)
- **C — errada:** local scope também se aplica a overrides de um server já
  definido em `.mcp.json` — não só a servers novos; isso descreve errado o
  próprio mecanismo central do tópico. (Equívoco de capacidade.)
- **D — errada:** a precedência é definida por scope (local > project > user),
  não por ordem alfabética de arquivos, e não há "comparação campo a campo"
  entre arquivos. (Feature inexistente porém verossímil.)

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Médio
- Rubrica: 6 = Bloom 3 + integração 1 + cenário 1 + distratores 1
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: precedência usa a entry inteira do scope vencedor — sem merge de campos

## Q5 — Resposta correta: **B** · (2.4)

O problema real é que a credencial está **literal e duplicada** em 40 arquivos.
A **env var expansion** (`${DOCS_SEARCH_TOKEN}`) resolve isso sem nenhuma
infraestrutura nova: os 40 `.mcp.json` passam a só **referenciar** a variável, e
uma rotação futura exige mudar o valor da variável onde ela é definida, não os
40 arquivos commitados. É a resposta de menor esforço que ataca a causa raiz.

- **A — errada:** construir um microserviço para empurrar o arquivo atualizado
  para 40 repositórios é resolver com infraestrutura nova algo que a expansão de
  env var já resolve nativamente, sem nenhum serviço adicional.
  (Over-engineering.)
- **B — correta.**
- **C — errada:** um hook que bloqueia qualquer commit tocando `.mcp.json`
  ataca a camada errada — dificulta editar o arquivo, mas não elimina as 40
  cópias literais da credencial nem reduz a superfície de cópia-e-cola exigida
  na rotação. (Camada/alvo errado.)
- **D — errada:** `.mcp.json` é por repositório; symlinkar o arquivo entre 40
  repositórios independentes (histórico de git e checkout próprios cada um) não
  é um mecanismo real suportado. (Feature inexistente porém verossímil.)

## Q6 — Resposta correta: **A** · (2.4)

**Tool** = ação que o modelo executa ativamente (`fetch_latest_price`, que muda a
cada chamada e aparece como `mcp__<server>__fetch_latest_price`).
`create_sdk_mcp_server` / `createSdkMcpServer` registra **somente tools** — a
função aceita um array `tools`; não existe parâmetro `resources`, e um server
MCP in-process criado por ela não pode registrar resources endereçáveis (doc
oficial, code.claude.com/docs/en/agent-sdk/custom-tools.md, seção "Create a
custom tool": `create_sdk_mcp_server(name=..., version=..., tools=[...])`).
**Resource** = dado referenciável sob demanda (`@server:protocol://memo-id`), só
puxado para o contexto quando o subagente decide que é relevante — suportado por
servers MCP **conectados externamente** (aqui, `research-docs`), que implementam
a capability `resources/list` do protocolo. Escopar `allowed_tools` só para os
subagentes que precisam de preço ao vivo aplica least privilege sobre a tool,
mantendo o memo acessível como referência leve do server externo.

- **A — correta.**
- **B — errada:** é tecnicamente possível registrar o memo como tool no server
  in-process (o primitivo é tools-only, mas nada impede modelar uma busca por ID
  como tool) — mas isso descarta a semântica de referência sob demanda: qualquer
  subagente que "ache que talvez precise" dispara uma chamada ativa contra 200
  memos em vez de só puxar o que julga relevante como anexo leve. O custo **não**
  é "o mesmo de qualquer forma": uma tool call executa (e cobra latência/tokens
  de resultado) toda vez que é chamada, enquanto a resource só entra no contexto
  quando de fato referenciada. (Camada/alvo errado — usa o primitivo certo para a
  coisa errada.)
- **C — errada:** `create_sdk_mcp_server` **não** registra resources — não existe
  esse parâmetro na função, só `tools`. Tratar a cotação ao vivo (que muda a cada
  chamada) como resource também inverteria o papel do primitivo: resource é dado
  passivo referenciável, não uma operação que precisa rodar de novo a cada
  chamada. (Feature inexistente porém verossímil.)
- **D — errada:** conceder `allowed_tools` a todos por padrão e confiar num
  lembrete no system prompt é enforcement não-determinístico onde
  `allowed_tools` já é o mecanismo determinístico de least privilege por papel.
  (Probabilístico onde precisa ser determinístico.)

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 8 = Bloom 4 + integração 2 + cenário 1 + distratores 2
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: casar a ferramenta ao requisito — `create_sdk_mcp_server` é tools-only (in-process); resources endereçáveis via `@server:protocol://...` vêm de servers MCP conectados externamente; `allowed_tools` para least privilege
