## Q1
Across a two-week trace review of the Customer Support Resolution Agent (Scenario 1), 100% of failing tool calls return the identical payload — `{"isError": true, "message": "Operation failed"}` — regardless of whether the underlying cause was a network timeout, an invalid order ID, or a refund request outside the policy window. The agent's behavior is inconsistent across these cases: it silently retries some calls a dozen times, drops others without telling the customer anything, and occasionally reports "system error" when the real issue is a business rule. What is the single most effective fix?

- **A)** Route every failing tool call through a small classifier model that reads the free-text error message and predicts, on every turn, which of the three failure types — network outage, invalid input, or policy violation — it most likely belongs to, then branches all downstream retry and messaging behavior on that prediction.
- **B)** Replace the uniform payload with structured fields — `errorCategory` (transient/validation/business/permission), `isRetryable`, and a customer-facing `message` — so retry logic and customer messaging are both driven by machine-readable metadata, not generic text.
- **C)** Have the agent infer the failure type from the tone of the error message text (e.g., words like "invalid" versus "timeout" versus "policy") and choose a retry strategy based on that inferred tone.
- **D)** Add a `--strict-errors` flag to the MCP server configuration so every tool throws a native Python exception instead of returning `isError: true`, letting the harness's built-in exception handler classify and manage every retry automatically, with no change to the tool's response shape.

## Q2
In the Multi-Agent Research System (Scenario 3), a source-summarization subagent's tool scope includes only read tools (`search_sources`, `fetch_source`) — it was never granted write access to the shared knowledge store. When the subagent calls `update_shared_knowledge_base(entry)` to persist a new finding, the call is rejected by the MCP server on every attempt, regardless of the entry's content — the rejection is about the caller's authorization, not the data itself. The tool must return a structured error so the subagent stops wasting cycles and doesn't try to work around the rejection. Which response is correct?

- **A)** Return `{"errorCategory": "transient", "isRetryable": true}` and have the subagent retry a bounded number of times before giving up, on the assumption that an access rejection might clear up the way a brief network blip would.
- **B)** Return `{"errorCategory": "permission", "isRetryable": false}`, stop retrying, and escalate to the coordinator so a properly-scoped agent performs the write or the subagent is granted the needed scope.
- **C)** Keep calling `update_shared_knowledge_base` with the entry reworded or reformatted in different ways, on the theory that a different phrasing of the request might get past the rejection.
- **D)** Return `{"errorCategory": "validation", "isRetryable": false}` and ask the caller to check the entry's schema, since the call is failing on this attempt.

## Q3
In the Developer Productivity agent (Scenario 4), a `run_lint` tool call fails because the caller passed a file path that does not exist in the repository — the same literal, unchanged path on every attempt. Logs show the harness retries this exact call three times, each attempt failing identically, before the run finally times out and reports a generic error to the developer. The tool's response for this failure sets `errorCategory: "transient"` and `isRetryable: true`. What is the most likely root cause of the wasted retries, and the correct fix?

- **A)** The failure is a validation error, not a transient one — retrying the exact same invalid file path can never succeed because the input never changes; `run_lint` should return `errorCategory: "validation"` and `isRetryable: false` (or a caller-correction hint) instead of `transient`/`true`.
- **B)** The harness's retry loop has a bug that ignores `isRetryable` on this call, retrying three times before giving up; the fix is to increase the model's `max_tokens` so it can reason more carefully before each retry attempt.
- **C)** The problem is that `run_lint`'s `description` field does not explain what a valid file path looks like; rewriting the description to include a regex pattern for valid paths will stop the harness from retrying.
- **D)** This is expected, safe behavior — three retries is a reasonable conservative default for any tool failure, and no change is needed since the run eventually terminated with a message to the developer.

## Q4
Telemetry across 500 Customer Support Resolution Agent (Scenario 1) sessions shows that when `search_order_history` is called for a customer account with zero past purchases, the tool returns `{"orders": [], "isError": true}`. In 100% of these cases the agent retries the identical call up to the configured retry limit, then tells the customer "we're experiencing a system issue, please try again later" — even though the account genuinely has no orders. What is the most likely root cause and correct fix?

- **A)** Raise the configured retry limit so the agent has more attempts to eventually find the customer's order history, since the current limit is likely too low for this case.
- **B)** Treat this as a permission error — the customer's account role may lack sufficient scope to view order history — and escalate to a human for a permissions review before responding.
- **C)** Recognize that zero matches is not a failure: `search_order_history` should return `{"orders": [], "isError": false}` so the agent can tell the customer no orders were found.
- **D)** Escalate to a human based on the agent's self-reported confidence in the tool's result falling below a 90% threshold, treating this zero-result response as triggering the same low-confidence escalation path used for other tool outputs.

## Q5
In the Multi-Agent Research System (Scenario 3), a synthesis subagent queries four independent sources for a competitive-analysis report. Three sources return usable data; the fourth times out after exhausting its local retry budget (2 of 2 attempts, both transient). All four attempts and their outcomes are logged. The subagent must now decide what to hand back to the coordinator so the final report is both useful and honest about its coverage. Which handoff is the single best choice?

- **A)** Discard the three successful results and report only a generic failure to the coordinator, since a single source's failure means the retrieval as a whole cannot be trusted.
- **B)** Only include a source's data in the handoff if at least two independent passes over that source agree on the same figures — including re-running the three sources that already succeeded cleanly on their very first pass — and discard anything that fails to reach that same agreement threshold.
- **C)** Silently fill in the fourth source's data with the most similar prior report's figures as a placeholder, so the coordinator receives a report that looks complete across all four sources.
- **D)** Return the three successful results plus a structured note of what was attempted against the fourth source (e.g., `attempted: "source_4: 2/2 retries exhausted"`), letting the coordinator decide whether to retry, flag the gap, or proceed with partial coverage.

## Q6
The Customer Support Resolution Agent (Scenario 1) wraps a third-party payment gateway whose API returns only a fixed set of plain-text error strings (e.g., `card_declined`, `gateway_timeout`, `invalid_cvv`) with no structured category field — the gateway is external and cannot be modified. A telemetry review shows the agent currently treats every one of these strings identically, retrying `card_declined` and `invalid_cvv` just as often as `gateway_timeout`, wasting an estimated 30% of its tool-call budget on inputs that can never succeed on retry. Which fix is most appropriate given that the upstream API's output format is fixed?

- **A)** Add a thin, deterministic mapping layer inside the tool wrapper that translates each of the gateway's fixed, known plain-text strings into a structured `errorCategory`/`isRetryable` pair (e.g., `gateway_timeout` → transient/retryable; `card_declined`, `invalid_cvv` → business or validation/non-retryable), since the upstream API's finite, unchanging error vocabulary is exactly what a fixed lookup table covers.
- **B)** Leave the raw strings as-is and add a line to the agent's system prompt such as "if the payment error message contains 'declined' or 'invalid', don't retry it," letting the model's own reading of the text decide whether to retry each time.
- **C)** Train a text-classification model on historical payment error strings to predict whether each new string is retryable, since a lookup table would require manual maintenance whenever the gateway adds new error strings.
- **D)** Escalate this payment error to a human based on the agent's self-reported confidence that the customer will be satisfied falling below a threshold, rather than on which underlying gateway string was actually returned.
