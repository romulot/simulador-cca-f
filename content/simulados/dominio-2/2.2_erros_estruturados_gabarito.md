# Gabarito — Domínio 2 · Task Statement 2.2

**Tema:** Implement structured error responses for MCP tools
Explicações em PT-BR. Todas as questões exercitam o **TS 2.2**.

---

## Q1 — Resposta correta: **B** · (2.2)

O anti-padrão central do tópico: um payload **uniforme e genérico** (`"Operation failed"`) não carrega `errorCategory` nem `isRetryable`, então nem o harness (retry) nem o agente (comunicação com o cliente) têm sinal para agir de forma diferente entre timeout de rede, ID inválido e violação de política. A correção é fazer a **tool** devolver esses campos estruturados — a decisão de retry e a mensagem ao cliente passam a vir dos metadados, não de texto livre.

- **A — errada:** treinar um classificador para inferir o tipo de falha a partir do texto do erro é **over-engineering** — adiciona uma camada de ML para reconstruir exatamente a informação (`errorCategory`) que a tool já deveria devolver estruturada de fábrica.
- **B — correta.**
- **C — errada:** inferir a falha pelo **tom** da mensagem de erro é um **proxy plausível não confiável** — tom textual não é um sinal confiável de categoria de erro (é a mesma lógica frágil de usar sentimento como proxy).
- **D — errada:** não existe flag `--strict-errors` no MCP server que transforme `isError` em exceção nativa — **feature inexistente porém verossímil**, soa a uma opção real de configuração mas não corresponde a nada do protocolo.

**Nota de nomenclatura:** a Messages API usa o campo snake_case `is_error` (dentro de um bloco `tool_result`); MCP usa camelCase `isError` na resposta da tool. Mesmo conceito, grafia diferente conforme o contexto — não confundir os dois nem tratá-los como campos distintos.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Aplicar
- Dificuldade: Médio
- Rubrica: 5 = Bloom 2 + integração 1 + cenário 1 + distratores 1
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: metadados estruturados (`errorCategory`/`isRetryable`) como base da decisão de retry e comunicação, não o texto do erro

## Q2 — Resposta correta: **B** · (2.2)

A rejeição acontece em **100% das tentativas independentemente do conteúdo** do `entry` — isso é a marca de um problema de **autorização/escopo**, não de disponibilidade transitória nem de formato de dado. `update_shared_knowledge_base` deveria devolver `errorCategory: "permission"` e `isRetryable: false`, e o subagente deve **parar de tentar** e **escalar ao coordenador** — seja para que um agente com o escopo correto faça a escrita, seja para que o escopo do subagente seja ampliado.

- **A — errada:** tratar a rejeição como `"transient"`/`isRetryable: true` e retry limitado é **equívoco de capacidade** — supõe que a rejeição pode "passar" como uma falha de rede passageira, mas a causa é a autorização do chamador, que retry nenhum muda.
- **B — correta.**
- **C — errada:** insistir reformulando ou reformatando o `entry` na esperança de que uma frase diferente "convença" o gate é **probabilístico onde precisa ser determinístico** — autorização é um portão fixo (concedida ou não), não uma questão de fraseado que o modelo possa contornar por tentativa e erro.
- **D — errada:** rotular como `"validation"` e mandar o chamador checar o schema do `entry` é **camada/alvo errado** — atribui a falha ao formato do dado quando a causa real é a ausência de escopo de escrita; "corrigir" o schema não resolve nada.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Aplicar
- Dificuldade: Médio
- Rubrica: 5 = Bloom 2 + integração 1 + cenário 1 + distratores 1
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: permission→não retryable; a resposta correta é escalar para reautorização, não retry nem reformular a chamada

## Q3 — Resposta correta: **A** · (2.2)

Repetir a **mesma chamada com o mesmo input inválido** nunca muda o resultado — isso é a marca registrada de um erro de **validação**, não transitório. Rotular como `transient`/`isRetryable: true` faz o harness desperdiçar tentativas em algo que não pode se resolver por repetição. A correção é a `run_lint` devolver `errorCategory: "validation"` e `isRetryable: false` (ou um caminho de correção do input pelo chamador).

- **A — correta.**
- **B — errada:** culpar um "bug do harness que ignora `isRetryable`" e propor aumentar `max_tokens` é **equívoco de capacidade** — mais tokens não corrige uma classificação de erro incorreta na tool; o campo enviado já está errado (`transient`/`true`), então o harness só está seguindo (corretamente) um metadado mal atribuído.
- **C — errada:** reescrever a `description` da tool com um regex de caminho válido ataca a camada errada — **camada/alvo errado**: o problema não é o modelo escolher a tool certa (seleção/2.1), é a **classificação do erro** depois que a chamada já falhou (2.2).
- **D — errada:** declarar o comportamento "esperado e seguro" ignora um desperdício mensurável e observável (três retries idênticos e fúteis) — **(não mapeia a um arquétipo §4 — erro mecanístico específico)**: é simplesmente negar um sintoma quantificado em vez de investigá-lo.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Difícil
- Rubrica: 8 = Bloom 3 + integração 2 + cenário 1 + distratores 2
- Cenário: S4 — Developer Productivity
- Princípio testado: validation→não repetir o mesmo input; a decisão de retry vem da categoria do erro, não da esperança de que repetir ajude

## Q4 — Resposta correta: **C** · (2.2)

Uma consulta que **encontra zero resultados** é uma execução **bem-sucedida** de uma pergunta válida — não é falha de acesso. `search_order_history` deveria devolver `isError: false` (ou omitir o campo) com `orders: []`, permitindo ao agente comunicar corretamente "nenhum pedido encontrado" em vez de acionar retries e uma mensagem de "erro de sistema" falsa.

- **A — errada:** aumentar o limite de retries para "eventualmente encontrar" pedidos que **não existem** é **equívoco de capacidade** — mais tentativas não criam dados que não existem; o problema não é volume de tentativas, é classificar resultado vazio como erro.
- **B — errada:** tratar ausência de pedidos como falta de permissão de acesso é **camada/alvo errado** — atribui a um controle de acesso (que nunca falhou) um sintoma que é, na verdade, resultado vazio válido de uma consulta bem-sucedida.
- **C — correta.**
- **D — errada:** escalar por **confiança auto-reportada** do agente é um **proxy plausível não confiável** — não há relação entre a confiança que o modelo reporta sobre si mesmo e se um resultado vazio é ou não um erro real.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Difícil
- Rubrica: 7 = Bloom 3 + integração 1 + cenário 1 + distratores 2
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: resultado vazio válido (0 matches) não é erro — `isError: false`

## Q5 — Resposta correta: **D** · (2.2)

O padrão de propagação correto: preservar os **resultados parciais** que deram certo e anexar uma **nota estruturada** (`attempted`) do que foi tentado contra a fonte que falhou e por quê. Isso dá ao coordenador informação suficiente para decidir — re-tentar, seguir com cobertura parcial documentada, ou sinalizar a lacuna — sem perder trabalho válido nem fingir que o relatório está completo.

- **A — errada:** descartar os três sucessos e devolver só uma falha genérica por causa de **uma** fonte isolada é **camada/alvo errado** — pune (descarta) agentes/fontes que funcionaram corretamente por causa de uma falha não relacionada em outro componente.
- **B — errada:** exigir concordância entre múltiplas passagens independentes — inclusive re-rodando as três fontes que já tinham sucesso na primeira passagem — é **voto/consenso que suprime sinal**: descarta resultados de primeira passagem válidos só por não repetirem, jogando fora sinal útil que já existia.
- **C — errada:** preencher a quarta fonte com dados de um relatório anterior parecido, sem sinalizar que é um substituto, é **(não mapeia a um arquétipo §4 — erro mecanístico específico: fabricação silenciosa de dado substituto sem proveniência)** — o §4.4 ("proxy plausível não confiável") descreve sinais de escalação frágeis (sentimento, confiança auto-reportada), não a fabricação de dados; aqui o problema é apresentar dado inventado como se fosse real, sem qualquer marcação de origem.
- **D — correta.**

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 10 = Bloom 4 + integração 2 + cenário 2 + distratores 2
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: recuperação local + propagação — reportar sucesso parcial com `attempted` em vez de tudo-ou-nada

## Q6 — Resposta correta: **A** · (2.2)

**Quebra-automatismo:** parece que "adicionar uma camada" é sempre over-engineering, mas aqui o vocabulário de erro da gateway é **fixo e conhecido** (não é um problema aberto) — um mapeamento **determinístico** (tabela de lookup) de cada string fixa para `errorCategory`/`isRetryable` é exatamente proporcional ao problema: a API upstream não pode mudar, e o conjunto de strings é finito, então cobrir esse conjunto com uma tradução determinística resolve a causa raiz sem inventar inferência probabilística nem manutenção de modelo.

- **A — correta.**
- **B — errada:** deixar as strings cruas e adicionar uma regra de texto no system prompt é **probabilístico onde precisa ser determinístico** — usa o julgamento textual do modelo para algo que é, na verdade, um mapeamento fixo e enumerável (conjunto finito e conhecido de strings).
- **C — errada:** treinar um classificador de texto para um vocabulário **finito e conhecido** é **over-engineering** — investe complexidade de ML e manutenção de dataset onde uma tabela de lookup determinística já cobre 100% dos casos possíveis.
- **D — errada:** escalar por **confiança auto-reportada** sobre a satisfação do cliente ignora completamente a taxonomia de erro (`errorCategory`/`isRetryable`) — **proxy plausível não confiável**, desconectado do sinal real que a gateway já fornece.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 9 = Bloom 4 + integração 2 + cenário 1 + distratores 2
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: mapear a causa raiz na camada certa (adapter determinístico na fronteira) em vez de over-engineering (ML) ou probabilismo (prompt) quando o problema já é finito e conhecido
