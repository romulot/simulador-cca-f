## Q1
In 34% of a two-week trace review of the Customer Support Resolution Agent (Scenario 1), the agent calls `lookup_account` when the customer's message actually requires `get_account_snapshot`, and vice versa, forcing a human agent to correct the tool call before continuing. Both tools are exposed to the same subagent, sit in the same `tools` array, and have never been restricted at the `tool_choice` level. `lookup_account`'s description reads "Get account information." and `get_account_snapshot`'s reads "Retrieve account details." Both share an identical `input_schema` (`{account_id: string}`). What is the most likely root cause of this misrouting?

- **A)** The two tool `description` strings are minimal and near-synonymous ("Get account information." vs. "Retrieve account details."), giving the model no reliable differentiator between them at selection time.
- **B)** `tool_choice` defaults to `"auto"`, which Anthropic's documentation describes as choosing between eligible tools at random whenever more than one could plausibly apply.
- **C)** Both tools' `input_schema` types the `account_id` field as `string` instead of a more specific type, which prevents the model from distinguishing between the two calls.
- **D)** The Python-level function dispatcher that executes the tool call inspects the handler's function name internally, and because `lookup_account` and `get_account_snapshot` are declared in the same module, the dispatcher confuses the two at the code level.

## Q2
Across the Multi-Agent Research System (Scenario 3), a single `analyze_document` tool is currently used for three distinct jobs inside the synthesis subagent: pulling specific field values out of a source, producing a prose summary of it, and checking whether a claim is supported by it. A review of 40 recent runs shows inconsistent results — sometimes a summary comes back when a specific date was requested, and sometimes a claim-check returns a full summary instead. The tool's `description` is accurate but written to cover all three jobs at once. What is the recommended design change?

- **A)** Keep a single tool, but expand its `description` into an exhaustive multi-page write-up enumerating every possible caller intent and expected output format.
- **B)** Force `tool_choice` to `{"type": "any"}` so the model is always required to call the tool on every turn, regardless of which of the three jobs is intended.
- **C)** Split `analyze_document` into three purpose-specific tools (e.g., `extract_data_points`, `summarize_content`, `verify_claim_against_source`), each with its own narrow input/output contract and description.
- **D)** Leave the tool as-is, and add keyword-matching rules to the system prompt (e.g., "if the request mentions a date, treat it as a field-extraction job") to route internally to the right behavior.

## Q3
In the Developer Productivity agent (Scenario 4), two internal tools originally named `analyze_content()` and `analyze_document()` in the Python codebase had near-duplicate descriptions ("Analyze content." / "Analyze a document.") and were misrouted in roughly 28% of code-review triage calls. A developer "fixes" this by renaming the Python functions to `extract_web_snippet()` and `analyze_source_doc()`, without touching either tool's `description` field. After deployment, misrouting continues at essentially the same ~28% rate. What most likely explains why the fix had no effect?

- **A)** Renaming a Python function requires restarting the MCP server process for the new binding to take effect, and the team deployed without a restart.
- **B)** The model selects a tool based on the `name`, `description`, and `input_schema` fields sent to the API on each turn — the underlying Python function name is an implementation detail the model never sees, so renaming it without updating the description changes nothing about how the tool is selected.
- **C)** The internal tool registry resolves every call by looking up the Python function name in a name-to-handler table that was built once at deploy time, so as long as that registry entry stays unchanged internally, the old routing behavior is guaranteed to persist no matter what the tool's public `description` field now says.
- **D)** Claude's tool selector weighs shorter, punchier function names more heavily when two descriptions are similar, so the newly shortened names actually made the ambiguity worse rather than better.

## Q4
In the Customer Support Resolution Agent (Scenario 1), `extract_data_points` (pulls specific field values) and `summarize_content` (produces prose summaries) each have clear, well-differentiated descriptions and route correctly in 96% of calls during a two-week baseline. A teammate then adds one line to the system prompt: "Whenever the customer's message contains the word report, always call summarize_content." Afterward, requests like "From this report, get the closing date and revenue" are misrouted to `summarize_content` in most cases, and overall correct routing drops to about 61%. What is the most effective fix?

- **A)** The drop shows the two tools' descriptions were never actually well differentiated in the first place; rewrite both `description` fields from scratch.
- **B)** Force `tool_choice` to `{"type": "tool", "name": "extract_data_points"}` whenever the input contains a number, on the theory that pinning the tool choice guarantees the correct tool is used for every data-extraction-shaped request going forward, no matter what the system prompt says.
- **C)** Treat the drop to 61% as expected variance in LLM tool selection and leave the system unchanged, since both tools still work correctly in most calls.
- **D)** Remove or narrow the keyword-sensitive system-prompt rule (e.g., scope it to requests with no other extraction signal) — the rule is overriding otherwise well-designed tool descriptions and creating an unintended keyword association between "report" and `summarize_content`.

## Q5
The Multi-Agent Research System (Scenario 3) team is about to ship a new `extract_data_points` tool alongside the already-shipped, well-described `summarize_content` and `verify_claim_against_source` tools. Before merging, they draft four candidate `description` strings for `extract_data_points` and want to catch differentiation problems before they cause misrouting in production, the way the earlier `analyze_content`/`analyze_document` overlap did. Which candidate description is strongest, judged against the purpose → when-to-use-vs-alternatives → input → example → output → boundary template?

- **A)** "Extracts specific field values (e.g., dates, amounts, entity names) from a document when the caller needs discrete data points rather than prose. Input: document text plus a list of target fields. Example: fields=['closing_date','revenue'] returns {'closing_date': '2026-03-01', 'revenue': '4.2M'}. Output: a JSON object mapping field name to value. Does not produce narrative summaries (use `summarize_content`) or verify claims against a source (use `verify_claim_against_source`)."
- **B)** "Extracts fields, produces summaries, and can also assist with claim verification when the other two tools are unavailable, return an error, or simply seem slower than expected, making it a single reliable general-purpose fallback that the caller can reach for whenever they are unsure which of the three document jobs actually applies."
- **C)** "Uses a state-of-the-art structured-parsing pipeline to deliver high-quality, production-grade results for any document-related data need."
- **D)** "Extracts specific field values from a document; if results seem incomplete, request a larger context window so more of the source document is visible to the model in a single call."

## Q6
The Developer Productivity agent (Scenario 4) has grown to 11 tools as codebase-navigation features expanded. Two of them, `find_references` ("Find references to a symbol.") and `find_usages` ("Find usages of a symbol."), sit in the same subagent's `tools` array and are functionally identical — both locate call sites for a given symbol. A trace review of 50 recent calls shows the model splitting almost 50/50 between the two regardless of phrasing, and a team lead proposes training a small classifier to pre-select the right tool before the agent even sees the request. What is the most effective, lowest-effort fix?

- **A)** Build the proposed classifier to pre-select between the two tools before the model call, training it on the request's phrasing plus a growing set of hand-labeled examples that the team would need to keep maintaining as new call-site patterns show up over time.
- **B)** Force `tool_choice` to `{"type": "tool", "name": "find_references"}` on every call so `find_usages` is never selected again.
- **C)** Recognize that `find_references` and `find_usages` describe the same operation; consolidate them into a single tool (or clearly differentiate the two if they truly serve different jobs) and rewrite the description so it is unambiguous — no classifier or routing layer is needed because the two tools already sit in the same scope.
- **D)** Split each tool further into per-language variants (e.g., `find_references_python`, `find_references_js`, `find_references_go`, `find_references_rust`, `find_references_java`) so the model always has a more specific, language-scoped signal to pick from instead of the two broad, overlapping tools it currently has to choose between on every single call.
