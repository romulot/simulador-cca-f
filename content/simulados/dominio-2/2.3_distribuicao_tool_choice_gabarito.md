Explicações em PT-BR. Todas as questões exercitam o **TS 2.3**.

## Q1 — Resposta correta: **B** · (2.3)

Escopar o subagente às ~4-5 tools do seu papel (mais uma ou duas cross-role de
alta frequência, se realmente necessárias) é a correção **arquitetural**: menos
opções por turno reduz a complexidade de decisão e explica por que subagentes
já escopados erram só 3% das vezes contra 22% do subagente com as 18 tools.

- **A — errada:** `tool_choice: "any"` só obriga a chamar *alguma* das 18
  tools — não reduz o conjunto nem melhora a escolha certa. (Equívoco de
  capacidade.)
- **B — correta.**
- **C — errada:** treinar um classificador para pré-selecionar candidatas é
  resolver com uma camada de ML o que um ajuste de escopo de tools já resolve.
  (Over-engineering.)
- **D — errada:** a ordem de listagem das tools no prompt não é o mecanismo de
  seleção do modelo — não há base para essa crença. (Não mapeia a um
  arquétipo §4 — erro mecanístico específico.)

## Q2 — Resposta correta: **A** · (2.3)

O uso legítimo do forçado é **sequenciar**: forçar `tool_choice` para
`run_linter` só no primeiro turno garante a abertura do pipeline; devolver a
`"auto"` nos turnos seguintes preserva a flexibilidade de seleção que o time
também exige. Isso é o próprio "quebra-automatismo" do tópico — forçar É a
resposta certa aqui, desde que aplicado só ao passo que precisa de garantia.

- **A — correta.**
- **B — errada:** forçar a mesma tool em todo turno trava o pipeline — o
  modelo nunca mais poderia escolher `run_tests` ou `post_review_comment`.
  (Não mapeia a um arquétipo §4 — erro mecanístico específico: força
  perpétua, não sequenciamento.)
- **C — errada:** `"any"` garante que *alguma* tool seja chamada em todo
  turno, mas não garante que seja `run_linter` especificamente nem que seja a
  primeira. (Equívoco de capacidade.)
- **D — errada:** depender só de instrução no system prompt é probabilístico
  onde o requisito ("sempre a primeira chamada") exige garantia
  determinística. (Probabilístico onde precisa ser determinístico.)

## Q3 — Resposta correta: **B** · (2.3)

`"any"` garante uma **chamada de tool** em vez de texto puro — por isso o
agente parou de responder em texto — mas não decide **qual** tool entre duas
com descrições parecidas; quem diferencia é a descrição (2.1). A taxa de 14%
de cross-selection continuar idêntica após a mudança é a evidência direta
disso: o time tratou o sintoma errado.

- **A — errada:** não existe uma avaliação "mais criteriosa" de descrições em
  `"any"` — essa distinção de comportamento entre `"auto"` e `"any"` não existe
  na API. (Feature inexistente porém verossímil.)
- **B — correta.**
- **C — errada:** treinar um classificador extra para desambiguar duas tools
  é resolver com ML um problema que se resolve reescrevendo as descrições.
  (Over-engineering.)
- **D — errada:** forçar `tool_choice` para uma das duas tools em todo turno
  ataca a camada errada (o mecanismo de seleção) quando o problema real está
  na camada de descrição das tools (2.1) — mascara o sintoma sem escalar para
  novas queries. (Camada/alvo errado.)

**Tópicos:** Tool Choice

- Rubrica: 7 = Bloom 3 + integração 1 + cenário 1 + distratores 2
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: descrições de ferramenta como seletor primário

## Q4 — Resposta correta: **A** · (2.3)

A causa raiz é o agente de síntese carregar tools fora do seu papel
(`web_search`, `scrape_website`) herdadas de um template compartilhado. A
correção é **remover** essas tools do conjunto do agente — escopo por
construção, não por instrução — deixando só as relevantes para síntese mais
uma cross-role pontual se necessário.

- **A — correta.**
- **B — errada:** trocar `tool_choice` para `"any"` não restringe *quais*
  tools estão disponíveis — só obriga a chamar alguma das que já existem no
  conjunto, incluindo as fora do papel. (Equívoco de capacidade.)
- **C — errada:** reforçar a instrução no system prompt mantendo as tools
  disponíveis ainda deixa a porta aberta a mau uso — é probabilístico onde o
  requisito pede garantia por escopo. (Probabilístico onde precisa ser
  determinístico.)
- **D — errada:** fundir os dois subagentes elimina a especialização e ataca
  a camada errada (a fronteira entre agentes) em vez de corrigir o escopo de
  tools do agente de síntese. (Camada/alvo errado.)

## Q5 — Resposta correta: **C** · (2.3)

A garantia de ordem completa combina dois mecanismos do 2.3: forçar
`tool_choice` para `run_tests` e depois `run_linter` nos dois primeiros
turnos (sequenciamento determinístico) **e** manter `deploy_preview` fora do
conjunto de tools disponíveis até que ambos tenham sucedido (escopo dinâmico
de tools por estágio) — só então o pipeline volta a `"auto"`. Isso guarda a
ordem sem travar a flexibilidade do restante do pipeline.

- **A — errada:** forçar `deploy_preview` em todo turno pode levá-lo a ser
  chamado antes mesmo de `run_tests`/`run_linter` rodarem — o oposto da
  garantia pedida, além de travar o restante do pipeline. (Não mapeia a um
  arquétipo §4 — erro mecanístico específico.)
- **B — errada:** `"any"` garante só que alguma tool seja chamada a cada
  turno; não impõe nenhuma ordem de dependência entre elas. (Equívoco de
  capacidade.)
- **C — correta.**
- **D — errada:** confiar só na instrução do system prompt com `"auto"` e as
  três tools sempre disponíveis é probabilístico onde o requisito ("nunca
  antes de ambos sucederem") exige garantia determinística. (Probabilístico
  onde precisa ser determinístico.)

## Q6 — Resposta correta: **D** · (2.3)

A estratégia mais defensável é escopar o agente às tools de resolução de
faturamento que ele de fato usa, somando uma ou duas cross-role de alta
frequência (ex.: `lookup_customer`) — nem o bundle de 11 tools completo, nem
um corte tão agressivo que quebre a flexibilidade legítima do papel.

- **A — errada:** reduzir a uma única tool e forçá-la para a sessão inteira
  elimina a flexibilidade que o papel de faturamento ainda precisa (há mais
  de uma ação de billing legítima). (Não mapeia a um arquétipo §4 — erro
  mecanístico específico: rigidez excessiva, não escopo proporcional.)
- **B — errada:** manter as 11 tools e adicionar um hook para bloquear
  `delete_account`/`hr_lookup` ataca a camada errada — o problema é o agente
  ter a tool disponível, não a execução dela; a correção de 2.3 é não
  conceder a tool, não um gate de runtime por cima. (Camada/alvo errado.)
- **C — errada:** treinar um classificador para decidir, por request, qual
- **D — correta.**
  bundle expor é resolver com ML um problema que um escopo estático de tools
  já resolve. (Over-engineering.)
