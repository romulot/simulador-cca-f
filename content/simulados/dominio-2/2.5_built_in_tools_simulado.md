## Q1
In a 40,000-file monorepo powering a developer-productivity coding assistant, an agent answers "where is `charge_customer` called?" by running `grep -rn charge_customer .` through the Bash tool. On a large branch the scan takes over 90 seconds, and a deny-rule meant to block reads under `secrets/` does not stop it, because the search runs through the shell instead of through the permission-checked tools. Which change most reliably fixes both problems?

- **A)** Keep the `grep -rn` Bash command, but append `--exclude-dir=secrets` by hand to every future invocation so the sensitive directory is skipped.
- **B)** Stand up a background indexing service that continuously pre-scans the entire repository into a dedicated search database, so that every future query is served from the index instead of walking the filesystem live.
- **C)** Use the Grep tool: it runs ripgrep under the hood, returns structured matches, and the deny-rules configured for Read/Grep/Glob apply deterministically to whatever it searches.
- **D)** Use the Glob tool with the pattern `**/*charge_customer*` to locate every file where the function is called.

## Q2
In a multi-agent research system, a synthesis subagent writes its running notes to a shared `findings.md` file for the coordinator to consume. Across recent runs about 15% of calls fail with the error "file has not been read yet" when the subagent invokes Edit to append a newly discovered source, even though its system prompt already tells it to keep the file updated. What is the correct fix?

- **A)** Have the subagent Read `findings.md` earlier in the same turn before calling Edit — Edit enforces this as a hard precondition, and no amount of prompt wording can substitute for actually reading the file first.
- **B)** Make the instruction to update the file more emphatic in the system prompt, and trust that the model will remember to read the file before editing it on every single run going forward.
- **C)** Replace the Edit calls with Write calls that supply the entire file's contents each time instead, on the assumption that Write has no read-before-write requirement to satisfy when the target file already exists on disk.
- **D)** Wrap every Edit call in a retry loop that reissues the exact same call up to three times, on the assumption that the precondition will eventually be satisfied.

## Q3
A customer-support resolution agent keeps every canned response in one 1,500-line `macros.yaml` file. Asked to update only the refund-policy entry, the agent calls Write with a fully regenerated file; support engineers have noticed that on some of these runs, unrelated macros for shipping and returns silently disappear from the saved file. What is the best way to prevent this going forward?

- **A)** Keep using Write, but have the agent Read the file first and diff the regenerated output against the original before saving, so any dropped macros are caught after the fact.
- **B)** Split `macros.yaml` into many smaller per-macro files, so each Write call only has to reproduce a small fraction of the content at a time.
- **C)** Add an instruction telling the model to be extremely careful and to always reproduce the file's full contents exactly whenever it regenerates it.
- **D)** Use Edit with an exact, unique `old_string` scoped to just the refund-policy entry, changing only that text and leaving the other roughly 1,499 lines untouched.

## Q4
While renaming a variable inside a 300-line Python module, a coding agent calls Edit with `old_string: "count"`, and the tool immediately fails with "old_string appears 7 times and is not unique." What is the correct way for the agent to proceed?

- **A)** Re-issue the identical Edit call seven times in a row, since Edit silently advances to the next matching occurrence on each successive call.
- **B)** Provide a longer `old_string` with enough surrounding context to pin down the one intended occurrence, or pass `replace_all: true` if every occurrence should actually change.
- **C)** Edit performs approximate matching under the hood, so progressively shorten `old_string` until it happens to resolve to exactly one match.
- **D)** Abandon Edit entirely for this rename and use Write to regenerate the entire 300-line module from scratch with the rename already applied consistently to every single occurrence throughout the file.

## Q5
A customer-support QA agent is meant only to read tickets and the macros knowledge base to answer questions like "why was this refund denied?" and must never modify anything; during a live demo it nonetheless edited a macro file after misreading an ambiguous instruction. The team now wants a guarantee, not just better wording, that this can never happen again. Which approach actually provides that guarantee?

- **A)** Restrict `allowed_tools` to `["Read", "Grep", "Glob"]` so Write, Edit, and Bash are unavailable, making any file modification impossible by construction.
- **B)** Add a firm rule to the system prompt stating that the agent is strictly read-only and must never, under any circumstances, edit or create files.
- **C)** Leave every tool enabled, but add a PostToolUse hook that detects and reverts any file the agent modifies after the fact.
- **D)** Leave Edit and Write enabled, and rely on the fact that a QA-style prompt referencing tickets and refund policy is unlikely to make the model attempt an edit in practice, especially given how the demo instructions were phrased this particular time.

## Q6
In a multi-agent research system, an analysis subagent finishes transforming a shared dataset and must run the project's `pytest` suite to confirm the transformation script still passes its regression tests before the coordinator accepts the result. A reviewer objects that "the agent should avoid Bash and use the built-in tools instead." Which response is correct?

- **A)** Use Grep to search the test files for `assert` statements and report the count as a proxy for whether the suite currently passes.
- **B)** Use Read to open each test file and reason carefully in natural language about whether it would pass, without ever actually executing anything, then report the expected pass/fail outcome to the coordinator as if it were an observed result.
- **C)** Use Bash to run `pytest` directly: executing a program is exactly Bash's job, and the "prefer dedicated tools" guidance targets read operations like `cat`/`grep`/`find`, not command execution.
- **D)** Build a custom MCP tool that wraps the test runner, so the subagent never has to invoke Bash directly for this step.
