## Q1 — Resposta correta: **C** · (2.5)

Busca de **conteúdo** é trabalho do **Grep** (ripgrep): saída estruturada, e as
deny-rules de permissão sobre Read/Grep/Glob aplicam de forma determinística —
diferente do `grep` via Bash, que é texto cru executado pelo shell e escapa
parte das regras de permissão.

- **A — errada:** continua no shell-out; a exclusão de `secrets/` vira uma flag
  manual, frágil e dependente de o operador lembrar de repeti-la em toda
  chamada futura — não é uma garantia de política (**camada/alvo errado**).
- **B — errada:** montar um serviço de indexação contínua para resolver o que
  o Grep (ripgrep) já resolve com bom desempenho é complexidade desnecessária
  (**over-engineering**).
- **C — correta.**
- **D — errada:** Glob casa **nomes/caminhos de arquivo** por padrão glob, não
  **conteúdo**; não encontra call sites de uma função dentro do corpo dos
  arquivos (**equívoco de capacidade**).

## Q2 — Resposta correta: **A** · (2.5)

Read-before-edit é uma **pré-condição determinística** do Edit: o arquivo
precisa ter sido lido na sessão antes da chamada. A correção é ler antes de
editar — nenhuma redação de prompt substitui essa checagem mecânica da tool.

- **A — correta.**
- **B — errada:** reforçar a instrução por texto é enforcement
  **probabilístico onde precisa ser determinístico** — o modelo pode
  esquecer, e a falha continua intermitente por construção.
- **C — errada:** Write também exige que o arquivo tenha sido lido antes
  quando ele já existe em disco; trocar de tool não elimina a pré-condição,
  é um **equívoco de capacidade** sobre o que Write realmente exige.
- **D — errada:** repetir a mesma chamada de Edit não satisfaz a
  pré-condição (nada mudou entre as tentativas); é **over-engineering** que
  não ataca a causa raiz.

## Q3 — Resposta correta: **D** · (2.5)

Mudança de poucas linhas em arquivo grande = **Edit** com `old_string` exato
e único: altera só o alvo e deixa o resto do arquivo intacto. Write regenera
o arquivo inteiro, gastando tokens e arriscando derrubar conteúdo não
relacionado — exatamente o bug relatado pelos engenheiros de suporte.

- **A — errada:** ler e diffar a cada Write é uma verificação **posterior**
  ao dano em vez de escolher a tool que previne o problema na origem — ataca
  o sintoma na camada errada do pipeline (**camada/alvo errado**).
- **B — errada:** fragmentar `macros.yaml` em vários arquivos para reduzir o
  que cada Write reproduz é reestruturar o modelo de dados para contornar uma
  escolha de tool — complexidade desnecessária (**over-engineering**).
- **C — errada:** pedir "cuidado" no prompt é enforcement
- **D — correta.**
  **probabilístico onde precisa ser determinístico** — não garante que nada
  será perdido na regeneração.

## Q4 — Resposta correta: **B** · (2.5)

`old_string` precisa ser **único** no arquivo. Com 7 ocorrências, ou se dá
mais contexto para fixar exatamente **uma**, ou se usa `replace_all: true`
para trocar todas de propósito — é casamento **exato**, sem fuzzy/regex.

- **A — errada:** Edit **não** avança silenciosamente para a próxima
  ocorrência — ele **falha** da mesma forma em toda chamada idêntica, porque
  nada no input mudou (**equívoco de capacidade**).
- **B — correta.**
- **C — errada:** não existe matching aproximado; encurtar a string só
  aumenta a chance de novas colisões, nunca "resolve" para uma única
  ocorrência por sorte (**equívoco de capacidade**).
- **D — errada:** trocar para Write e regenerar o arquivo inteiro é
  exatamente o que `replace_all: true` já resolve, sem o risco de derrubar
  código não relacionado — mais máquina do que o requisito pede
  (**over-engineering**).

## Q5 — Resposta correta: **A** · (2.5)

Restringir `allowed_tools` a Read/Grep/Glob torna a escrita **impossível por
construção** — é a garantia determinística de configuração. Sem Write, Edit
ou Bash disponíveis, não há como o agente modificar um arquivo.

- **A — correta.**
- **B — errada:** uma instrução "read-only" no prompt é exatamente o que já
  falhou no demo — enforcement **probabilístico onde precisa ser
  determinístico**.
- **C — errada:** reverter depois via PostToolUse é reativo: a escrita chega
  a acontecer e chega a tocar o disco antes da reversão, além de ter mais
  peças móveis do que simplesmente não conceder a tool (**camada/alvo
  errado**).
- **D — errada:** confiar que "esse tipo de prompt raramente edita" é apostar
  numa frequência observada como garantia — **proxy plausível não
  confiável**.

## Q6 — Resposta correta: **C** · (2.5)

Rodar `pytest` é **execução de comando** — o trabalho do **Bash**. A guidance
"prefira tools dedicadas" mira operações de **leitura** (`cat`/`grep`/`find`),
não a execução de programas. (Quebra-automatismo: "evite Bash" não é
absoluto — aqui Bash é exatamente a tool certa.)

- **A — errada:** contar `assert` nos arquivos de teste é um sinal que não
  diz se a suíte passa agora — **proxy plausível não confiável**.
- **B — errada:** ler e "raciocinar" sobre os testes sem executar nada não
  produz um resultado de runtime real; não há substituto para efetivamente
  rodar a suíte (não mapeia a um arquétipo §4 — erro mecanístico específico:
  reportar um resultado não observado como se fosse observado).
- **C — correta.**
- **D — errada:** empacotar o test runner numa MCP tool customizada só para
  evitar chamar Bash diretamente é complexidade desnecessária para algo que o
  Bash já faz de forma direta (**over-engineering**).
