## Q1 — Resposta correta: **A** · (2.1)

A `description` (reforçada pelo `input_schema`) é o **sinal primário de seleção** que o modelo recebe — não há nada mais para diferenciar aqui, já que ambos os schemas são idênticos. Descrições mínimas e quase sinônimas ("Get account information." vs. "Retrieve account details.") não dão nenhum critério de escolha, então o misrouting é esperado, não acidental.

- **A — correta.**
- **B — errada:** `"auto"` não é seleção aleatória; o modelo decide com base no par `(name, description, input_schema)`. Afirmar que é aleatório é um **equívoco de capacidade** sobre o mecanismo de `tool_choice`.
- **C — errada:** tipar `account_id` como `string` é normal e não é a causa da ambiguidade — **(não mapeia a um arquétipo §4 — erro mecanístico específico)**, apenas confunde tipo de campo com diferenciação semântica.
- **D — errada:** o modelo nunca vê o nome da função Python nem existe "dispatcher que confunde nomes" — atribuir a causa a esse componente é **camada/alvo errado** (culpa o código de execução quando o problema está no par `description`/`input_schema` enviado à API).

## Q2 — Resposta correta: **C** · (2.1)

Quando uma tool genérica cobre trabalhos distintos (extração de campos, resumo, verificação de claim), a correção recomendada é **dividir em tools de propósito único**, cada uma com contrato de input/output estreito. Isso é o que torna cada `description` fácil de escrever e de diferenciar — ataca a causa raiz em vez de compensá-la.

- **A — errada:** inflar a `description` num texto exaustivo é **over-engineering** — adiciona complexidade textual sem resolver o fato de a tool fazer três trabalhos incompatíveis.
- **B — errada:** `tool_choice: any` apenas obriga a chamar *alguma* tool a cada turno; não ajuda a escolher entre os três trabalhos, e obrigar uma chamada em todo turno é uma aplicação de **camada/alvo errado** (mecanismo de obrigatoriedade usado para tentar resolver um problema de diferenciação).
- **C — correta.**
- **D — errada:** mover a lógica de roteamento para regras de palavra-chave no system prompt é **over-engineering** — cria uma camada de roteamento paralela em vez de corrigir o design da tool, e é exatamente o tipo de regra que pode depois sobrepor descrições boas (ver Q4).

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Entender
- Dificuldade: Fácil
- Rubrica: 3 = Bloom 1 + integração 1 + cenário 1 + distratores 0
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: descrições de ferramenta como seletor primário

## Q3 — Resposta correta: **B** · (2.1)

O modelo seleciona a tool a partir de `name`, `description` e `input_schema` — os únicos campos que a API expõe a ele. O nome da função Python é um detalhe de implementação invisível ao modelo; renomear a função sem tocar na `description` não muda nenhum sinal que o modelo recebe, então o misrouting persiste sem surpresa.

- **A — errada:** não existe requisito de reiniciar o servidor MCP para uma função renomeada "valer" — é uma **feature inexistente porém verossímil**, no estilo de uma exigência operacional plausível mas fabricada.
- **B — correta.**
- **C — errada:** não existe "registro interno por nome de função" que decida o roteamento à parte da `description` — atribuir a causa a esse componente fictício é **camada/alvo errado** (aponta para uma camada de execução que não é onde a seleção realmente acontece).
- **D — errada:** o seletor do modelo não pondera "nomes mais curtos" como sinal — essa é uma crença específica sobre como o mecanismo de seleção funciona que não corresponde à realidade, um **equívoco de capacidade**.

## Q4 — Resposta correta: **D** · (2.1)

Uma regra **sensível a palavra-chave** no system prompt pode **sobrepor descrições de tool bem escritas** e criar uma associação indevida ("report" → sempre `summarize_content`), mesmo quando as descrições originais já diferenciavam bem os dois tools (96% de acerto antes da mudança). A correção de menor esforço que ataca a causa raiz é remover ou restringir a regra do system prompt — não tocar nas tools, que já estavam corretas.

- **A — errada:** as descrições não pioraram — o baseline de 96% prova que já diferenciavam bem; culpar as descrições aqui é **camada/alvo errado** (o componente que mudou foi o system prompt, não as tools).
- **B — errada:** forçar `tool_choice` para uma tool específica sempre que houver um número é **over-engineering** — cria uma regra frágil e paralela em vez de remover a causa raiz (a linha do system prompt), e não generaliza para outros padrões de linguagem.
- **C — errada:** uma queda de 96% para 61% correlacionada exatamente com a mudança no system prompt não é "variância esperada" — **(não mapeia a um arquétipo §4 — erro mecanístico específico)**: é simplesmente ignorar um sinal de regressão observável e mensurado.
- **D — correta.**

A opção A segue o template completo do 2.1: **propósito** (extrai valores de campo específicos) → **quando usar vs. alternativas** (não para resumos, não para verificação de claim, com o nome exato das outras tools) → **input** → **exemplo concreto** → **output** → **fronteira explícita** (o que NÃO faz). É a única que reduz a ambiguidade contra `summarize_content` e `verify_claim_against_source` em vez de recriá-la.

## Q6 — Resposta correta: **C** · (2.1)

**Quebra-automatismo:** o reflexo de "construir um classificador" (A) parece a solução robusta, mas aqui é over-engineering — as duas tools fazem literalmente o mesmo trabalho. A correção de menor esforço e maior alavancagem é reconhecer a sobreposição e **consolidar/diferenciar + reescrever a descrição**, sem nenhuma camada de roteamento nova: os dois tools já estão no mesmo escopo do subagente, então o ajuste é puramente de design de descrição (2.1), não de arquitetura de distribuição (2.3).

- **A — errada:** treinar um classificador para pré-selecionar a tool é **over-engineering** — resolve com uma camada de ML algo que um ajuste de descrição/consolidação resolve com muito menos esforço.
- **B — errada:** forçar `tool_choice` para `find_references` em todo turno é **camada/alvo errado** — usa um mecanismo de sequenciamento de chamada (2.3) para tentar apagar permanentemente `find_usages`, quebrando a funcionalidade que essa tool deveria oferecer, em vez de corrigir a descrição.
- **C — correta.**
- **D — errada:** dividir ainda mais em variantes por linguagem é **over-engineering** — multiplica tools no eixo errado (linguagem) quando o problema real é que duas tools já descrevem a mesma operação.

**Metadados (revisão; não exibir ao candidato):**

- Dificuldade: Médio

- Cenário: S4 — Developer Productivity
