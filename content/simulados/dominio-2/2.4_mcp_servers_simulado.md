## Q1
In production, an engineer on the Customer Support Resolution Agent team (Scenario 1) starts personally trying out a third-party `ticket-summarizer` MCP server pulled from a public registry, testing it across 6 of the team's repositories before deciding whether it's worth recommending. It hasn't been reviewed or vetted against the team's ticket data, and the engineer doesn't want any teammate to pick it up by accident just by cloning one of those repos. Following the same habit that got the team's vetted `crm` and `linter-rules` servers shared with everyone, the engineer is about to add `ticket-summarizer` to each repository's committed `.mcp.json`. What is the correct way to configure this instead?

- **A)** Add a `ticket-summarizer` entry at **local scope** in each of the 6 repositories being tested, so it stays out of every committed `.mcp.json` while the engineer tries it out machine by machine, repo by repo.
- **B)** Add `ticket-summarizer` once to `~/.claude.json` (user scope): it becomes available to the engineer across every repository they open, without touching any repo's committed `.mcp.json`, so a teammate who clones one of those repos never sees the unvetted server.
- **C)** Add `ticket-summarizer` to each of the 6 repositories' committed `.mcp.json`, the same way `crm` and `linter-rules` were shared, and simply ask teammates over Slack not to use it until it's been reviewed.
- **D)** Add `ticket-summarizer` under a fourth **staging** scope in `.mcp.json` — reserved for servers not yet vetted for team-wide use — which Claude Code loads only when a developer opts in, without appearing for other team members by default.

## Q2
In production, the developer-productivity team's onboarding checklist (Scenario 4) requires each new engineer to manually paste a 12-line MCP server JSON block into their local config before their first commit, and 3 of the last 5 new hires missed this step, only discovering the missing `linter-rules` MCP server when their first pull request failed CI. The team wants every developer who clones the repository to automatically get the shared `linter-rules` server, while each developer's personal `scratch-notes` server, used only for their own draft docs, stays private to their machine. Where should each server be declared?

- **A)** Put both servers in `~/.claude.json`, so every developer starts from the exact same personal defaults.
- **B)** Put both servers in the project `.mcp.json`, since committing both together keeps the whole team's tooling consistent.
- **C)** Put `linter-rules` in the project `.mcp.json` (committed to git, so cloning the repository shares it automatically) and `scratch-notes` in each developer's own `~/.claude.json` (user scope, personal).
- **D)** Keep `linter-rules` as a manual paste in the onboarding doc, but shorten the JSON block from 12 lines to 6 to reduce copy-paste mistakes, and add `scratch-notes` to the same doc.

## Q3
In production, the multi-agent research pipeline's (Scenario 3) `search-index` MCP server entry in `.mcp.json` sets its base URL as `"${SEARCH_API_URL:-https://search.internal.example.com}/mcp"` and its auth header as `"Bearer ${SEARCH_API_KEY}"`. After a CI runner image was rebuilt last week, all 4 research subagents fail before a single turn executes, and the logs show a config-parsing error, not a connection-refused error. The team confirms that neither `SEARCH_API_URL` nor `SEARCH_API_KEY` was carried into the rebuilt image's environment. What is the most likely root cause?

- **A)** `SEARCH_API_URL` has no working default and is missing on the new image, so the whole config fails to parse before any subagent runs.
- **B)** Both variables silently resolve to empty strings when unset, so the server starts with a blank URL and a blank auth header and simply fails to connect.
- **C)** `${VAR:-default}` expressions are only evaluated the first time `.mcp.json` is read after a fresh clone; the rebuilt image had a stale cached read, so neither variable was re-evaluated this time.
- **D)** `SEARCH_API_KEY` is required with no default and its value is missing on the rebuilt image, so Claude Code fails to parse the config at load time rather than connecting with an empty credential.

## Q4
In production, a Customer Support Resolution Agent (Scenario 1) engineer reports that the `crm` MCP server is using the wrong timeout: the committed `.mcp.json` (project scope) sets a 30-second timeout, and the engineer's personal local-scope override, added last month to point at a staging replica, sets no timeout field at all. The engineer expected Claude Code to fall back to the project's 30-second value for that one missing field while keeping the rest of the local override in place. Instead, requests from that machine now hang well past 30 seconds. What is the most accurate diagnosis?

- **A)** Claude Code does not merge fields across scopes: the local-scope entry wins in its entirety, including its missing timeout field, so the client falls back to its own default.
- **B)** The project scope's timeout should take precedence over the local scope specifically for numeric fields, while string fields such as the URL still follow whatever the local override sets.
- **C)** The local override is being ignored entirely, because local scope only applies when adding a brand-new server, not when overriding a server that a lower-precedence scope like `.mcp.json` already defines.
- **D)** `.mcp.json` and the local-scope config are read in file-system alphabetical order, and whichever file's path sorts first for this particular server name wins the comparison field by field, not scope precedence.

## Q5

- **B)** Replace the literal credential in each of the 40 files with `"Bearer ${DOCS_SEARCH_TOKEN}"`, so future rotations only require updating the environment variable's value wherever it is set, not the 40 committed files.

## Q6
In production, a multi-agent research system (Scenario 3) gives its subagents two capabilities: (a) a live `fetch_latest_price` lookup against a market-data API — the price changes on every call, so the last 10 calls each returned a different value — built as a tool on an in-process MCP server via `create_sdk_mcp_server`; and (b) pulling the full text of one specific memo, by ID, out of a 200-memo research archive kept on the team's separately connected `research-docs` MCP server, only when a subagent decides that memo is relevant to the claim it is checking. The team is deciding which MCP primitive backs each capability, and how to scope `allowed_tools` for the live price lookup across subagents. Which design correctly matches each capability to its primitive?

- **A)** Register `fetch_latest_price` as a **tool** on the in-process `create_sdk_mcp_server`, scoped via `allowed_tools` to the subagents needing live pricing; reference the memo as a **resource** on `research-docs`, pulled in on demand via `@research-docs:protocol://memo-id`.
- **B)** Register both capabilities as tools on the in-process server, including the memo lookup, and let any subagent call the memo tool whenever it thinks the memo might possibly matter, instead of wiring a second server for 200 memos, since a tool call and an on-demand resource reference cost the pipeline about the same either way.
- **C)** Register both `fetch_latest_price` and the memo as **resources** on the in-process server built with `create_sdk_mcp_server`, since that primitive registers tools and resources side by side, letting subagents reference either one with `@server:protocol://...` instead of a tool call.
- **D)** Grant every subagent `allowed_tools` access to `fetch_latest_price` by default, and rely on each subagent's own system prompt to remind it to only call the tool when genuinely needed for the claim, trusting that prompt instructions are as reliable as a scoping mechanism here.
