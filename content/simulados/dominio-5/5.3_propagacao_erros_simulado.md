# Simulado — Task Statement 5.3: Implement error propagation strategies across multi-agent systems

> Domínio 5 · 6 questões · escolha a **única melhor** resposta.

## Q1
A multi-agent research system delegates six subtopics per brief. When a source times out, the research subagent's report reads `{"status": "error", "message": "search unavailable"}`. Across 120 briefs the coordinator answered that report by re-issuing the identical query three times and then dropping the subtopic; 14% of all subtopics were dropped this way. Instrumentation on the source shows that, on 60% of those failing calls, it had returned partial matches and named two alternative archives. Which change is most effective?

- **A)** Add a `PostToolUse` hook that inspects every failed search and decides, outside the model, whether the coordinator retries, rewrites the query, or moves on.
- **B)** Strengthen the coordinator's system prompt with instructions to vary the query and try a different source whenever a subagent reports an error.
- **C)** Have the subagent's report carry the failure category, the query `attempted`, any partial results, and the alternative sources the search offered.
- **D)** Raise the coordinator's retry budget for failed subtopics and add exponential backoff between attempts, so an unavailable source has time to recover.

## Q2
An extraction pipeline processed 1,900 invoices last month. The `discount_line` field is optional in the target schema, and 210 invoices genuinely carry none. For each of those, the lookup subagent returned `isError: true` with `errorCategory: "not_found"`, and the coordinator re-issued the same lookup until its step budget was exhausted; those 210 invoices finished with no row written at all. The remaining 1,690 invoices were written correctly. Which change is most effective?

- **A)** Report the lookup as successful with an empty result set, and record the verified absence of a discount line as a finding.
- **B)** Keep `isError: true` and have the coordinator annotate the invoice as a coverage gap instead of re-issuing the lookup.
- **C)** Keep the error but set `isRetryable: false` on `not_found`, so the coordinator stops after the first attempt and moves on.
- **D)** Make `discount_line` `required` in the extraction schema, so that every invoice yields a value for the field and the lookup never comes back with nothing.

## Q3
Across 40 research briefs, an average of 5 of 6 subtopics returned findings. In the 31 briefs where one subagent's source timed out, that subagent called its report tool with `{"status": "ok", "message": "no findings"}`, and the final synthesis listed the subtopic as "no evidence found" beside the five researched ones, with no distinction drawn. A spot check of 12 of those subtopics found published evidence sitting in the archive that had been down. What is the most likely root cause?

- **A)** The synthesis step has no instruction to annotate coverage per subtopic, so it presents all six subtopics with the same confidence.
- **B)** The subagent reported an access failure as a successful empty result, erasing the difference between verified absence and unverified.
- **C)** The decomposition is too coarse: with only six subtopics per brief, one lost source silently removes a sixth of the coverage.
- **D)** The coordinator has no retry budget for timed-out sources, so a single timeout costs the whole subtopic permanently.

## Q4
A customer-support resolution agent delegates billing lookups to a subagent. Last week 340 of 5,000 lookups came back with `isError: true`, `errorCategory: "permission"`, `isRetryable: false`, and the message "billing service temporarily unable to complete your request". The subagent retried each of those four times with backoff before reporting, adding a median 19 seconds per case and resolving none of them. Transient timeouts in the same period cleared on the second attempt. What is the most likely root cause?

- **A)** The backoff intervals are too short, so all four attempts land inside the same outage window at the billing provider.
- **B)** The subagent should have switched to the secondary billing source after the second failure instead of retrying the same one.
- **C)** `errorCategory: "permission"` is mislabelled by the billing API, since a permission can be granted while the case is still open.
- **D)** The subagent's local retry decides on the error message text, which reads as transient, rather than on the `isRetryable` field.

## Q5
All six subagents of a research system authenticate to the source archive with one shared credential, and on Tuesday it expired mid-run. Every subagent returned the same envelope: `errorCategory: "permission"`, `isRetryable: false`, `attempted` populated, no partial results, no alternatives. The coordinator re-delegated all six subtopics twice, with new queries and different archives, burned its whole delegation budget on each of the 22 runs that afternoon, and then synthesized reports in which every subtopic was annotated as a coverage gap. What is the best coordinator behaviour here?

- **A)** Re-delegate each subtopic once against an alternative archive, since changing source is the standard recovery for a non-retryable access failure.
- **B)** Stop the run and report the systemic failure: six identical non-retryable permission errors point to one shared cause no subtopic recovery reaches.
- **C)** Synthesize the report as it did, so that the requester still receives a coverage map saying which subtopics carry evidence and which ones do not.
- **D)** Add a `PreToolUse` hook that validates the shared credential before each delegation and blocks the run whenever that credential is invalid.

## Q6
A Claude Code review pipeline delegates each changed file to a subagent through the `Task` tool. Reports already carry the failure category, the command `attempted`, partial results, and alternatives. The coordinator's `allowedTools` grants it exactly two tools: `Task` and `submit_review`. Across 50 pull requests, 88 files failed lint with a non-retryable configuration error; the coordinator re-delegated each of them until its budget ran out, then submitted reviews that listed those 88 files among the clean ones. Which change is most effective?

- **A)** Give the coordinator a tool to record a file as unverified and one to record it as reviewed-clean, so an unresolved failure has a destination.
- **B)** Extend the report envelope with an attempt counter, an exhausted flag, and a suggested next action, giving the coordinator more context to reason over.
- **C)** Instruct the coordinator in its system prompt to stop re-delegating non-retryable failures and to mention each of them in the review text instead.
- **D)** Set `tool_choice` to `any` for the coordinator, so that every turn has to produce a tool call and the re-delegation loop terminates.
