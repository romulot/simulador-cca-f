## Q1 — Resposta correta: **B** · (1.3)

A ferramenta de spawn (`Task`/`Agent`, dependendo da versão do Claude Code) é o **único** mecanismo pelo qual um coordenador delega. Se `allowedTools` não a inclui, nenhum prompt bem escrito e nenhum `AgentDefinition` bem desenhado importam — o coordenador literalmente não tem como emitir a tool call de spawn. É o ponto-cego clássico do 1.3: a causa está na disponibilidade da ferramenta, não na qualidade do prompt.

- **A — errada:** **camada/alvo errado** — culpa a `description` dos subagentes (que afetaria *qual* subagente é escolhido, não *se* algum é chamado) quando o problema real está em `allowedTools` do coordenador.
- **B — correta.**
- **C — errada:** **equívoco de capacidade** — inverte a direção do isolamento de contexto: contexto isolado descreve o que o *subagente* recebe do pai, não algo que o coordenador "herda" dos subagentes; e isso não bloquearia o spawn.
- **D — errada:** **feature inexistente porém verossímil** — `share_context=True` não existe na API do `AgentDefinition`; soa plausível mas é inventado, e nunca é a resposta certa.

**Metadados (revisão; não exibir ao candidato):**

- Dificuldade: Médio
- Rubrica: 5 = Bloom 2 + integração 1 + cenário 1 + distratores 1
- Cenário: S4 — Developer Productivity
- Princípio testado: casar a ferramenta ao requisito (`Task` habilita a delegação; sem ela, delegação é impossível)

## Q2 — Resposta correta: **C** · (1.3)

Subagentes têm **contexto isolado**: o único canal pai→filho é a string de prompt escrita ao emitir o `Task`. Se os achados do pesquisador não estão explicitamente naquele texto, a síntese simplesmente não os tem — daí tratar o tema como inexplorado. É a skill central do 1.3: colocar os achados completos no prompt do subagente.

- **A — errada:** **equívoco de capacidade** — assume que subagentes acumulam turnos como um único agente contínuo; na prática cada spawn começa com contexto isolado, sem herança automática.
- **B — errada:** **feature inexistente porém verossímil** — não existe `share_context=True`; nenhuma flag "linka" transcritos entre subagentes.
- **C — correta.**
- **D — errada:** **camada/alvo errado** — `fork_session` bifurca uma sessão a partir de um ponto de baseline compartilhado (útil para explorar ramos, ver 1.7); não é o mecanismo de handoff entre dois subagentes distintos e não resolve a ausência dos achados no prompt.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Entender
- Dificuldade: Fácil
- Rubrica: 2 = Bloom 1 + integração 0 + cenário 0 + distratores 1
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: contexto isolado — o prompt é o único canal pai→filho

## Q3 — Resposta correta: **A** · (1.3)

Para paralelizar, o coordenador emite **múltiplas tool calls `Task` dentro de uma única resposta** — os subagentes rodam concorrentemente e o tempo total tende ao do lookup mais lento, não à soma dos três. O trace mostra exatamente o padrão sequencial (uma call, espera o resultado, próxima call no turno seguinte) que essa mudança elimina.

- **A — correta.**
- **B — errada:** **equívoco de capacidade** — "aumentar `max_tokens` acelera a subtarefa" confunde limite de saída com velocidade; o gargalo aqui é a orquestração sequencial, não a capacidade de cada subagente.
- **C — errada:** **camada/alvo errado** — `fork_session` não foi desenhado para compartilhar progresso parcial entre subagentes em execução; é bifurcação de sessão, não sincronização em tempo real.
- **D — errada:** **over-engineering** — consolidar em um subagente genérico com classificador interno de roteamento adiciona uma camada de decisão onde o ajuste simples (emitir as três `Task` calls juntas) já resolve, e ainda sacrifica a especialização de cada lookup.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Difícil
- Rubrica: 9 = Bloom 3 + integração 2 + cenário 2 + distratores 2
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: resposta proporcional / menor esforço — spawn paralelo ataca a causa raiz (orquestração sequencial) sem redesenho

## Q4 — Resposta correta: **D** · (1.3)

A causa raiz é a **perda de proveniência no handoff**: achados e fontes chegaram corretamente pareados do pesquisador, mas foram achatados em texto livre no prompt da síntese, onde a associação claim↔fonte se perde por proximidade textual ambígua. A correção é passar os achados num formato estruturado que mantenha cada claim explicitamente pareada com seus próprios metadados de fonte — preservando no handoff o que já existia na saída bruta.

- **A — errada:** **over-engineering** — dar `WebFetch` à síntese para "re-verificar" adiciona uma capacidade e um passo extra quando o problema é estrutural (como os dados chegam ao prompt), não uma falta de verificação.
- **B — errada:** **camada/alvo errado** — `fork_session` não é o mecanismo de handoff entre dois subagentes diferentes; forçar contexto idêntico não resolve como os achados foram formatados no prompt da síntese.
- **C — errada:** **voto/consenso que suprime sinal** — rodar três passes e manter só o que 2 de 3 concordam trata erro sistemático de formatação como se fosse ruído aleatório; não corrige a causa e descarta atribuições corretas que por acaso não repetiram.
- **D — correta.**

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Difícil
- Rubrica: 9 = Bloom 3 + integração 2 + cenário 2 + distratores 2
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: causa raiz > sintoma — handoff estruturado (conteúdo separado de metadados) preserva proveniência

## Q5 — Resposta correta: **B** · (1.3)

Este é um item de **quebra de automatismo**: o instinto padrão do 1.3 é "restrinja `tools`/não dê `Task` a um subagente" (ver Q1 do lab anterior e o princípio de least privilege). Mas o papel *declarado* aqui exige decomposição real — o lead test-writer precisa decidir e delegar a três sub-subagentes especializados. Negar-lhe `Task` o impediria de cumprir o próprio papel para o qual foi desenhado. Aqui, **casar a ferramenta ao requisito** significa conceder `Task`, porque a necessidade de spawn aninhado é genuína, não um vazamento de responsabilidade.

- **A — errada:** **equívoco de capacidade** — assume que "só mesclar" dispensa qualquer ferramenta, ignorando que o papel declarado inclui decidir e disparar a delegação para os três sub-subagentes; sem `Task`, ele não pode cumprir a própria descrição de papel.
- **B — correta.**
- **C — errada:** **over-engineering** — dar o conjunto de ferramentas default completo (incluindo `WebSearch`, `Bash`) "para se adaptar a qualquer necessidade futura" é escopo além do papel declarado; contradiz least privilege sem necessidade demonstrada.
- **D — errada:** **camada/alvo errado** — transferir a responsabilidade de spawn para o coordenador contradiz o desenho declarado (o lead é que decide e delega); resolve no nível errado da hierarquia o que já está corretamente atribuído ao lead.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 10 = Bloom 4 + integração 2 + cenário 2 + distratores 2
- Cenário: S4 — Developer Productivity
- Princípio testado: least privilege / ferramentas escopadas — escopar ao requisito real do papel, não a um reflexo de "nunca dar `Task` a subagentes"

## Q6 — Resposta correta: **C** · (1.3)

A skill do 1.3 aqui é **prompt por objetivo, não passo-a-passo**: substituir o script fixo por meta + critério de qualidade (cobrir as três tabelas, combinar pedidos agrupados, devolver algo legível) dá ao subagente margem para lidar com casos que a receita rígida não previu — exatamente o caso dos pedidos agrupados observado nos 18% de tickets.

- **A — errada:** **over-engineering** — empilhar mais passos e condicionais para cobrir cada caso antecipável aumenta a rigidez do script em vez de resolvê-la; sempre haverá um próximo caso não antecipado.
- **B — errada:** **camada/alvo errado** — mover o mesmo script rígido do prompt do `Task` para o system prompt do `AgentDefinition` não muda a natureza procedural da instrução; só troca o arquivo onde a rigidez mora.
- **C — correta.**
- **D — errada:** **proxy plausível não confiável** — confiança auto-reportada pelo próprio subagente não é um sinal confiável de correção (ele pode estar "confiante" numa resposta incompleta); e essa mudança não toca o problema real, que é como a instrução foi escrita.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Médio
- Rubrica: 6 = Bloom 4 + integração 0 + cenário 1 + distratores 1
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: prompt por objetivo (metas + critérios) > script procedural — adaptabilidade a casos não previstos

### Conceitos reforçados
- `Task`/`Agent` habilita a delegação; `allowedTools` do coordenador precisa incluí-la — sem isso, nenhum prompt ou `AgentDefinition` resolve.
- `AgentDefinition` = `description` (seleção) + prompt (papel) + `tools` (escopo) — escopar ao requisito real do papel, não a um reflexo fixo.
- Contexto isolado: o único canal pai→filho é a string de prompt; achados completos precisam estar explícitos nela.
- Handoff estruturado separa conteúdo (claim) de metadados (fonte) → preserva proveniência; achatar em texto livre perde a associação.
- Spawn paralelo = múltiplas tool calls `Task` numa única resposta do coordenador; uma call por turno é sequencial (soma das latências).
- Prompt por objetivo (metas + critérios de qualidade), não script procedural → adaptabilidade a casos não previstos.
- Nested delegation (subagente com `Task`) é válido quando o papel *declarado* exige decomposição real — não é automaticamente um antipadrão.
- `fork_session` bifurca uma sessão a partir de baseline compartilhado; não é handoff entre subagentes distintos nem sincronização de progresso em tempo real.
- Confiança auto-reportada e voto/consenso por maioria não são substitutos confiáveis para corrigir a causa raiz de um problema estrutural.
