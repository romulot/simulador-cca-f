## Q1
A platform engineering team runs one Claude Code session per feature branch, and last Tuesday the laptop running the `payments-refactor` investigation crashed mid-session. By the time the machine restarted, two newer sessions had already been opened for unrelated branches in the same project directory. The engineer needs to return to that exact interrupted investigation — not whichever session Claude Code would treat as most recent — and keep its accumulated context intact. What is the correct approach?

- **A)** Capture the session ID recorded for that investigation (e.g., from the earlier run's `ResultMessage.session_id` or `--resume` output) and pass that specific ID to `resume`.
- **B)** Use `continue` with the branch name as an argument — `continue` accepts a target identifier and will jump straight to the session for that branch.
- **C)** Sessions cannot be resumed once newer sessions have been opened in the same project directory; the engineer must start the investigation over from scratch.
- **D)** Fork the crashed session (`fork_session=True`) — forking always targets whichever session was most recently active, so it will land back on the crashed investigation automatically.

## Q2
A multi-agent research session has already ingested and synthesized 40 sources to answer a market-sizing question — that shared baseline took considerable time to build. The team now wants to test two different valuation methodologies on top of that same baseline, in parallel, without either line of work contaminating the other or altering the original session. What should they do?

- **A)** Run both methodologies one after another in the same session, so they inherit the exact same accumulated context throughout.
- **B)** Start two completely unrelated fresh sessions and re-ingest and re-synthesize all 40 sources from scratch in each one.
- **C)** Fork the analyzed session twice (`fork_session=True`), giving each valuation methodology its own independent branch with a new session ID, leaving the original untouched.
- **D)** Use `continue` twice in a row — each `continue` call is supposed to automatically spin up an isolated branch of the prior work.

## Q3
A customer support resolution agent's session read through the account's 12 policy documents and the full ticket history before drafting a resolution. ## Q4
A multi-agent research session ran 30 tool calls — web fetches and document parses — over two hours. A post-hoc audit finds that 24 of those 30 underlying sources have since been taken down or revised, so most of the session's tool results are now stale; only a handful of high-level conclusions still hold up. What is the most reliable way to proceed?

- **A)** Resume the old session anyway — the accumulated volume of context should outweigh the fact that most of the underlying data has since changed.
- **B)** Fork the stale session (`fork_session=True`) into a new branch, carrying the same 24 stale tool results forward into that branch.
- **C)** Resume the session and simply raise `max_turns` so the agent has enough room to work around all the outdated tool results.
- **D)** Start a fresh session and inject a structured summary of the conclusions that are still valid, discarding the stale tool results entirely.

## Q5
An engineer forks a completed codebase-analysis session (`fork_session=True`) to prototype a risky refactor without disturbing the original investigation. After the forked session runs several `Edit` calls, a teammate running a separate session in the same repository directory reports seeing those exact file changes already on disk. What best explains this, and what should the engineer have used instead if full isolation of the file changes was actually required?

- **A)** Forking branches the conversation only, not the filesystem — edits made in the fork are real writes, visible to any session in the same directory; for file isolation, use a git worktree instead.
- **B)** This is a bug: `fork_session=True` is supposed to sandbox the filesystem as well, so the underlying Claude Code SDK failed to isolate the edits from the rest of the repository.
- **C)** The fork must have accidentally reused the original session's ID, so both sessions ended up sharing the exact same file-edit history from that point onward.
- **D)** The teammate's session must have been separately resumed from the forked session's ID, which is why the edits appeared to be shared between them.

## Q6
In a customer support environment, an on-call automation script kicks off Claude Code from a deployment pipeline whose working directory differs from where the original ticket-triage session was started. Passing the correct session ID to `--resume` nonetheless returns a brand-new, empty session with no prior history, even though the ID itself is confirmed correct. What is the most likely cause?

- **A)** Session IDs expire a few minutes after the session ends and cannot be resumed past that window.
- **B)** Resuming is only possible from within the exact same `query()` call that originally created the session — it cannot cross into a separate script, process, or pipeline stage.
- **C)** The `resume` call ran from a different working directory (`cwd`) than the one that created the session, so the SDK looked in the wrong project path on disk.
- **D)** `fork_session` must always be set to `True` for `resume` to find and reattach to an existing session.
