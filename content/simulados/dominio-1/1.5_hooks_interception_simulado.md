## Q1
In 34 of the last 200 resolved support tickets, the agent misreported an order date or delivery window because it reasoned directly over raw tool results: `mcp__billing__get_order` returns Unix epoch integers, `mcp__shipping__track` returns ISO 8601 strings, and `mcp__crm__lookup_order` returns a proprietary six-digit date code. Engineering wants every timestamp the model sees to already be in one consistent format, with zero per-tool logic left in the system prompt and no risk that the model skips the conversion under load. Which design most reliably achieves this?

- **A)** Add a rule to the system prompt instructing the model to normalize every timestamp it encounters into ISO 8601 before reasoning about the ticket.
- **B)** Register a `PostToolUse` hook matched to all three tools that parses each raw result and returns `updatedToolOutput` as a list of content blocks with the timestamp already rewritten to ISO 8601.
- **C)** Register a `PreToolUse` hook matched to all three tools that rewrites the outgoing call arguments so each tool receives dates in ISO 8601 before it runs.
- **D)** Return `updatedToolOutput` as `{"content": [...]}` from a `PostToolUse` hook, since that dict wraps the corrected result the same way a tool-result message is wrapped elsewhere in the conversation transcript.

## Q2
In 3 of the deployments a developer-productivity agent triggered last quarter through its `mcp__release__deploy_to_prod` tool, the deploy shipped during an active change freeze because the agent treated an engineer's chat message ("approved, ship it") as sufficient authorization, even though policy requires freeze-window deploy calls to be blocked and rerouted to a change-exception ticket. Leadership now wants a guarantee that no freeze-window deploy call can ever execute, with the agent redirected to the exception process instead of failing silently or retrying blindly. Which implementation guarantees this?

- **A)** Add a system-prompt rule, repeated at the top of every turn and again right before any deploy-related tool call, stating that the agent must never call `deploy_to_prod` during a change freeze and must instead open an exception ticket right away.
- **B)** A `PostToolUse` hook on `deploy_to_prod` that logs freeze-window deploys for a weekly compliance review.
- **C)** A classifier that scores how convincing each deploy request's chat justification sounds, blocking calls whose approval message scores below a threshold.
- **D)** A `PreToolUse` hook on `deploy_to_prod` that returns `permissionDecision: "deny"` with a `permissionDecisionReason` pointing to the change-exception ticket process whenever the current time falls inside the freeze window.

## Q3
In a 50-run load test of a multi-agent research system, a `PreToolUse` hook with `matcher: "run_query"` — meant to cap each subagent at 5 calls to the shared `mcp__search__run_query` tool and block the 6th — never triggered once; every subagent made as many calls as it wanted, and no error or warning appeared anywhere in the logs. What should the engineer check first?

- **A)** Whether `PreToolUse` hooks are even supported for tools exposed through an MCP server, since some hook types only apply to built-in tools.
- **B)** Whether the session's `permission_mode` was set to `"ask"`, since hooks stay inert unless the session is already in interactive approval mode.
- **C)** Whether the matcher string matches the tool's full name — a short name like `run_query` is compared as an exact string, so it never matches `mcp__search__run_query` and the hook silently never fires.
- **D)** Whether the cap logic should instead live in a `PostToolUse` hook, since only hooks that run after the tool executes can enforce a per-subagent call budget.

## Q4
In 1 of 20 sampled support cases after a team switched a subagent to `bypassPermissions` to remove interactive-approval latency, the subagent called `process_refund` directly on a $1,200 request, even though `allowed_tools` had been configured to expose only `lookup_order` and `issue_credit_under_50` — a list the team assumed would keep the subagent from ever reaching `process_refund`. What is the most likely root cause, and what should replace the current control?

- **A)** `bypassPermissions` ignores tool-availability restrictions like `allowed_tools`; the team should instead deny the unwanted tool explicitly via `disallowed_tools` or reintroduce a permission mode that actually enforces the allow-list.
- **B)** `allowed_tools` only restricts built-in tools such as `Bash` or `Read`, never MCP tools like `process_refund`, so the list was never going to constrain this subagent.
- **C)** The subagent's system prompt did not repeat the tool restriction strongly enough; adding a stronger instruction reminding it to only use the two approved tools will close the gap.
- **D)** The orchestrator, not the subagent, must have called `process_refund` and merged the result into the subagent's context, since a correctly scoped subagent operating under a properly enforced allow-list could never have reached that tool on its own in the first place.

## Q5
Across a sample of 300 citations a multi-agent research system pulled into a final report, 41 were mis-cited because the 5 subagents' literature-search MCP tools return author/year metadata in 5 different shapes — some nest it under `metadata`, some flatten it, and one omits the year entirely, requiring a follow-up call. The team is deciding where to put the logic that unifies all 5 shapes into one citation schema before the lead agent synthesizes the report. Which approach is the best tradeoff?

- **A)** Duplicate the shape-specific parsing logic inside each of the 5 subagents' prompts, so each subagent is responsible for reconciling its own tool's format.
- **B)** A single `PostToolUse` hook matched to all 5 search tools that parses each tool's raw shape and returns `updatedToolOutput` with a unified citation schema, so every subagent's result is normalized once, deterministically, before any agent reasons over it.
- **C)** Leave citations in their raw per-tool shape and have the lead agent's final synthesis prompt include instructions to reconcile the 5 formats when assembling the report.
- **D)** Insert a dedicated citation-normalization subagent between each search subagent and the lead, which re-reads every citation and re-formats it through its own reasoning before forwarding it on, adding an extra reasoning hop for every single citation the system produces.

## Q6
Roughly 40 engineers read a developer-productivity agent's daily digest of lint warnings pulled from `mcp__lint__get_warnings`, a tool that blends output from three linters whose only inconsistency is cosmetic — one capitalizes severity as `WARNING`, another as `warning`, the third as `Warn`. No downstream system parses the field, and no one has complained about the casing. Before adding a normalization step to next week's roadmap, what is the most proportionate next step?

- **A)** Ship the digest as-is; a `PostToolUse` normalization hook is not worth building for a purely cosmetic, human-read field with no correctness requirement.
- **B)** Build a `PostToolUse` hook matched to `get_warnings` that rewrites the severity field into one consistent casing via `updatedToolOutput`, following the same deterministic-normalization pattern used for tool data that feeds business logic.
- **C)** Add a `PreToolUse` hook on `get_warnings` that rejects the call unless the linter's severity casing already matches a fixed enum.
- **D)** Route the three linters' output through a small classifier trained to first detect which linter produced each warning, then apply a distinct per-source casing and formatting rule before the digest is assembled and sent out.
