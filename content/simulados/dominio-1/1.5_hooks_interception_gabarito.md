## Q1 — Resposta correta: **B** · (1.5)

`PostToolUse` intercepta o **resultado** de cada tool depois que ela executa e, antes de o modelo processá-lo, pode reescrevê-lo via `updatedToolOutput` — uma **lista de blocos de conteúdo**, no mesmo formato do resultado original. Registrar esse hook nas três tools resolve a heterogeneidade de uma vez, deterministicamente, sem depender do modelo.

- **A — errada:** pedir a normalização no system prompt é **probabilístico onde precisa ser determinístico** — o modelo pode esquecer sob carga, que é exatamente o sintoma dos 34 casos.
- **B — correta.**
- **C — errada:** `PreToolUse` age sobre os **argumentos de entrada** da chamada, antes de a tool executar; ele não tem acesso ao resultado que ainda não existe — é **camada/alvo errado** para este problema.
- **D — errada:** `updatedToolOutput` não é um dict `{"content": [...]}` — essa forma imita o formato de mensagem de resultado de tool da API, mas não é a shape real esperada (que é a lista de blocos, no formato do próprio resultado). É uma **feature inexistente porém verossímil**.

## Q3 — Resposta correta: **C** · (1.5)

O matcher de hook é comparado como **string exata** (ou regex) contra o **nome completo** da tool. Uma tool MCP tem nome `mcp__server__tool`; um matcher com o nome curto (`run_query`) nunca casa com `mcp__search__run_query`, então o hook **nunca dispara** — sem erro, sem warning, falha completamente silenciosa. É o primeiro lugar a checar.

- **A — errada:** `PreToolUse` funciona normalmente com tools MCP; essa é uma crença errada sobre o que o hook é **capaz** de interceptar — **equívoco de capacidade**.
- **B — errada:** hooks não exigem `permission_mode: "ask"` para disparar; essa suposta pré-condição não existe — **feature inexistente porém verossímil**.
- **C — correta.**
- **D — errada:** trocar para `PostToolUse` não resolveria um cap de chamadas: ele roda **depois** da execução, quando já é tarde para bloquear a 6ª chamada — é **camada/alvo errado** (o tipo de hook certo para bloquear uma ação antes de executar já é o `PreToolUse`; o problema real é o matcher, não o tipo de evento).

### Conceitos reforçados
- `PostToolUse` normaliza/reescreve o **resultado** via `updatedToolOutput` — **lista de blocos**, no formato do resultado original, nunca um dict `{"content": [...]}`.
- `PreToolUse` é o gate de **política**: roda antes da execução e, com `deny` + `permissionDecisionReason`, bloqueia e **redireciona** (ex.: para escalação/exceção).
- Matcher de hook = **string exata (ou regex) contra o nome completo** da tool (`mcp__server__tool`); nome curto = hook morto, falha em silêncio.
- `bypassPermissions` ignora `allowed_tools`; para excluir uma tool específica, use `disallowed_tools`.
- Centralizar normalização heterogênea num único hook > duplicar por tool > delegar ao prompt.
- Nem toda normalização exige hook: quando não há garantia de correção/compliance em jogo (campo cosmético, sem consumidor automatizado), a resposta proporcional pode ser não construir nada — construir um hook nesse caso é over-engineering.
