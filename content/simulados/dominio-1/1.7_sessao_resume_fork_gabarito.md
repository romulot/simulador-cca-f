## Q1 — Resposta correta: **A** · (1.7)

A sessão desejada é uma **específica** (a que crashou), não a mais recente do diretório. O mecanismo certo é capturar o `session_id` daquela execução (registrado em `ResultMessage.session_id`, ou devolvido junto do `--resume` anterior) e passá-lo explicitamente a `resume` — isso retoma a sessão certa com o contexto acumulado intacto.

- **A — correta.**
- **B — errada:** afirma que `continue` aceita um identificador (o nome da branch) como alvo — **feature inexistente porém verossímil** (arquétipo §4.5): `continue` não recebe identificador nenhum; ele sempre retoma a sessão MAIS RECENTE do diretório, então "passar a branch" não teria efeito real.
- **C — errada:** afirma que sessões deixam de ser resumíveis depois que outras são abertas no mesmo diretório — não mapeia a um arquétipo §4 (erro mecanístico específico): cada sessão é gravada em disco por `session_id`, independente de quantas outras sessões existam depois; nada expira por causa disso.
- **D — errada:** propõe usar `fork_session=True` supondo que fork "sempre aponta para a sessão mais recentemente ativa" — **camada/alvo errado** (arquétipo §4.3): usa o mecanismo de ramificação (que cria um ID NOVO a partir de uma sessão) para o objetivo de apontar para uma sessão antiga específica — o mecanismo certo para isso é `resume` com o id certo, não fork.

## Q2 — Resposta correta: **C** · (1.7)

As duas metodologias de valuation compartilham o mesmo baseline (40 fontes já sintetizadas) mas precisam evoluir **sem interferência mútua** e sem alterar o original. Isso é exatamente o caso de uso de `fork_session=True`: cada chamada de fork cria um ramo independente (ID novo) a partir do baseline, e o original permanece intocado — perfeito para comparar abordagens divergentes que partem do mesmo ponto.

- **A — errada:** roda as duas metodologias na MESMA sessão, sequencialmente — **camada/alvo errado** (arquétipo §4.3): usa a sessão compartilhada como se fosse o mecanismo de isolamento; as duas linhas de trabalho passam a contaminar o mesmo contexto em vez de evoluir em ramos separados.
- **B — errada:** descarta o baseline já construído e reprocessa as 40 fontes do zero em cada uma das duas sessões novas — não mapeia a um arquétipo §4 (erro mecanístico específico): joga fora exatamente o trabalho compartilhado que o fork existe para preservar, pagando o custo de reingestão duas vezes.
- **C — correta.**
- **D — errada:** supõe que `continue` chamado duas vezes "cria automaticamente" ramos isolados — **feature inexistente porém verossímil** (arquétipo §4.5): `continue` não ramifica nada; ele sempre aponta para a sessão mais recente, então a segunda chamada reapontaria para a MESMA sessão, não para uma nova ramificação.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Aplicar
- Dificuldade: Médio
- Rubrica: 6 = Bloom 2 + integração 2 + cenário 1 + distratores 1
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: `fork_session=True` ramifica um baseline compartilhado em ramos independentes (id novo, original intacto) para explorar abordagens divergentes sem contaminação mútua.

## Q3 — Resposta correta: **B** · (1.7)

Apenas 3 dos 12 documentos mudaram — staleness **parcial**, não total. A resposta proporcional é informar ao agente especificamente QUAIS documentos mudaram, para que ele re-analise só esses de forma direcionada; o restante do contexto (os outros 9 documentos e o histórico do ticket) continua válido e não precisa ser refeito.

- **A — errada:** confia integralmente nas leituras antigas dos 12 documentos — não mapeia a um arquétipo §4 (erro mecanístico específico): ignora que 3 deles de fato mudaram, arriscando aplicar uma janela de reembolso já revogada.
- **B — correta.**
- **C — errada:** instrui o agente a descartar TODOS os 12 documentos como desconhecidos — não mapeia a um arquétipo §4 (erro mecanístico específico): joga fora o contexto válido dos 9 documentos que não mudaram, forçando reprocessamento desnecessário.
- **D — errada:** nunca resumir após qualquer atualização, sempre re-puxando ticket e os 12 documentos do zero — **quebra-automatismo** (§10; não mapeia a um arquétipo §4 — é a armadilha de generalizar em excesso a lição "dados majoritariamente obsoletos → sessão nova" (o cenário certo para essa lição é a Q4, com staleness quase total) para um caso de staleness PARCIAL, onde a re-análise direcionada já resolve com muito menos esforço): contraria o princípio de resposta proporcional / menor esforço primeiro.

## Q4 — Resposta correta: **D** · (1.7)

24 de 30 tool results estão obsoletos — staleness **quase total**, diferente do caso parcial da Q3. Aqui a re-análise direcionada não é suficiente porque a maior parte da base factual mudou; a via mais confiável é abrir uma sessão NOVA e injetar um resumo estruturado apenas das conclusões que ainda se sustentam, descartando os tool results obsoletos em vez de carregá-los para a frente.

- **A — errada:** supõe que "resumir a sessão antiga de qualquer forma" é seguro porque o volume de contexto acumulado compensaria a desatualização dos dados — **equívoco de capacidade** (arquétipo §4.6): é o mesmo padrão de "janela maior resolve diluição de atenção" — quantidade de contexto acumulado não corrige a veracidade/atualidade do conteúdo.
- **B — errada:** forka a sessão obsoleta para um ramo novo, carregando os mesmos 24 resultados obsoletos para dentro dele — **camada/alvo errado** (arquétipo §4.3): usa o mecanismo de ramificação (que resolve isolamento entre linhas de trabalho) para um problema que é obsolescência de dados — o fork simplesmente duplica o lixo, não o remove.
- **C — errada:** apenas aumenta `max_turns` para o agente "trabalhar em torno" dos resultados desatualizados — **equívoco de capacidade** (arquétipo §4.6): mais orçamento de turnos não torna dados obsoletos corretos; o problema é a qualidade da base de contexto, não a quantidade de turnos disponíveis para raciocinar sobre ela.
- **D — correta.**

## Q5 — Resposta correta: **A** · (1.7)

Fork ramifica a **conversa**, não o filesystem: as edições de arquivo feitas no fork são escritas REAIS em disco, visíveis a qualquer sessão apontando para o mesmo diretório — é exatamente por isso que o colega viu as mudanças sem ter tocado no fork. Se o engenheiro precisava também de isolamento dos ARQUIVOS, a ferramenta certa não é `fork_session` isoladamente, e sim um git branch/worktree separado ou *file checkpointing*.

- **A — correta.**
- **B — errada:** trata o comportamento como um bug, alegando que `fork_session=True` "deveria" isolar o filesystem também — **equívoco de capacidade** (arquétipo §4.6): supõe que o fork tem (ou deveria ter) uma capacidade de sandboxing de arquivos que ele nunca teve por design; isolar a CONVERSA é o próprio propósito da feature, não uma versão incompleta de isolar o disco.
- **C — errada:** propõe que o fork "deve ter reutilizado" acidentalmente o ID da sessão original — não mapeia a um arquétipo §4 (erro mecanístico específico): fork sempre gera um ID NOVO por design; não existe reuso acidental de ID que explique o sintoma observado.
- **D — errada:** propõe que a sessão do colega "deve ter sido resumida" a partir do ID do fork — não mapeia a um arquétipo §4 (erro mecanístico específico): o sintoma independe de o colega ter resumido algo; edições em disco são visíveis a QUALQUER sessão no mesmo diretório, resumida ou não.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 10 = Bloom 4 + integração 2 + cenário 2 + distratores 2
- Cenário: S4 — Developer Productivity
- Princípio testado: fork ramifica a CONVERSA, não o filesystem — edições de arquivo são reais e visíveis a qualquer sessão no mesmo diretório.

## Q6 — Resposta correta: **C** · (1.7)

Sessões são indexadas em disco por **cwd** (o diretório de projeto no momento em que a sessão foi criada), não só pelo `session_id`. Quando o script de automação chama `--resume` a partir de um `cwd` diferente do que criou a sessão, o SDK procura no caminho de projeto errado e devolve uma sessão nova e vazia — mesmo com o ID correto.

- **A — errada:** afirma que IDs de sessão "expiram em poucos minutos" — **feature inexistente porém verossímil** (arquétipo §4.5): não existe expiração por tempo; o transcript persiste em disco até ser removido explicitamente.
- **B — errada:** afirma que resumir só funciona "dentro da mesma chamada `query()`" que criou a sessão — não mapeia a um arquétipo §4 (erro mecanístico específico): inverte o propósito da feature — `resume` existe justamente para funcionar ENTRE chamadas `query()` distintas, inclusive em processos/scripts diferentes.
- **C — correta.**
- **D — errada:** afirma que `fork_session` precisa estar sempre `True` para `resume` funcionar — **feature inexistente porém verossímil** (arquétipo §4.5): inventa um acoplamento obrigatório entre os dois parâmetros que não existe — `resume` e `fork_session` são mecanismos independentes (retomar vs. ramificar).

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Médio
- Rubrica: 6 = Bloom 3 + integração 1 + cenário 1 + distratores 1
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: `resume` depende do `cwd` correto — sessões são indexadas por diretório de projeto, não apenas pelo `session_id`.

### Conceitos reforçados
- `resume=session_id` retoma uma sessão ESPECÍFICA com o contexto intacto; `continue` pega a mais recente do diretório; `fork_session=True` ramifica um baseline em um ID novo, deixando o original intacto — use fork para explorar abordagens divergentes em paralelo.
- Staleness PARCIAL (poucos arquivos/documentos mudaram) → resume + informe quais mudaram, para re-análise direcionada. Staleness QUASE TOTAL (maioria dos tool results obsoleta) → sessão nova + resumo estruturado das conclusões ainda válidas, não resumir a sessão velha.
- Fork ramifica a CONVERSA, não o filesystem: edições de arquivo no fork são escritas reais, visíveis a qualquer sessão no mesmo diretório — para isolar também os arquivos, use git branch/worktree ou checkpointing.
- `resume` depende do `cwd` correto: sessões são indexadas por diretório de projeto; rodar de um cwd diferente devolve uma sessão nova mesmo com o ID certo.
- Pegadinha recorrente: não existe acoplamento obrigatório entre `resume` e `fork_session`, nem expiração por tempo, nem restrição a uma única chamada `query()` — são invenções verossímeis, não comportamento real do SDK.
