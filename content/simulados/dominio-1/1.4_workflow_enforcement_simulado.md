## Q1
In 3% of trials, a customer-support agent calls `process_refund` before verifying the customer's identity through `get_customer`, even though the system prompt states this order is mandatory. The business requires an actual guarantee that no refund is ever processed for an unverified customer — not merely a lower failure rate. What is the most effective way to enforce this?

- **A)** Rewrite the system prompt with more emphatic language ("ALWAYS verify identity before refunding — this is critical") and re-run the trial.
- **B)** Add several few-shot examples in the prompt showing the correct call order, so the model has concrete precedent to follow.
- **C)** Add a `PreToolUse` hook that returns a `deny` `permissionDecision` for `process_refund` unless a prior `get_customer` call already succeeded in the same session.
- **D)** Lower the model's temperature so its behavior is less variable from run to run.

## Q2
Over two weeks, 40 production deploys went out through a CI pipeline with zero `PreToolUse` hook invocations recorded — even though a prerequisite gate was configured to deny any deploy without a passing test-suite check. The gate targets a deploy tool exposed through an MCP server, and the `HookMatcher` was written as `matcher: "deploy_production"`. What is the most likely root cause?

- **A)** The hook should be registered on `PostToolUse` instead, since MCP tool calls only become visible to hooks after they finish executing.
- **B)** `PreToolUse` hooks cannot deny calls to tools provided by an MCP server; only built-in tools support a `deny` `permissionDecision`.
- **C)** The hook's timeout is too short for the test-suite check to finish evaluating before `PreToolUse` gives up and allows the call through.
- **D)** The `HookMatcher` uses the short tool name; MCP-provided tools are matched by their fully qualified name (`mcp__release__deploy_production`), so the matcher silently never matches.

## Q3
In 22% of tickets escalated to a human fact-checker in a multi-agent research pipeline, the fact-checker reports they can't tell what to actually verify. The pipeline routes any citation flagged as contradictory straight to them, but they have no access to the full multi-agent transcript — only whatever content is attached to the escalation ticket itself. Which handoff content is most appropriate?

- **A)** A structured summary with fixed fields — claim, conflicting sources, why flagged, recommended resolution.
- **B)** A short free-text note, e.g., "This citation looks contradictory, please check it."
- **C)** A link to the full multi-agent transcript so the fact-checker can read through everything and reconstruct the context themselves.
- **D)** The original source document forwarded as-is, with no summary or analysis attached.

## Q4
After a support agent handles refunds for 30 different customers across a single session, a refund for customer `C-47` goes through without `get_customer` ever being called for that customer — even though a `PreToolUse` gate is active and is supposed to require verification before every refund. Earlier in the same session, the agent had verified a different customer, `C-11`, and resolved that ticket. What is the root cause?

- **A)** The gate should be reinforced with a stronger, more explicit system-prompt reminder telling the agent to call `get_customer` again for every single new customer before issuing any refund.
- **B)** The gate's state is a single session-wide `verified` flag instead of one scoped per customer, so verifying any customer flips it for every later refund, regardless of who it's for.
- **C)** A classifier should be added to detect when the conversation has switched to a different customer, and trigger re-verification only then.
- **D)** The agent should self-report, before each refund, whether it believes the current customer was already verified, and skip the gate when it says yes.

## Q5
Across 50 recent pull requests touching payment logic, 12 skipped the mandatory senior-engineer sign-off because their descriptions read as "confident" to a sentiment/tone classifier used to trigger escalation — even though the changed files were squarely in the policy's scope. Pull requests with hedging language ("I think this might work") get escalated regardless of what they touch. What is the most effective fix?

- **A)** Lower the classifier's confidence threshold so more pull requests get flagged as uncertain, indirectly catching more payment-touching PRs.
- **B)** Add a second classifier, trained specifically on payment-related language, to catch confident-sounding payment PRs that the tone classifier misses.
- **C)** Keep the tone classifier, but also require the author to self-rate their own confidence in the description, and escalate whenever either signal is low.
- **D)** Escalate based on a deterministic check of the changed file paths (e.g., under `payments/`), not on how confident the description reads.

## Q6
For the last 200 published reports, 100% passed through mandatory editor review before going live, regardless of what the citation-checking subagent flagged in each one, and editorial review has historically caught essentially all citation errors before publication. A teammate now proposes adding a `PreToolUse` hook that denies the `publish_report` tool until every citation has been manually confirmed one by one. Given the mandatory editor review already in place for every report, what is the most appropriate response to the proposal?

- **A)** Build the proposed `PreToolUse` deny gate anyway: a deterministic hook is the safer default for a citation-accuracy requirement, so it should be added on top of the existing editor review.
- **B)** Skip the hard gate: have the subagent flag low-confidence citations in its output, and rely on the mandatory editor review already in place to catch anything that slips through.
- **C)** Replace the proposal with a confidence-scoring classifier that auto-approves citations above a threshold and only escalates the rest for manual confirmation.
- **D)** Escalate to the editor based on the subagent's self-reported confidence in each citation, and skip the gate whenever the subagent reports high confidence.
