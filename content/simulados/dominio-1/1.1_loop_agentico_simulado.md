## Q1
A developer-productivity agent inside an internal CLI tool runs a loop that calls the Claude API, executes any requested tool, and repeats. Across a sample of 50 runs, 9 stop after exactly one API call even though the task clearly required editing multiple files, while 6 others run until a hard cap of 15 iterations without finishing. The current loop exits as soon as the assistant's response contains any non-empty text field, on the theory that generated commentary signals the task is finished. What is the most effective fix?

- **A)** Add a second-pass classifier that reads the assistant's text after every turn and predicts, independently of any tool call, whether the task is actually finished.
- **B)** Replace the text-presence check with `stop_reason`: keep looping while it is `"tool_use"`, and only stop once it becomes `"end_turn"` — a single response can contain both narrative text and a `tool_use` block.
- **C)** Instruct the model, in the system prompt, not to include any text before it has finished issuing every tool call the task requires.
- **D)** Lower the hard iteration cap from 15 to 5 so runs of this kind fail faster and the team notices the bug sooner.

## Q2
A customer support resolution agent's harness executes the `look_up_order` tool exactly as requested, but the developer's loop appends only the assistant's message object to the running `messages` list and discards the tool's return value entirely. In production, telemetry shows the agent calls `look_up_order` with the identical order ID on every single turn until it exhausts the iteration budget, never referencing any data from the lookup in its replies. What is the root cause?

- **A)** `max_tokens` is set too low, silently truncating the tool's returned JSON before the model can read it.
- **B)** The tool should be marked so the harness enforces at most one call per task, since a tool that gets invoked repeatedly with the exact same arguments is assumed, by that policy alone, to already be malfunctioning and unsafe to call again.
- **C)** The Messages API is stateless — without a `tool_result` block matched to the `tool_use_id` appended to the history, the model never sees the tool's output and has no way to know it already ran.
- **D)** The system prompt needs an explicit instruction telling the model never to call the same tool twice in a row.

## Q3
A multi-agent research system's lead agent is asked to search three sources and then synthesize a summary. Logs show that on 22% of runs, the assistant's response contains both a short line like "I'll start by searching the first source" and a `tool_use` block requesting that search — yet the harness's loop treats any non-empty text as the finished answer and returns it to the user, skipping the tool call entirely. What is the most effective fix?

- **A)** Key the loop off `stop_reason == "tool_use"` instead of text presence — a single turn can legitimately contain both narrative text and a `tool_use` block, and only `stop_reason` reliably signals whether more tool calls are still requested.
- **B)** Rewrite the search tool's description to be less ambiguous, so Claude commits to the call instead of hesitating with filler text first.
- **C)** Add few-shot examples to the system prompt showing tool-call-only turns, training the model not to emit any text before calling a tool.
- **D)** Move the lead agent to a model with a larger context window, since the premature stop is caused by attention dilution over the multi-step plan.

## Q4
A developer-productivity agent enforces `while stop_reason == "tool_use" and iterations < 25`. Over the last two weeks, 4 of 200 runs on large multi-file refactors hit the 25-iteration cap and were cut off mid-task, with the model still requesting new, distinct file edits right up to the cutoff. A teammate wants to simply double the cap to 50 and move on. Before agreeing, what should you check first?

- **A)** Whether adding a natural-language instruction that tells the model to summarize its progress every 5 turns would let the loop detect completion sooner.
- **B)** Whether replacing the iteration cap with a sentiment check on the assistant's tone would better predict when the agent is stuck.
- **C)** Whether introducing a routing classifier that pre-labels each incoming task as "small" or "large" before the run even starts, and then assigns a different, more restrictive tool set for each label, would prevent this kind of cutoff from recurring on future large-refactor runs.
- **D)** Whether the stop condition already correctly follows `stop_reason` and the affected runs show genuine per-turn progress rather than repeated identical tool calls — if so, the cap is only a safety net, and raising it for legitimately large tasks is reasonable.

## Q5
A multi-agent research system must answer questions where the number and order of searches depends entirely on what earlier searches return — sometimes 2 searches suffice, sometimes 8 are needed with follow-ups on prior findings. The team is choosing the orchestration design for the lead agent's tool loop before building it. Which approach is the most effective, and why?

- **A)** Keep the loop model-driven: each turn Claude selects the next tool via a `tool_use` block from the accumulated context, the harness executes it and appends the `tool_result`, continuing until `stop_reason` is `"end_turn"` — this adapts naturally to a variable, data-dependent number of steps.
- **B)** Pre-configure a fixed decision tree (search → fetch → summarize, exactly three steps) before runtime, since a hardcoded sequence is inherently more predictable and auditable than letting the model choose tools at runtime.
- **C)** Add a routing classifier upstream that reads the user's question and predicts the total number of searches needed, then allocates that many fixed tool-call slots in advance.
- **D)** Let the model call the search tool directly from its own generation without the harness executing anything, trusting the model's internal reasoning to run the search itself.

## Q6
A customer support resolution agent correctly loops on `stop_reason == "tool_use"` and stops on `"end_turn"`, with a hard cap of 20 iterations as a safety net. A new bulk-refund workflow needs to look up and process up to 30 distinct order IDs in a single conversation, one tool call per order; every call returns a valid `tool_result` and the model keeps requesting the next order in sequence, but the cap cuts the run off at order 20. What is the most effective fix?

- **A)** Split the workflow across multiple separate agent sessions, each hard-capped at 10 iterations, and stitch the partial results together after every session ends.
- **B)** Raise the iteration cap to a value that comfortably covers the workflow's legitimate per-order tool-call pattern (for example, 40) — the stop logic is already correct, and each iteration here reflects real, necessary progress rather than a stuck loop.
- **C)** Replace the iteration cap with a check for the phrase "all refunds processed" in the assistant's text, treating that semantic marker as more reliable than a raw count.
- **D)** Add a classifier that inspects the content of each `tool_result` after every single call and predicts, using its own self-reported confidence score, whether the refund workflow is still "on track," automatically escalating to a human whenever that confidence drops below a fixed threshold.
