## Q1
In a developer-productivity workflow built with the Claude Agent SDK, a coordinator agent is supposed to delegate code-review and test-writing requests to two specialized subagents, each defined with a clear `AgentDefinition` and a well-scoped `description`. Across a trial of 20 pull requests, the coordinator answered every single one itself and never invoked either subagent, even when a request matched a subagent's description almost verbatim. The coordinator's system prompt explicitly describes when to delegate, and its `allowedTools` list is `["Read", "Grep", "Bash"]`. What is the single most likely cause, and what is the correct fix?

- **A)** The subagents' `description` fields don't restate the coordinator's full system prompt, so the coordinator cannot recognize when to hand off work — rewrite each description to mirror the coordinator's prompt.
- **B)** The coordinator's `allowedTools` list omits `"Task"`, so it has no mechanism to spawn a subagent at all, no matter how well the prompt and `AgentDefinition`s are written — add `"Task"` to `allowedTools`.
- **C)** The coordinator has inherited the subagents' isolated context, which prevents it from recognizing that subagents exist — reconfigure the session so context flows from child to parent.
- **D)** The `AgentDefinition`s are missing `share_context=True`, which is required for the coordinator to discover and route to a subagent at runtime — add that field to each `AgentDefinition`.

## Q2
In 9 of 10 recent runs, a multi-agent research system's final report treats its topic as almost entirely unexplored, omitting nearly everything the research subagent found. The pipeline spawns a research subagent via the `Task` tool to gather findings on a topic, then spawns a separate synthesis subagent to write the final report from those findings. Both subagents are configured with narrow, well-written `AgentDefinition`s, and the research subagent's raw output is confirmed thorough and accurate in every run. Which mechanism must the coordinator use so the synthesis subagent actually receives the research subagent's findings?

- **A)** Rely on subagents automatically inheriting the full conversation history from earlier subagent runs in the same coordinator session, the way a single agent accumulates turns.
- **B)** Set `share_context=True` when spawning the synthesis subagent so it links directly to the research subagent's transcript instead of starting from a clean slate.
- **C)** Include the research subagent's findings directly in the text of the prompt used to spawn the synthesis subagent, since the prompt string is the only channel from parent to child.
- **D)** Use `fork_session` on the research subagent's session so the synthesis subagent starts from the exact same branch point the research subagent reached, carrying its state forward.

## Q3
A support-ticket coordinator resolves each ticket by running three independent lookups — billing history, shipping status, and refund eligibility — each handled by its own subagent that completes in under 10 seconds when run alone. Across a sample of tickets requiring all three lookups, the coordinator's end-to-end resolution time averaged 27 seconds. Trace logs show the coordinator emits one `Task` tool call, waits for that subagent's result, then emits the next `Task` call in the following turn, repeating for the third lookup. What is the single best way to fix the latency?

- **A)** Emit all three `Task` tool calls within a single coordinator response, so the lookups run concurrently and total time approaches the slowest single lookup rather than their sum.
- **B)** Increase each lookup subagent's `max_tokens` so each one completes its own query faster.
- **C)** Give the three lookup subagents `fork_session` so they can share partial progress with each other while each lookup is still running.
- **D)** Consolidate the three lookups into one generalized subagent with a broader tool set and an internal classifier that decides at runtime which table or tables to query.

## Q4
In a multi-agent research pipeline, a synthesis subagent receives a single prompt containing ten paragraphs of research findings and their sources pasted together as free text, then writes a cited report. Across a sample of 50 generated reports, 15 contained quotes attributed to the wrong source, even though each research subagent's raw output had correctly paired every claim with its source URL before the coordinator assembled the synthesis prompt. What is the single best fix for the misattribution?

- **A)** Give the synthesis subagent `WebFetch` access so it can revisit each URL and re-verify which claim came from which source before writing the report, catching mismatches after the fact.
- **B)** Have the coordinator use `fork_session` so the synthesis subagent shares the exact context window the research subagent used, instead of receiving a fresh, isolated context of its own.
- **C)** Run the synthesis step three times and keep only the source attributions that agree across at least two of the three independent runs, treating majority agreement as ground truth.
- **D)** Pass the findings in a structured format that pairs each claim with its own source metadata, instead of flattening everything into free text.

## Q5

Its stated role: receive a module's spec from the coordinator, decide which of three independent test suites are needed (unit, integration, contract), delegate each suite to its own specialized sub-subagent — a unit-writer, an integration-writer, and a contract-writer — and merge their three outputs into one PR-ready diff. Which tool configuration for the lead test-writer's `AgentDefinition` best fits this stated role?

- **A)** Give it no tools at all, since its only stated job is merging output that is handed to it.
- **B)** Include `"Task"` in its tools, since its stated role requires it to spawn its own specialized sub-subagents for each test type — genuine nested delegation matching a real sub-decomposition need.
- **C)** Give it the full default tool set, including `WebSearch` and `Bash`, so it can adapt to any testing need that comes up later.
- **D)** Give it `Write` and `Edit` only, and have the coordinator itself spawn the three sub-subagents directly, with the lead test-writer only merging their results.

## Q6
A support coordinator's prompt for a ticket-lookup subagent is a fixed script: "Step 1: query the billing table by ticket ID. Step 2: if empty, query the shipping table. Step 3: if still empty, query the refunds table. Step 4: return the first non-empty result verbatim." In 18% of tickets tied to bundled orders — where billing and shipping records must be combined — the subagent returns only one table's raw, unformatted fields and never recognizes that the ticket needs both. Which change best follows the recommended way to write coordinator-to-subagent prompts?

- **A)** Add more numbered steps and conditionals to the script, explicitly covering bundled orders, unusual status codes, and every other edge case reviewers can anticipate in advance.
- **B)** Keep the script exactly as written, but move it from the `Task` prompt into the ticket-lookup subagent's `AgentDefinition` system prompt instead, so the rigid recipe simply lives in a different configuration file.
- **C)** Replace the script with the underlying objective and quality bar — look up this ticket across billing, shipping, and refunds, and combine records for bundled orders — letting the subagent decide how.
- **D)** Escalate any ticket where the subagent's self-reported confidence in its own answer is low, instead of changing anything about how the prompt itself is written.
