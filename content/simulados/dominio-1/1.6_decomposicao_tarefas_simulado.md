## Q1
In 92% of pull requests submitted to this platform team, the automated reviewer runs the same four review aspects—coding style, security, test coverage, and documentation—in the same fixed order every time, regardless of what each diff actually contains. The team is deciding how to formally decompose this review workflow going forward, and wants an approach that matches how predictable the process already is. Which decomposition strategy best fits this task?

- **A)** A dynamic agent that decides at runtime which of the four review aspects to run, based on intermediate findings in each diff.
- **B)** Have the model self-report a confidence score for each aspect, then skip whichever aspects it feels most confident about.
- **C)** A fixed sequential pipeline (prompt chaining) where each of the four aspects is a predefined step, run in the same order every time.
- **D)** A single prompt that pastes the entire diff and asks the model to address all four aspects at once, no matter how large the diff is.

## Q2
A pull request modifies 40 files across three services. When the review is attempted as a single prompt containing all 40 diffs at once, the findings become shallow and inconsistent — flagging a naming issue in one file while missing an identical one three files later. What decomposition change is most likely to fix this pattern?

- **A)** Run a per-file local analysis pass for each of the 40 files, then a separate cross-file integration pass that checks how the files interact with each other.
- **B)** Keep the single-prompt review, but ask for a larger context window and a higher max-output limit so the model has more room to cover all 40 files.
- **C)** Train a machine-learning classifier on historical bug reports to predict which of the 40 files are risky, then review only those files in one prompt.
- **D)** Grant the reviewer agent Bash access to run a static-analysis linter across all 40 files, without changing anything about how the review prompt itself is currently decomposed into passes.

## Q3
Quarterly signups dropped 18% quarter-over-quarter, and a three-person research team assigns Claude the task "investigate why and produce a root-cause report." Nobody knows in advance which data sources, time ranges, or user segments will turn out to matter — that only becomes clear once the agent starts pulling data and finds signals worth following up on. Which decomposition approach best fits this task?

- **A)** A fixed pipeline with the same predefined steps, run in the same order, regardless of what the data actually shows once the investigation starts.
- **B)** Train a machine-learning classifier on historical signup data to predict the root cause directly, then generate the final report from that single upfront prediction, skipping any further exploration.
- **C)** Ask the model to write the full root-cause report in one response, without querying any data sources or logs first.
- **D)** Dynamic decomposition: have the agent first explore the available data, then generate a prioritized plan of follow-up subtasks that adapts as findings come in.

## Q4
During a per-file-only review pass (no cross-file integration step), the reviewer approved a pull request where `calculate_discount()` is defined with two parameters in `pricing.py` but is called with three arguments in `checkout.py` — each file looked correct in isolation, and the mismatch reached staging before a runtime error surfaced it. The team wants to know why adding a cross-file integration pass would have caught this earlier. What is the best explanation?

- **A)** Per-file passes are already fully sufficient on their own; adding a cross-file integration pass would only be redundant extra work.
- **B)** The mismatch spans two files, so no single-file pass sees both the definition and the call site together — only a pass across files can compare them.
- **C)** The integration pass works by re-running each file's local pass a second time, still strictly one file at a time, purely to double-check the exact same earlier findings.
- **D)** The integration pass is meant to fully replace the per-file passes rather than run alongside them, so the team should drop per-file review from the workflow altogether.

## Q5
Across a sample of 500 resolved support tickets, the sequence of verification and remediation steps varied by account tier, product line, and region in 78% of cases — no two tickets followed an identical set of steps. The team currently uses a fixed five-step script for every ticket and is considering replacing it with a dynamic planner that decides each ticket's steps at runtime based on what it finds in the account and ticket data. A skeptical engineer objects: "This is over-engineering — just keep the fixed script, like every other support workflow." Is the skeptic right?

- **A)** No — the steps genuinely vary case by case based on discovered account and ticket attributes, so dynamic decomposition matches the real shape of the work; a fixed script would miss steps.
- **B)** Yes — dynamic decomposition is inherently over-engineering for any customer-facing workflow, so the fixed five-step script should be kept regardless of how much the required steps vary by ticket.
- **C)** No — but only because agents should first rate their own confidence that the fixed script covered the ticket correctly, and switch to the dynamic planner only for low-confidence tickets.
- **D)** No — the better fix is to train a classifier on the 500 historical tickets to predict a separate fixed step-sequence for every account-tier-and-product-line combination well in advance.

## Q6
Across all 200 planning calls the coordinator made last week, every single one set `tool_choice` to force the model to call a single `decompose_plan` tool that returns a JSON array of subtasks, before any subagent is spawned via the `Task` tool. After each forced call returns, the coordinator still spawns a separate subagent for every subtask to actually run the searches and compile results. A new teammate asks why the coordinator doesn't skip the subagent-spawning step, since "the model already produced the plan by calling the tool." What is the best explanation of what the forced `tool_choice` call actually accomplished?

- **A)** Forcing `tool_choice` to `decompose_plan` makes Claude execute each subtask internally before returning, so the coordinator's later spawn step is redundant and safe to remove.
- **B)** Forcing `tool_choice` guaranteed the plan came back as validated structured output — the subtask list — but it executed nothing; running each subtask still requires the coordinator to spawn it separately.
- **C)** The forced call was unnecessary altogether: dynamic decomposition never benefits from a structured plan, so each subagent should decide its own subtasks independently with no shared plan.
- **D)** The forced `decompose_plan` call should be replaced by a plain-text prompt asking the model to "list the subtasks," since forcing a specific tool only adds latency with no benefit over free-form text.
