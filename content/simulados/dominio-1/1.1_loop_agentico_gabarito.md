## Q1 — Resposta correta: **B** · (1.1)

O bug-raiz é conflar "o assistente produziu texto" com "a tarefa terminou". Uma única resposta pode conter **texto narrativo e um bloco `tool_use` no mesmo turno** — texto não é sinal de término. O contrato confiável é o `stop_reason`: continua enquanto for `"tool_use"`, para quando virar `"end_turn"`.

- **A — errada:** over-engineering — adicionar um classificador de segunda passada para "adivinhar" se a tarefa terminou, quando o próprio `stop_reason` já responde isso de forma determinística.
- **B — correta.**
- **C — errada:** probabilístico onde precisa ser determinístico — instruir via prompt para "não incluir texto antes de terminar" tenta controlar por linguagem natural um comportamento que o modelo pode legitimamente variar; não corrige a lógica de parada do loop.
- **D — errada:** camada/alvo errado — reduzir o teto de iterações não toca no bug (parada prematura por presença de texto); só faz outros runs falharem mais rápido, sem resolver a causa.

## Q2 — Resposta correta: **C** · (1.1)

A Messages API é *stateless*: o histórico completo é reenviado a cada volta. O modelo só "vê" o retorno da ferramenta através de um bloco `tool_result` casado ao `tool_use_id` do `tool_use` original. Sem esse bloco no histórico, o modelo não tem como saber que a chamada já ocorreu — e repete a mesma chamada, exatamente o sintoma da telemetria.

- **A — errada:** camada/alvo errado — `max_tokens` limita a geração do assistente, não o conteúdo do `tool_result` inserido pelo harness; não explica a repetição idêntica a cada turno.
- **B — errada:** camada/alvo errado — restringir o número de chamadas ao tool não resolve a falta do resultado no histórico; o modelo continuaria "cego" ao que já rodou.
- **C — correta.**
- **D — errada:** probabilístico onde precisa ser determinístico — uma instrução de prompt não substitui o protocolo estrutural de anexar o `tool_result`; o modelo não tem memória própria da chamada sem o bloco correto no histórico.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Entender
- Dificuldade: Fácil
- Rubrica: 3 = Bloom 1 + integração 0 + cenário 1 + distratores 1
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: API stateless — `tool_result` casado ao `tool_use_id` é o único canal de retorno ao modelo

## Q3 — Resposta correta: **A** · (1.1)

Mesmo turno pode conter texto narrativo **e** um `tool_use` — não são mutuamente exclusivos. O loop deve decidir com base em `stop_reason` (continuar em `"tool_use"`), nunca com base em "há texto ou não". É o mesmo anti-padrão de "presença de texto = terminou", aqui causando o skip do tool call.

- **A — correta.**
- **B — errada:** camada/alvo errado — a descrição da ferramenta não é a causa; o cenário mostra o modelo chamando corretamente a ferramenta certa, o bug está na lógica do loop, não na seleção de tool.
- **C — errada:** probabilístico onde precisa ser determinístico — few-shot pode até reduzir a frequência do texto solto, mas não garante o comportamento; a garantia correta vem de checar `stop_reason`, não de moldar a saída do modelo via exemplos.
- **D — errada:** equívoco de capacidade — "janela maior resolve diluição de atenção" é o erro clássico de atribuir um bug de lógica de loop a uma limitação de capacidade do modelo.

**Metadados (revisão; não exibir ao candidato):**

- Dificuldade: Difícil
- Rubrica: 7 = Bloom 3 + integração 1 + cenário 1 + distratores 2
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: texto e `tool_use` podem coexistir no mesmo turno — só `stop_reason` decide continuação

## Q4 — Resposta correta: **D** · (1.1)

O teto de iterações é **rede de segurança**, não o mecanismo primário de parada — mas isso não significa que ele nunca deva ser ajustado. Antes de mudar qualquer número, o passo certo é verificar a causa raiz: a lógica de `stop_reason` está correta? Os runs afetados mostram progresso real por turno (edições distintas) ou estão repetindo a mesma chamada? Se o `stop_reason` já governa corretamente e o teto só está baixo demais para o tamanho legítimo da tarefa, aumentá-lo é proporcional.

- **A — errada:** probabilístico onde precisa ser determinístico — pedir resumos de progresso em linguagem natural não é um sinal confiável para o loop decidir quando parar.
- **B — errada:** proxy não confiável — sentimento/tom do texto do assistente não mede progresso real da tarefa.
- **C — errada:** over-engineering — um classificador de roteamento por "tamanho da tarefa" resolve com mais uma camada de ML algo que uma verificação direta do `stop_reason` e do padrão de chamadas já resolve.
- **D — correta.**

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Analisar
- Dificuldade: Médio
- Rubrica: 6 = Bloom 3 + integração 1 + cenário 1 + distratores 1
- Cenário: S4 — Developer Productivity
- Princípio testado: teto de iterações é rede de segurança — calibrar após confirmar que `stop_reason` já governa corretamente

## Q5 — Resposta correta: **A** · (1.1)

Quando o número e a ordem dos passos dependem do resultado de passos anteriores, o loop deve ser **dirigido pelo modelo**: a cada turno Claude escolhe a próxima ferramenta via `tool_use` a partir do contexto acumulado, o harness executa e devolve o `tool_result`, até `stop_reason` virar `"end_turn"`. Esse desenho absorve naturalmente uma contagem de passos variável e dependente de dados.

- **A — correta.**
- **B — errada:** over-engineering na direção da rigidez — uma árvore de decisão fixa "parece" mais previsível, mas quebra exatamente nos casos abertos do cenário (as vezes 2, às vezes 8 buscas); "inerentemente mais previsível" é uma generalização que não vale para tarefas de passo variável.
- **C — errada:** over-engineering — um classificador que prevê de antemão "quantas buscas serão necessárias" tenta substituir por ML algo que o próprio loop dirigido pelo modelo já resolve, turno a turno, sem essa camada extra.
- **D — errada:** feature/capacidade inexistente — o modelo não executa ferramentas por conta própria; ele emite o bloco `tool_use`, e é o harness que executa e devolve o `tool_result`. Sem esse papel do harness, o loop simplesmente não funciona.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 10 = Bloom 4 + integração 2 + cenário 2 + distratores 2
- Cenário: S3 — Multi-Agent Research System
- Princípio testado: decisão dirigida pelo modelo (turno a turno) vence árvore de decisão pré-configurada quando os passos dependem de resultados intermediários

## Q6 — Resposta correta: **B** · (1.1)

Quebra-automatismo: nem toda vez que um run bate no teto de iterações o teto está "errado por princípio". Aqui a lógica de `stop_reason` já está correta e cada iteração corresponde a progresso real e necessário (um pedido de reembolso por vez, com `tool_result` válido a cada chamada). O teto é rede de segurança; para uma tarefa legitimamente longa, ajustá-lo para um valor que cubra o padrão real de uso é a resposta proporcional — não um sintoma a mascarar.

- **A — errada:** camada/alvo errado — fragmentar em múltiplas sessões com o mesmo teto baixo só empurra o mesmo limite artificial para outro lugar e adiciona a complexidade de costurar resultados parciais, sem necessidade.
- **B — correta.**
- **C — errada:** probabilístico onde precisa ser determinístico — trocar uma contagem exata por um marcador textual no texto do assistente reintroduz exatamente o anti-padrão de parar por linguagem natural.
- **D — errada:** over-engineering + proxy não confiável — um classificador de "confiança" sobre cada `tool_result` para decidir se está "on track" adiciona uma camada de ML sobre um problema que já está resolvido corretamente pelo `stop_reason`; confiança auto-inferida não é um sinal confiável de progresso.

**Metadados (revisão; não exibir ao candidato):**
- Bloom: Avaliar
- Dificuldade: Difícil
- Rubrica: 8 = Bloom 4 + integração 1 + cenário 1 + distratores 2
- Cenário: S1 — Customer Support Resolution Agent
- Princípio testado: resposta proporcional — calibrar o teto (rede de segurança) para o padrão real de uso, não tratá-lo como sintoma a mascarar sempre

### Conceitos reforçados
- Término do loop guiado por `stop_reason` (`"tool_use"` → continua; `"end_turn"` → para); nunca por presença/ausência de texto.
- Um mesmo turno pode conter texto narrativo **e** um bloco `tool_use` — texto não é indicador de conclusão.
- API *stateless*: anexar a resposta do assistente + o `tool_result` (casado por `tool_use_id`) ao histórico a cada iteração, senão o modelo "esquece" que a ferramenta já rodou.
- Teto de iterações é **rede de segurança**, não o critério de parada — mas pode e deve ser calibrado quando a lógica de `stop_reason` está correta e o teto é baixo demais para o tamanho legítimo da tarefa.
- Decisão dirigida pelo modelo (turno a turno, via `tool_use`) vs. árvore de decisão pré-configurada — a primeira é necessária quando a sequência de passos depende de resultados intermediários.
- Anti-padrões: parar por linguagem natural, "texto = conclusão", teto de iterações tratado como sintoma sempre errado, over-engineering com classificadores/roteamento onde `stop_reason` já resolve, proxies não confiáveis (sentimento, confiança auto-reportada).
