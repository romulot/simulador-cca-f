## Q1 — Resposta correta: **C** · (1.4)

O requisito é uma **garantia**, não uma taxa de falha baixa. Um hook `PreToolUse` que retorna `deny` como `permissionDecision` para `process_refund` sem verificação prévia é enforcement **determinístico**: a operação fica impossível sem a pré-condição, independente do que o modelo "decida" fazer.

- **A — errada:** **probabilístico onde precisa ser determinístico** — reforçar o texto do prompt ainda deixa uma chance não-nula de falha (os 3% observados); é instrução, não garantia.
- **B — errada:** **probabilístico onde precisa ser determinístico** — few-shot ajuda o modelo a *aprender o padrão*, mas continua sendo inferência probabilística, não um bloqueio real.
- **C — correta.**
- **D — errada:** **equívoco de capacidade** — temperatura controla aleatoriedade da amostragem de texto; não é um mecanismo de compliance e não elimina a possibilidade de a ordem errada ocorrer.

## Q2 — Resposta correta: **D** · (1.4)

Tools expostas por um MCP server são vistas pelo modelo (e pelo `HookMatcher`) pelo nome **totalmente qualificado** `mcp__<server>__<tool>`. Um matcher escrito com o nome curto (`"deploy_production"`) nunca casa com `mcp__release__deploy_production` — o hook fica configurado, mas é um **no-op silencioso**: nada dispara, nada é negado, e nenhum erro aparece nos logs porque, do ponto de vista do sistema de hooks, o matcher simplesmente não encontrou a tool que ele esperava.

- **A — errada:** **camada/alvo errado** — troca o evento certo (`PreToolUse`, que roda antes da execução e é o único que pode negar) por `PostToolUse`, que só vê a chamada depois que ela já rodou; isso pioraria a situação, não a corrigiria.
- **B — errada:** **equívoco de capacidade** — hooks `PreToolUse` conseguem negar tools de MCP servers normalmente; a afirmação de que só built-ins suportam `deny` é falsa e mal interpreta o mecanismo.
- **C — errada:** **camada/alvo errado** — timeout do hook é um componente real, mas não é o que explica "zero invocações"; a causa está em o matcher nunca casar, não em o hook expirar depois de casar.
- **D — correta.**

## Q3 — Resposta correta: **A** · (1.4)

O humano **não tem acesso ao transcript**, então o handoff precisa carregar tudo que ele precisa em **campos fixos e estruturados**: a claim, as fontes em conflito, por que foi flagrado, e uma ação recomendada. É a skill central do 1.4 — handoff estruturado substitui a necessidade de o humano reconstruir contexto.

- **A — correta.**
- **B — errada:** **handoff sem estrutura** — uma nota livre e vaga não carrega os campos fixos (quais fontes, qual a claim, por quê) que a decisão exige; sem eles, o fact-checker tem que reconstruir a triagem sozinho, exatamente o trabalho que o handoff deveria carregar.
- **C — errada:** **camada/alvo errado** — empurra o trabalho de síntese para a camada errada (o humano, que foi explicitamente descrito como sem acesso ao transcript), quando quem deveria sintetizar é o próprio pipeline antes do handoff.
- **D — errada:** **equívoco de capacidade** — assume que encaminhar o documento-fonte bruto equivale a informar o humano; ignora que o valor do handoff está exatamente na análise que falta.

## Q4 — Resposta correta: **B** · (1.4)

O gate é determinístico na forma (um `PreToolUse` que bloqueia), mas o **estado que ele consulta está mal-escopado**: um único flag `verified` vale para a sessão inteira, não por cliente. Depois que QUALQUER cliente é verificado, o flag fica `True` para sempre e "libera" reembolsos de outros clientes que nunca passaram por `get_customer`. A causa raiz não é o agente "esquecer" de verificar — é o gate checar a pergunta errada ("alguém foi verificado?" em vez de "*este* cliente foi verificado?").

- **A — errada:** **probabilístico onde precisa ser determinístico** — é a resposta-reflexo clássica do domínio ("reforce o prompt"), mas o problema está no modelo de estado do gate, não na instrução ao agente; reforçar o prompt não muda o que o flag representa.
- **B — correta.**
- **C — errada:** **over-engineering** — treinar um classificador para detectar troca de cliente adiciona uma camada de ML para resolver o que uma estrutura de dados simples (chave por `customer_id`) já resolve.
- **D — errada:** **proxy plausível não confiável** — confiar no auto-relato do modelo sobre se "acha" que o cliente atual já foi verificado é exatamente o tipo de sinal não-confiável que um gate determinístico deveria eliminar, não reintroduzir.

## Q5 — Resposta correta: **D** · (1.4)

A condição que realmente importa para a política ("este PR toca lógica de pagamento?") é observável diretamente nos **arquivos alterados** — um sinal determinístico. Escalar com base em tom/sentimento da descrição usa um **proxy** que não tem relação causal com o que a política quer proteger: um autor confiante que toca `payments/` escapa, e um autor inseguro sobre um PR de baixo risco é escalado sem necessidade.

- **A — errada:** **proxy plausível não confiável** — ajustar o limiar do classificador de tom ainda deixa a decisão presa a um sinal (linguagem da descrição) que não é o que a política pretende medir.
- **B — errada:** **over-engineering** — treinar um segundo classificador especializado em "linguagem de pagamento" adiciona uma camada de ML para compensar a primeira, quando o dado determinístico (caminho do arquivo) já está disponível sem inferência alguma.
- **C — errada:** **proxy plausível não confiável** — combinar dois sinais não-confiáveis (tom automatizado + autoavaliação do autor) não os torna confiáveis; nenhum dos dois mede o que realmente importa (quais arquivos mudaram).
- **D — correta.**

## Q6 — Resposta correta: **B** · (1.4)

Este é um item de **quebra de automatismo**: o reflexo do 1.4 é "garantia determinística pede hook/gate" (ver Q1/Q2). Mas aqui já existe uma garantia determinística equivalente — **100% dos relatórios passam por revisão humana obrigatória antes de publicar**, independentemente do que o subagente flagrar. Adicionar um segundo gate automatizado que bloqueia `publish_report` até confirmação manual citação-por-citação duplica um controle que já existe, sem ganho de confiabilidade correspondente, e ainda adiciona fricção a um fluxo que a revisão do editor já cobre. A resposta proporcional é sinalizar (via prompt) as citações de baixa confiança e deixar a revisão obrigatória já existente capturar o que passar.

- **A — errada:** **over-engineering** — é a escolha "padrão" do domínio, mas aplicada sem necessidade aqui: construir um gate determinístico redundante quando o controle determinístico equivalente (revisão obrigatória do editor) já está em produção é esforço extra sem ganho de garantia.
- **B — correta.**
- **C — errada:** **over-engineering** — um classificador de confiança para auto-aprovar citações adiciona uma camada de ML e de decisão automatizada exatamente onde a revisão humana mandatória já resolve o problema sem infraestrutura nova.
- **D — errada:** **proxy plausível não confiável** — pular o gate quando o subagente "se diz" confiante troca um controle observável (revisão de 100% dos relatórios) por um sinal auto-reportado, que é menos confiável, não mais.

### Conceitos reforçados
- Garantia determinística → hook `PreToolUse` com `deny`/`permissionDecision`, nunca só prompt/few-shot (falha não-nula).
- `HookMatcher` para tools de MCP server precisa do **nome totalmente qualificado** (`mcp__server__tool`); nome curto = no-op silencioso, não erro visível.
- Handoff estruturado (campos fixos: claim, fontes, causa, ação) para quem não vê o transcript — texto livre ou "leia tudo" não substitui isso.
- Um gate determinístico na forma ainda pode falhar se o **estado for mal-escopado** (global em vez de por entidade/`customer_id`).
- Escalar por sentimento/tom/confiança auto-reportada é proxy não-confiável; prefira um sinal determinístico ligado à condição real da política (ex.: arquivos alterados).
- Enforcement é proporcional: se já existe um controle determinístico equivalente (ex.: revisão humana obrigatória), duplicá-lo com outro gate automatizado é over-engineering, não segurança extra.
