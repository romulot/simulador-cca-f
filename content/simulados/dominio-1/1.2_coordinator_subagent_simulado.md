## Q1
In a Multi-Agent Research System (Scenario 3) building a competitive-landscape report, the customer's brief asks for five angles: pricing, product features, customer sentiment, go-to-market strategy, and partnership ecosystem. The coordinator's decomposition log shows it spawned exactly three subagents, scoped to "pricing-tier comparison," "feature-matrix comparison," and "customer-review sentiment." All three complete successfully — a manual audit confirms 100% of the facts in their outputs are accurate — and the synthesis subagent merges them into a coherent report. The customer rejects the deliverable: it never mentions go-to-market strategy or partnership ecosystem at all. What is the most likely root cause?

- **A)** The coordinator's task decomposition covered only three of the five angles the brief asked for, so no subagent was ever assigned the other two — the gap originates at the coordinator, not downstream.
- **B)** The customer-review sentiment subagent should have been instructed to flag, in its own output, whenever a requested topic falls outside the scope it was given.
- **C)** The synthesis subagent needs a stricter merge prompt so it notices when fewer than five topics are represented in the inputs it receives.
- **D)** The subagents' search tool returned too few sources on go-to-market strategy and partnerships, so those topics never surfaced in the retrieved data.

## Q2
In a Developer Productivity workflow (Scenario 4), a coordinator reviews a 40-file pull request and determines that `auth/session.py` — one of the 40 — touches token-expiry logic flagged as high-risk in a security postmortem three sprints ago. It then calls the `Task` tool to spawn a security-review subagent scoped to that one file. When the subagent's review comes back, it treats `session.py` as routine and never mentions the prior high-risk flag. What must the coordinator have done differently for that context to reach the subagent?

- **A)** Nothing extra should have been needed — the subagent automatically inherits the full conversation history of the coordinator's session the moment it is spawned via `Task`.
- **B)** The coordinator should rely on a shared memory store that every subagent polls before starting its own task.
- **C)** The subagent should message the coordinator directly, mid-task, over a subagent-to-coordinator channel to request any context it is missing.
- **D)** The coordinator should have included the "high-risk" flag and relevant detail explicitly in the prompt it passed when spawning the subagent, since subagents start with an isolated context and inherit nothing automatically.

## Q3
In a Customer Support Resolution Agent system (Scenario 1), roughly 70% of incoming tickets touch only one of three areas — billing, technical troubleshooting, or account security — while the rest span two or more. The team is designing the coordinator's dispatch logic for a hub-and-spoke architecture. Which design choice best reflects a well-built coordinator for this mix of tickets?

- **A)** Always invoke the billing, technical, and security subagents for every ticket, regardless of what the ticket is about, to guarantee nothing is missed.
- **B)** Analyze each ticket's content and dynamically invoke only the subagents relevant to it, with all inter-subagent communication routed through the coordinator.
- **C)** Let the technical-troubleshooting subagent forward the ticket directly to the security subagent whenever it detects an account-security angle, bypassing the coordinator.
- **D)** Give every subagent access to the billing, technical, and security tools so any subagent can resolve any ticket type on its own.

## Q4
For a single ticket about a duplicate charge and a missing refund, the coordinator delegates "summarize the customer's recent support history" to subagent 1 and "summarize the customer's recent account activity" to subagent 2. In production, the two subagents both query the same ticket-log and account-timeline tables and return outputs that overlap in 90% of their sentences, describing the same five interactions twice, because the two assignments were never defined as covering different data. What is the most appropriate coordinator-level fix?

- **A)** Increase both subagents' `max_tokens` so the duplicated content is less likely to be cut off mid-sentence.
- **B)** Have the two subagents compare their draft outputs with each other directly and negotiate, turn by turn, which one keeps which sentences before either one ever returns anything to the coordinator at all.
- **C)** Redefine the two delegated subtopics so each subagent is scoped to a distinct, non-overlapping slice of the ticket data before delegation (for example, interaction history vs. billing/account changes).
- **D)** Give subagent 1 access to both the ticket-log and account-timeline data sources so it alone decides what counts as "recent," leaving subagent 2's assignment unchanged.

## Q5
In a Developer Productivity workflow (Scenario 4), a coordinator is asked to validate a 12-line, single-function bug-fix diff before merge. Following its usual pattern for larger changes, it spawns a "test-runner" subagent and a separate "lint-checker" subagent, each starting a fresh isolated context, reading the diff, calling exactly one tool, and returning a one-line pass/fail. Median round-trip time for this diff is now 38 seconds, almost all of it subagent spin-up and context-loading rather than the checks themselves. What is the most appropriate fix?

- **A)** Add a third "aggregator" subagent whose only job is to combine the test-runner's and lint-checker's results into one summary for the coordinator.
- **B)** Force `tool_choice` on both subagents so each calls its checker tool on the very first turn, cutting a round of reasoning.
- **C)** Keep the two subagents but reduce their `max_tokens` so each returns its one-line verdict faster.
- **D)** Have the coordinator run the test suite and the linter itself, in its own turn, without spawning subagents at all — for a check this small, hub-and-spoke coordination overhead exceeds the benefit of delegating to separately-scoped subagents.

## Q6
In a Multi-Agent Research System (Scenario 3), the coordinator has five available subagents — web-search, code-execution, citation-checker, sentiment-analyzer, and summarizer — though a typical query only needs two or three. A retrospective found that in 20% of past reports, a relevant angle was missing because the coordinator's initial subagent selection for that query was too narrow (the same failure mode as an incomplete decomposition). The team is redesigning how the coordinator decides which subagents to invoke. Which approach best balances coverage and efficiency going forward?

- **A)** Always invoke all five subagents on every query, treating the extra latency and token cost as an acceptable fixed overhead so no angle is ever missed.
- **B)** Have the coordinator analyze the query upfront to select the subagents whose specialty matches the identified requirements, and invoke additional subagents afterward if the initial synthesis signals a coverage gap.
- **C)** Hard-code a fixed mapping from query category to subagent subset so the same categories always trigger the same subagents, updating the mapping only when a new category is discovered.
- **D)** Let the web-search subagent, once invoked, decide on its own which of the remaining four subagents to call based on what it finds, so that routing happens only after the first subagent's results are already in hand.
