## Q1 — Resposta correta: **C** · (1.6)

O workflow é **PREVISÍVEL**: 92% dos PRs passam pelos mesmos quatro aspectos, na mesma ordem, sempre. Isso é exatamente o caso de uso de **prompt chaining** — um pipeline sequencial fixo, com cada aspecto como um passo predefinido.

- **A — errada:** dinâmico caro para algo já previsível = **over-engineering** (§4.1): decidir em runtime o que já se sabe de antemão só adiciona custo e não-determinismo, sem ganho.
- **B — errada:** confiança auto-relatada pelo modelo para decidir o que pular é um **proxy plausível não confiável** (§4.4): nada garante que a confiança do modelo reflita se o aspecto realmente precisa ser revisado — pular segurança/testes com base nisso é arriscado.
- **C — correta.**
- **D — errada:** despejar tudo num prompt só, "não importa quão grande seja o diff", é o **equívoco de capacidade** (§4.6): a alternativa assume que uma única passada absorve qualquer tamanho de diff sem perda de qualidade — subestima que a atenção do modelo se dilui conforme o escopo do prompt cresce, mesmo quando o processo já é conhecido e poderia ser decomposto em passos limpos.

**Tópicos:** Decomposição de Tarefas

## Q2 — Resposta correta: **A** · (1.6)

PR grande (40 arquivos) revisado num prompt único produz achados rasos e inconsistentes — **attention dilution**: o escopo por passo é grande demais para o modelo manter atenção uniforme sobre tudo. A correção é decompor em **passe local por arquivo + passe de integração cross-file**, cada um com escopo pequeno e focado.

- **A — correta.**
- **B — errada:** "aumentar a janela de contexto e o limite de max-output resolve" é o **equívoco de capacidade** (§4.6) citado explicitamente no guia: mais espaço não resolve diluição de atenção, porque o problema não é falta de espaço, é excesso de escopo simultâneo por passo.
- **C — errada:** treinar um classificador de ML para prever quais arquivos são arriscados é **over-engineering** (§4.1): a decomposição em passes (sem coletar dados rotulados nem treinar/manter um modelo) já resolve o problema mais diretamente.
- **D — errada:** dar acesso Bash a um linter estático ataca a **camada/alvo errado** (§4.3): resolve disponibilidade de ferramenta, não a estrutura da decomposição da revisão — o prompt review continua decompostos do mesmo jeito (ruim).

- Cenário: S4 — Developer Productivity
- Princípio testado: revisão independente > auto-revisão (passe por arquivo + passe de integração)

## Q3 — Resposta correta: **D** · (1.6)

Tarefa **ABERTA/investigativa**: nem os dados relevantes nem os segmentos afetados são conhecidos de antemão — só aparecem conforme o agente explora. Isso pede **decomposição dinâmica adaptativa**: mapear → identificar sinais de alto impacto → plano priorizado que se adapta ao que é descoberto.

- **A — errada:** pipeline fixo com os mesmos passos, na mesma ordem, "independentemente do que os dados mostrarem" é o **erro-espelho do over-engineering: pipeline fixo/rígido para tarefa aberta** (o inverso do arquétipo 1 — não mapeia a um arquétipo §4 com nome próprio; é o mesmo tipo de erro em espelho, não um erro mecanístico à parte) — decompor de forma fixa uma tarefa cujo formato real só se revela durante a investigação.
- **B — errada:** treinar um classificador de ML para prever a causa raiz direto, pulando exploração, é **over-engineering** (§4.1): monta um pipeline de ML pesado (coleta, rotulagem, treino) para substituir a exploração agêntica, que já resolve isso com ferramentas de leitura/análise.
- **C — errada:** escrever o relatório completo sem consultar nenhuma fonte de dados é sintoma clássico de pular a decomposição inteiramente (não mapeia a um arquétipo §4 — erro mecanístico específico deste cenário: ausência total de exploração, não um dos sete padrões listados) — sem exploração, o relatório não tem grounding em evidência real.
- **D — correta.**

## Q4 — Resposta correta: **B** · (1.6)

O mismatch chamador/definição **cruza dois arquivos** (`pricing.py` define, `checkout.py` chama). Nenhum passe de arquivo isolado vê os dois lados ao mesmo tempo — só o **passe de integração cross-file** compara definição e chamada lado a lado.

- **A — errada:** afirma que os passes locais já são "totalmente suficientes" — é **camada/alvo errado** (§4.3): superestima o que o passe local (escopo por arquivo) é capaz de ver e nega a necessidade da camada certa para esse tipo de erro (a integração cross-file) — foi exatamente o que os passes locais não detectaram, pois cada um só viu metade do problema.
- **B — correta.**
- **C — errada:** descreve o passe de integração como "re-rodar cada arquivo isolado de novo" — é **equívoco de capacidade** (§4.6): assume que repetir o mesmo escopo local (arquivo por arquivo) adiciona alguma capacidade nova de detecção, quando na verdade inverte o mecanismo — o ganho da integração vem de olhar **através** dos arquivos, não de repetir o mesmo escopo local.
- **D — errada:** trata a integração como substituta dos passes locais — é **camada/alvo errado** (§4.3): confunde o alvo de cada camada (o passe local cobre estilo/segurança por arquivo; o cross-file cobre a interação entre arquivos) — ela **complementa**, não substitui (achados de estilo/segurança por arquivo continuam vindo do passe local; o cross-file é adicional).

## Q5 — Resposta correta: **A** · (1.6)

**Quebra-automatismo:** o candidato apressado reconhece "planejador dinâmico + workflow de suporte" e aplica de cabeça o rótulo "over-engineering" (o padrão da Q1/Q3-B). Mas aqui o dado muda o caso: em 78% dos 500 tickets a sequência de passos **realmente varia** por conta de atributos só descobertos ao examinar cada ticket. Isso é o retrato exato de uma tarefa cuja forma real é descoberta em runtime — decomposição dinâmica é a escolha correta, não over-engineering.

- **A — correta.**
- **B — errada:** aplica o rótulo "over-engineering" de forma automática e universal ("inerentemente... para qualquer workflow de atendimento"), ignorando o dado concreto de que os passos variam de fato em 78% dos casos — é a armadilha do quebra-automatismo (§10; não mapeia a um arquétipo §4 — o erro aqui não é escolher a técnica errada, é aplicar o rótulo certo de forma automática, ignorando a evidência do cenário): o distrator clássico da prova, aqui, é a resposta ERRADA.
- **C — errada:** confiança auto-relatada pelo agente sobre se o script fixo "cobriu corretamente" o ticket é um **proxy plausível não confiável** (§4.4) — não há garantia de que essa autoavaliação capture a variabilidade real descrita no enunciado.
- **D — errada:** treinar um classificador para prever, com antecedência, um script fixo por combinação tier×linha-de-produto é **over-engineering** (§4.1) — monta um pipeline de ML pesado e ainda assim volta a ser rígido por combinação, perdendo a granularidade por ticket que a decomposição dinâmica oferece de forma mais simples.

**Tópicos:** Decomposição de Tarefas

## Q6 — Resposta correta: **B** · (1.6)

`tool_choice` forçado para `decompose_plan` garante que a resposta do modelo venha como **saída estruturada validada** (a lista de subtarefas em JSON) — mas isso é só a etapa de **planejamento**. Forçar a tool_choice não executa nada; a **execução** de cada subtarefa continua exigindo que o coordenador a dispare separadamente (ex.: via `Task` tool).

- **A — errada:** assume que a chamada forçada também **executa** as subtarefas internamente — é um **equívoco de capacidade** (§4.6): confunde "produzir um plano estruturado" com "ter executado o plano". `tool_choice` forçado é saída estruturada, não execução.
- **B — correta.**
- **C — errada:** propõe eliminar o plano compartilhado e deixar cada subagente decidir por conta própria — é **camada/alvo errado** (§4.3): ataca o mecanismo errado, tratando a chamada forçada (a camada de planejamento estruturado) como se fosse dispensável, quando na verdade é ela que sustenta a coordenação — perde exatamente a garantia que a decomposição dinâmica com plano central oferece (evitar trabalho duplicado/conflitante entre subagentes).
- **D — errada:** troca a tool forçada por um prompt de texto livre pedindo para "listar as subtarefas" — é **probabilístico onde precisa ser determinístico** (§4.2): texto livre não garante um formato parseável; a tool forçada é o que dá a garantia estrutural que o pipeline downstream depende.
