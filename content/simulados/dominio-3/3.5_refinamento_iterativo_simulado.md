## Q1
A team uses Claude Code to generate data-normalization functions. Across the last 30 requests, 12 came back with the date field in the wrong format. The prompt describes the transformation in prose — `"normalize the dates"` — and the source data contains values such as `07/03/2024`, which admits a day/month reading and a month/day reading, both defensible. The rest of each generated function is correct, and the suite catches the mismatch only after the code is written. Which action is most effective at removing the inconsistency?

- **A)** Rewrite the prose description so that it specifies the required date handling precisely and leaves no room for a second reading.
- **B)** Add two or three concrete input → output examples to the prompt, including `07/03/2024` mapped to the expected ISO output.
- **C)** Add a date-format classifier ahead of the generation step, so it inspects the column and picks the reading first.
- **D)** Send the entire dataset with the prompt, so that a larger context lets Claude infer the intended date convention.

## Q2
A CI job asks Claude Code to fix an implementation until a 9-test suite passes. The job runs pytest, captures the exit code, and on failure replies with a single line: `"the tests are still failing, please fix"`. Each round continues the previous session with `--resume`, so the prior attempt stays in context. After 4 rounds the pass rate has not moved past 60%. The suite is stable and its assertions have been confirmed correct by two reviewers. What is the most likely root cause?

- **A)** Four rounds is too few for convergence; raising the loop's cap to ten rounds would let the fixes accumulate.
- **B)** This is single-run variance; run three instances each round and keep the fix that appears in at least two of them.
- **C)** The feedback carries no information; the raw pytest output — input, actual value, expected value — is what guides the fix.
- **D)** The 9-test suite is too large and dilutes the model's attention; splitting it into single-test CI jobs would fix the plateau.

## Q3
A generated migration script fails 5 of the suite's 9 tests, and review turns up three defects. Dates written with slashes, such as `07/03/2024`, come out read as month/day. When an id repeats, the record kept is the first one encountered rather than the most recent one. And the deduplication step rescans the whole accumulated list once per record, putting the 400,000-row job over its runtime budget. All three have to be fixed before the migration runs. How should the fix be requested?

- **A)** All three in a single detailed message, because two of the three share the same deduplication line, and the third produces the data that line reads.
- **B)** One defect per message, from the simplest to the hardest, so that each regression can be isolated before the next fix lands.
- **C)** Ask three independent instances in parallel, one defect each, then merge the three resulting diffs into the script.
- **D)** Write the precedence rule into `./CLAUDE.md` and then ask for a single generic corrective pass over the script.

## Q4
A developer productivity tool generates boilerplate for new service modules. Review of one batch flags 6 issues in 6 different files: an import named against convention, a missing docstring, a log line with no request context, and three comparable one-line items. None of the six touches shared code or a shared decision. After an earlier incident with three interlocking defects, the team adopted a standing rule: always send every issue in a single message. Which approach is best for this batch?

- **A)** Send all six in one message, as the team's standing rule requires, since fewer round-trips means less cost per batch.
- **B)** Build a coordinator agent that spawns one subagent per file with the `Task` tool and merges the six results.
- **C)** Have the model report a confidence score for each of the six fixes and review only those it reports as low.
- **D)** Fix them sequentially, one request per file — these problems are independent, not interacting ones.

## Q5
An engineer must add cache invalidation to a legacy service he has never worked on. Two earlier attempts were thrown away: in both, decisions nobody had raised surfaced only after the code existed — the invalidation policy, and the behavior on partial failure. About 40% of the second attempt's diff had to be rewritten once those two questions were finally answered. He is about to start the third attempt. What is the most effective next step?

- **A)** Ask for the implementation and, at the end, ask for a written list of the decisions it made along the way.
- **B)** Ask Claude to interview him — the questions it needs answered before writing code — then implement.
- **C)** Enter plan mode, review and approve the plan Claude proposes, and only then let it implement the change.
- **D)** Ask for three alternative implementations of the change and pick the best of them after a comparison.

## Q6
A CI pipeline generates migration scripts. In 8% of runs, null values in the date column come out as the string `"None"` instead of a null. Two corrections have already shipped, both refining the prompt wording, and the defect reappeared in the batch after each one. The 9-test suite passes on every run: none of its cases exercises a null date. Which action is most effective at stopping the recurrence?

- **A)** Add `"be careful with null values"` to the project's `./CLAUDE.md`, so that every run carries the warning.
- **B)** Run the CI job with `claude --strict-nulls`, so null values are preserved end to end.
- **C)** Add a test case with the exact null input and the expected null output, then iterate on that failure.
- **D)** Add a second review pass in which the model checks its own output for null handling.
