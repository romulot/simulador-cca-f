## Q1
In a monorepo, test files live scattered across `packages/web/`, `apps/admin/`, and other packages, each following the same mocking convention. A recent audit found that 18 of 40 new test files across three different packages did not follow this convention, because it currently lives only in each engineer's head. The team wants the convention to surface automatically whenever Claude reads or writes any `*.test.tsx` file, anywhere in the repo, without adding to the baseline context of sessions that never touch a test file. Which configuration achieves this?

- **A)** Add a `CLAUDE.md` file under every package that currently contains test files (`packages/web/CLAUDE.md`, `apps/admin/CLAUDE.md`, and so on), each repeating the exact same mocking-convention paragraph verbatim, with a plan to add another such file the next time a new package is created.
- **B)** Add a rule at `.claude/rules/testing.md` with `paths: ["**/*.test.tsx"]`, so the convention loads only when Claude reads or edits a matching file, in any package.
- **C)** Move the mocking convention into the root `./CLAUDE.md`, so it is present in every session's starting context from the very first message, whether or not a test file is ever touched that session.
- **D)** Add a rule with `paths: "*.test.tsx"` (no `**`) at the repo root, expecting it to activate for any test file the team writes, at any nesting depth or package.

## Q2
A team is splitting up a 900-line root `./CLAUDE.md`. One section documents Terraform conventions relevant only to `infra/**`; a review of the last 50 sessions shows `infra/**` files were touched in only 6 of them, yet that section alone added roughly 1,400 tokens to every session's starting context before the split. An engineer proposes moving the Terraform section into `.claude/rules/terraform.md` with `paths: ["infra/**"]`. Which statement correctly explains why this reduces average context usage compared to leaving it in `./CLAUDE.md`?

- **A)** It doesn't really change anything: a rule under `.claude/rules/` still loads at the start of every session exactly like `./CLAUDE.md` does, regardless of whether it declares `paths:` or not; the whole split is purely cosmetic file reorganization with no effect on what actually ends up in context at session start, so the 1,400-token cost is still paid by every one of the 50 sessions either way.
- **B)** The real fix is to keep the section in `./CLAUDE.md` and run `/compact` at the end of every session, which purges the Terraform tokens from the transcript before the next session starts.
- **C)** Moving the rule to `~/.claude/rules/` (user scope) instead of the project would guarantee it only loads for the engineers who actually work on `infra/**`.
- **D)** A rule with `paths: ["infra/**"]` only enters context when Claude reads or edits a file under `infra/**`; the 44 sessions that never touch that path never pay the token cost, unlike content with no `paths:`.

## Q3
A CI-integrated pipeline has an `api-conventions.md` rule with `paths: "*.service.ts"` (the comma-separated string form), intended to surface the team's error-handling convention for every `*.service.ts` file in the monorepo. Over the last 15 PRs that touched nested service files such as `packages/api/user.service.ts`, the convention was silently absent from context in 9 of them, even though the rule file exists, is committed, and no one edited it recently. What is the most likely root cause?

- **A)** `*.service.ts` only matches within a single path segment, so it never matches a nested path like `packages/api/user.service.ts`; the fix is `**/*.service.ts`.
- **B)** Claude's instruction-following degrades over the course of a longer PR-review session, making it progressively more likely to disregard a convention it saw earlier in the same session — a pattern consistent with the convention going missing in roughly 60% of the recent PRs rather than 100% of them.
- **C)** A teammate's personal rule at `~/.claude/rules/` declares a conflicting glob for the exact same convention name, and per the documented scope precedence, user scope is silently overriding project scope's activation in those 9 specific PRs.
- **D)** The organization has a managed, org-wide policy layer for `.claude/rules/` that only partially activates project-scope rules until a platform admin formally reviews and approves each one, similar to the managed `CLAUDE.md` scope.

## Q4
A team enforces its `*.test.tsx` mocking convention by keeping a copy of the same paragraph in a `CLAUDE.md` file under each package that has tests: `packages/web/CLAUDE.md` and `apps/admin/CLAUDE.md`. Last month, a third package, `apps/mobile/`, was added; all 6 test files written there since are missing the convention, while the two older packages remain fine. What is the root cause, and what change actually prevents this from recurring the next time a package is added?

- **A)** Add a fourth `CLAUDE.md` file under `apps/mobile/` with the same paragraph, matching what was done for the first two packages.
- **B)** Trust that Claude will apply the convention to `apps/mobile/` on its own initiative going forward, since it has already seen the same paragraph in two sibling packages.
- **C)** Replace the per-package `CLAUDE.md` copies with a single path-rule, e.g. `paths: ["**/*.test.tsx"]`, so the convention is scoped to the file type it actually targets and any new package inherits it automatically.
- **D)** Move the convention into a `~/.claude/rules/` file in each affected developer's home directory, so it "follows" them into whichever package they happen to be working in.

## Q5
A project has three pieces of guidance to place: (1) "every commit message must reference a ticket ID," which applies to literally every commit regardless of file type; (2) "every `*.graphql` file must start with an owner-team comment," relevant only to GraphQL files scattered across several services; (3) a deprecated error-wrapping pattern used only inside `services/billing-legacy/` and nowhere else. An engineer proposes putting all three into one `.claude/rules/all-conventions.md` with `paths: ["**"]`, arguing path-scoped rules are "the more modern mechanism" and should replace `./CLAUDE.md` wherever possible. What is the best split?

- **A)** Follow the proposal: `paths: ["**"]` matches every file anyway, so consolidating all three conventions into one path-rule centralizes guidance without losing anything, and it still counts as a "path-scoped rule" on paper even though nothing about its matching behavior differs from a plain global rule with no `paths:` at all.
- **B)** Split by spread pattern: the commit-message rule goes into a global rule or `./CLAUDE.md` (no `paths:`); the `*.graphql` rule becomes a path-rule with `paths: ["**/*.graphql"]`; the billing-legacy pattern becomes a subdirectory `CLAUDE.md` under `services/billing-legacy/`.
- **C)** Register all three as resources inside `.mcp.json`, since that file already governs what gets loaded into Claude Code's context, and MCP resources are meant precisely for this kind of shared team guidance.
- **D)** Write a small script that scans the codebase at the start of each session and dynamically decides which of the three convention texts to inject that session, replacing native `paths:` scoping with custom logic maintained by the platform team.

## Q6
A CI team wants a rule's Terraform-review convention to apply to every `*.ts` file except generated code, so an engineer writes `paths: ["**/*.ts", "!**/*.generated.ts"]` in `.claude/rules/no-generated.md`, expecting the second pattern to exclude `*.generated.ts` from activating the rule, the same way a `.gitignore` line would. A week later, the convention is still showing up in context when Claude edits `output/schema.generated.ts`. What should the team conclude, and what actually fixes it?

- **A)** Trust the current configuration: since Claude Code rules generally mirror `.gitignore` semantics, `!**/*.generated.ts` should already be excluding those files, so the recurrence must be an unrelated caching issue.
- **B)** Rewrite `no-generated.md` as a skill instead of a rule, keeping the same two-pattern `paths` list, since a skill's `paths` field is documented to support `!` exclusion where a rule's does not.
- **C)** Keep the two-pattern `paths` list as a best-effort signal, and add a line to the rule body asking the model to "please skip this convention for any file that looks auto-generated."
- **D)** Recognize that `!` negation isn't part of this `paths:` glob format, so the second pattern is inert and every `*.ts` file, generated or not, still matches the first one; instead, scope the positive glob to only the tree that needs the convention (e.g. `paths: ["src/**/*.ts"]`) while keeping generated output under its own directory, such as `output/generated/**`, entirely outside that glob.
