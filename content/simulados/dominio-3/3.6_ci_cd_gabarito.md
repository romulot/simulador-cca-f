**Tópico:** CI/CD com Claude Code — `structured_output` via `--json-schema`, reprodutibilidade com `--bare` + `--append-system-prompt-file`, desfecho do run como parte do contrato do gate, revisão independente × sessão continuada
Explicações em PT-BR. Todas as questões exercitam o **TS 3.6**.

## Q1 — Resposta correta: **C** · (3.6)

O enunciado entrega os dois lados do contrato quebrado: o `jq` lê `.structured_output.findings` e os achados estão, em prosa, no campo `result`. É exatamente a divisão de campos do print mode: `--output-format json` devolve o envelope do run (com `result` carregando o **texto** do modelo), e é `--json-schema` que faz a saída ser **validada contra o schema** e colocada no campo `structured_output`. Sem `--json-schema`, `structured_output` simplesmente não existe — e `jq` sobre um campo ausente devolve `null`, que é o sintoma relatado. A correção é declarar o schema dos achados (arquivo, linha, severidade) e passá-lo com `--json-schema` junto do `--output-format json` que já está lá: um argumento a mais transforma "pedi JSON no prompt" em "a plataforma valida antes de me devolver".

- **A — errada:** regex sobre `.result` aceita a prosa como formato de integração permanente. Funciona no exemplo que o autor testou e quebra na primeira variação de redação do modelo — que é livre por construção, porque nada valida esse campo. Além disso ataca a camada de consumo (o parser do pipeline) quando o defeito está na camada de produção (o run não foi instruído a emitir saída estruturada), e a garantia de forma existe e está a uma flag de distância (arquétipo §4: **camada/alvo errado**).
- **B — errada:** `"reply with JSON only, no text around it"` é enforcement por prompt para um requisito de forma. Mesmo que o modelo obedeça, `result` passa a conter uma string que *parece* JSON e `structured_output` **continua inexistente** — o `jq` do enunciado segue devolvendo `null`, porque ele lê o campo validado, não o texto. E na execução em que o modelo cercar o JSON com uma frase de cortesia, o pipeline quebra sem aviso (arquétipo §4: **probabilístico onde precisa ser determinístico**).
- **C — correta.**
- **D — errada:** `--strict-json` não existe. Soa plausível porque o CLI real tem `-p`/`--print`, `--output-format json` e `--json-schema`, e "strict" é vocabulário comum de validação. Note o que aconteceria ao adotar esta alternativa: flag inválida é reportada em **stderr antes de o run começar**, então o resultado não é uma review degradada — é um job que **não roda**. Trocar "nenhum comentário postado" por "nenhuma review executada" não é correção (arquétipo §4: **feature inexistente porém verossímil**).

## Q2 — Resposta correta: **A** · (3.6)

`--bare` faz exatamente o que o time queria: pula o auto-discovery de hooks, skills, plugins, MCP servers, auto memory **e do `CLAUDE.md`** — é o modo recomendado para CI justamente quando se precisa do mesmo resultado em toda máquina. O efeito colateral relatado é a consequência direta disso: os critérios de review do time viviam no `CLAUDE.md`, e o `CLAUDE.md` deixou de ser carregado. O caminho previsto para devolver contexto sem desfazer o isolamento é injetá-lo **explicitamente** no system prompt: `--append-system-prompt-file CLAUDE.md` (ou `--append-system-prompt` com o texto). O ganho conceitual é que o contexto passa a ser um argumento versionado da invocação, não algo que o ambiente do runner descobre — que é a definição de reprodutível.

- **A — correta.**
- **B — errada:** é o quase-certo da questão, e resolve o sintoma pelo preço do requisito. Remover `--bare` reativa o auto-discovery inteiro: junto com o `CLAUDE.md` voltam hooks, skills, plugins, MCP servers e auto memory presentes naquele runner — ou seja, volta a variar de máquina para máquina, que é precisamente o problema que motivou o `--bare`. Trocar a propriedade que se queria garantir para recuperar um insumo que se pode passar por argumento é agir na camada errada (arquétipo §4: **camada/alvo errado**).
- **C — errada:** `--claude-md` não existe. É verossímil porque o arquivo se chama assim e porque o CLI real tem flags de arquivo (`--append-system-prompt-file`, `--settings`); mas não há flag que "recarregue a memória" contornando o `--bare`. Uma flag inválida é reportada em stderr antes de o run começar, então isso não é um ajuste sutil — é um job que não roda (arquétipo §4: **feature inexistente porém verossímil**).
- **D — errada:** instruir "leia o `CLAUDE.md` antes de revisar" troca contexto garantido por um pedido que depende do modelo decidir ler, de o Read estar disponível no run e de o arquivo estar onde a instrução diz. Como enforcement de "os critérios do time estão sempre presentes", é probabilístico onde o requisito é determinístico — e consome turnos e tokens para obter o que uma flag entrega antes do primeiro turno (arquétipo §4: **probabilístico onde precisa ser determinístico**).

## Q3 — Resposta correta: **D** · (3.6)

O enunciado dá três observações e não declara o acoplamento entre elas; o trabalho é relacioná-las. O diff é `base...HEAD`, então cada re-execução revisa **de novo** todo o intervalo e reencontra legitimamente os mesmos defeitos — reencontrar não é o bug. O prompt já pede "só o que é novo ou segue aberto", e ainda assim 4 comentários idênticos foram postados: isso é a medida de que a instrução em prosa **não é garantia**. E o requisito é absoluto ("nunca postar duas vezes"), o que o classifica como caso de enforcement determinístico. A resposta é deduplicar por fingerprint no gate — comparar o achado com o que já está postado naquele PR e não postar o repetido — mantendo a instrução do prompt, que continua útil como redutor de ruído e de custo. É o contraste que 1.4/1.5 já cobravam: quando o requisito é uma garantia, ela vive no código do gate (hook/gate determinístico), e o prompt fica como otimização, não como mecanismo.

- **A — errada:** mais exemplos de achado já reportado reforçam o mesmo mecanismo que já falhou de forma observada. Few-shot melhora a taxa; não produz a garantia que o requisito pede, e a próxima execução pode repetir o comentário sem nenhum sinal de que repetiu (arquétipo §4: **probabilístico onde precisa ser determinístico**).
- **B — errada:** revisar só o diff incremental entre os dois commits novos reduz a duplicata como efeito colateral e paga com cobertura: um blocker introduzido antes desses commits e ainda aberto deixa de ser reportado, exatamente o caso que a instrução do prompt existia para preservar. Trocar o escopo da revisão para consertar a idempotência da **postagem** é atuar na camada errada — o problema não é o que se revisa, é o que se publica (arquétipo §4: **camada/alvo errado**).
- **C — errada:** duas execuções e postar só a interseção descarta o achado real que apenas uma delas viu — suprime sinal para comprar consistência aparente. Pior: não endereça o requisito, porque a duplicata do enunciado é **entre execuções do gate em momentos diferentes**, e a interseção de duas execuções simultâneas não sabe nada do que foi postado ontem. Custa o dobro e o defeito permanece (arquétipo §4: **voto/consenso que suprime sinal**).
- **D — correta.**

## Q4 — Resposta correta: **B** · (3.6)

O gerador e o revisor são a mesma sessão: via `--resume`, a instância que revisa herda todo o raciocínio que produziu o código, inclusive a interpretação que transformou um campo opcional em obrigatório. Ela não vê divergência porque, do ponto de vista do contexto dela, o código implementa a decisão que ela mesma tomou — 18 "no issues found" em 20 é a assinatura desse viés, não uma medida de qualidade. A correção é estrutural: rodar a revisão como **instância independente**, cujo único contexto é o requisito e o diff. Assim a comparação é feita entre os dois artefatos, sem a memória de por que o código ficou daquele jeito, e a leitura "opcional" do requisito volta a ser possível. É o princípio de **revisão independente > auto-revisão**. Vale o contraste com o 3.5, onde `--resume` era a resposta **certa**: lá se iterava na *mesma* tarefa e a continuidade do contexto era o ativo (devolver a falha real do teste sem reconstruir o histórico); aqui se quer um revisor sem compromisso com a decisão tomada, e a mesma continuidade é o passivo. O mecanismo não é bom nem ruim por si — depende de a continuidade ajudar ou contaminar.

- **A — errada:** `--max-turns` é um teto de turnos agênticos e, ao ser atingido, o run **sai com erro** — não é um controle de contexto nem de rigor. E reenviar o requisito inteiro na sessão retomada não remove nada: o contexto anterior continua ali, com a interpretação original, e passa a competir com a nova cópia. Supõe que o obstáculo é espaço/oportunidade quando é comprometimento com uma decisão já tomada (arquétipo §4: **equívoco de capacidade**).
- **B — correta.**
- **C — errada:** "seja crítico com o próprio trabalho e assuma que há bugs" é instrução de postura, não critério. Ela não informa **o que** comparar nem desfaz a premissa herdada — a instância continua achando que "obrigatório" era o entendimento correto, e agora procura bugs *dentro* dessa premissa. Mesmo cumprida com afinco, não é garantia de nada (arquétipo §4: **probabilístico onde precisa ser determinístico**).
- **D — errada:** é o quase-certo, e a razão de errar é o detalhe que o 1.7 fixa: `--fork-session` existe, mas o fork **herda o contexto** da sessão de origem — ele ramifica a partir dela, criando um histórico separado dali para frente. Isso resolve poluir a sessão geradora com a conversa de revisão; não resolve o viés, porque a interpretação do requisito veio *antes* do ponto de bifurcação e viaja com o fork. Mecanismo real, aplicado ao problema errado (arquétipo §4: **camada/alvo errado**).

**Tópicos:** CI/CD

- Cenário: S2 — Code Generation with Claude Code

## Q5 — Resposta correta: **A** · (3.6)

O gate confundiu duas coisas diferentes: "a review rodou e não achou blocker" e "a review não rodou de verdade". O log mostra `subtype: "success"` **sem** `structured_output`, e a doc é explícita em tratar esse caso como **falha** — sucesso no envelope do run não é o mesmo que saída validada disponível. O comment builder, ao ler um array ausente como array vazio, converteu ausência de informação em veredito de aprovação, e um PR foi para produção com bug de autenticação por causa dessa conversão. A resposta é fazer o **desfecho do run** parte do contrato do gate: `subtype` de erro (por exemplo `error_max_structured_output_retries`), ou sucesso sem `structured_output`, falham o gate com **exit code próprio**, distinto do exit code de "achou blocker". Duas ideias que o lab já cobrava se encontram aqui: o erro estruturado do 2.2 (categoria/retriabilidade explícitas em vez de string genérica) e a propagação de erro do 5.3 (a falha do passo de baixo tem de chegar ao decisor como falha, e não virar resultado neutro).

- **A — correta.**
- **B — errada:** avisa e libera, tratando "não vieram achados" como evidência de que não há defeito. É proxy inválido: o que houve foi ausência de **review**, não ausência de **defeito**, e usar um como leitura do outro é exatamente o que produziu o incidente descrito. Um aviso em comentário também não é enforcement — ninguém é obrigado a ler (arquétipo §4: **proxy plausível não confiável**).
- **C — errada:** o erro está em classificar a falha como transitória. Retry é a resposta certa para o que o 2.2 marca como `isRetryable: true` — timeout, indisponibilidade momentânea, algo que a mesma chamada resolve ao repetir. Uma review que terminou sem `structured_output` não está nessa categoria: o run completou e não produziu a saída validada, o que aponta para prompt, schema ou esgotamento de retries de estruturação (`error_max_structured_output_retries`) — repetir não muda a causa. E o critério de saída piora o defeito: "libera assim que **alguma** das três devolver zero" seleciona sistematicamente a execução mais permissiva, então basta uma tentativa degradada para o PR passar, e o esquema converte instabilidade em aprovação (arquétipo: **erro tratado como transitório / proxy de tentativa aprovada** — retry aplicado a falha não-retriável, tomando "a tentativa que passou" como proxy do veredito. É vizinho do §4-4, mas não colide com B: B é *política sobre uma falha já conhecida* — sabe que a review falhou e decide liberar —, enquanto C é *estratégia de recuperação* — tenta apagar a falha repetindo-a).
- **D — errada:** `required` no JSON Schema fala de **presença de propriedade** no objeto, não de conteúdo: um array de achados presente e vazio satisfaz `required`. E array vazio é resultado **válido** — PR sem blocker existe (2.2: resultado vazio válido ≠ erro), então tentar proibi-lo é proibir a resposta certa. Sobretudo: nenhuma alteração de schema faz o `structured_output` existir num run que não o produziu, que é o defeito real. Vale lembrar que schemas são validados em **draft-07** e que `format` entra como anotação, **não** é enforced — schema não é o lugar de garantir semântica de negócio (arquétipo §4: **equívoco de capacidade**).

## Q6 — Resposta correta: **C** · (3.6)

Este é o quebra-automatismo do tópico: aqui o `CLAUDE.md` é a **resposta correta**, e não o distrator "instrução em prosa onde falta garantia". A diferença está no que se escreve nele. Os três sintomas apontam para a mesma lacuna, e ela é de **informação**, não de disciplina: o job não sabe quais cenários a suíte já cobre (por isso 9 de 12 repetem), não sabe que existem fixtures compartilhadas em `conftest.py` (por isso monta setup à mão) e não tem definição de "teste que vale revisar" (por isso enche o PR). Documentar os fixtures disponíveis, os padrões de teste do projeto e o critério de valor — e colocar os arquivos de teste existentes no contexto do run — fornece justamente aquilo cuja falta produz cada sintoma. É a resposta proporcional atacando a causa raiz: nenhuma camada nova, e a convenção passa a ser insumo versionado. Nota de integração operacional com a Q2: se este job rodar com `--bare`, o `CLAUDE.md` **não** é auto-descoberto, e esse conteúdo tem de entrar via `--append-system-prompt-file`.

- **A — errada:** um segundo passe que pontua e descarta é uma camada de julgamento construída sobre a mesma lacuna de informação. O avaliador também não sabe o que a suíte cobre nem quais fixtures existem, então pontua "valor" contra um critério que ninguém escreveu — e o resultado provável é filtrar 12 testes ruins até restarem 3 testes ruins. Infraestrutura e custo por run a mais para um problema que informar o gerador resolve (arquétipo §4: **over-engineering**).
- **B — errada:** "escreva apenas testes de alto valor e não duplique cenário existente" é adjetivo sem critério — o análogo direto do "seja conservador" do 4.1, que não melhora precisão porque não diz *como* decidir. Note que esta alternativa até menciona os três pontos certos, inclusive reusar os fixtures compartilhados, e ainda assim não pode funcionar: cada um dos três pede uma informação que o run não tem — quais cenários a suíte cobre, quais fixtures existem e onde, e o que o projeto considera valor. Instrução mais enfática sobre informação ausente pede um comportamento cuja pré-condição não foi satisfeita (arquétipo §4: **probabilístico onde precisa ser determinístico**).
- **C — correta.**
- **D — errada:** `--tools` é de fato a flag que **restringe** quais tools existem no run (≠ `--allowedTools`, que apenas **pré-aprova** as que já existem), então o mecanismo está correto — e é isso que torna o distrator atraente. Só que remover o Write muda o **formato de entrega**, não a qualidade: os 9 testes redundantes continuam sendo propostos, agora em prosa, e o humano passa a digitá-los. O custo de revisão que fez o time fechar os PRs sem ler aumenta em vez de cair (arquétipo §4: **camada/alvo errado**).
