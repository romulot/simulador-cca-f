## Q1 — Resposta correta: **B** · (3.1)

O problema é de **escopo de memória**: `~/.claude/CLAUDE.md` é memória de **usuário**
— pessoal, não versionada, não vai para o git e portanto não chega às máquinas dos
outros 3 engenheiros. A convenção de time pertence ao `./CLAUDE.md` do **projeto**,
commitado no repo: qualquer pessoa que clonar o repo passa a carregar a mesma
memória automaticamente, sem passo manual por máquina.

- **A — errada:** ainda é memória de **usuário** em cada máquina — não resolve a
  causa (falta de compartilhamento via git), só empurra o mesmo problema para o
  próximo engenheiro que entrar no time (arquétipo §4: **camada/alvo errado** —
  continua escrevendo na camada errada em vez de mover para o escopo compartilhado).
- **B — correta.**
- **C — errada:** construir um serviço de sincronização de arquivo pessoal quando
  o mecanismo de compartilhamento já existe de graça (`git commit` no `./CLAUDE.md`
  do projeto) é **over-engineering** (arquétipo §4).
- **D — errada:** enforcement por **prompt manual repetido** (colar a cada sessão)
  em vez de corrigir a configuração — depende de disciplina humana, não escala e
  não é determinístico (arquétipo §4: **probabilístico onde precisa ser
  determinístico**).

## Q2 — Resposta correta: **A** · (3.1)

As camadas de memória (managed, user, project, subdirectory) são **concatenadas**
no contexto — não existe "última que sobrescreve as outras". Além disso, a camada
**managed** (`/etc/claude-code/CLAUDE.md`) é projetada para ser **não-sobrescrevível**
por camadas mais baixas — é por isso que a linha contraditória no `./CLAUDE.md` do
projeto não muda o comportamento: as duas instruções coexistem no contexto, e a
política managed prevalece por design, não por ordem de carregamento.

- **A — correta.**
- **B — errada:** é o erro clássico "**root sobrescreve tudo**" — mistura o modelo
  de concatenação de memória com um modelo de override que não existe aqui
  (arquétipo §4: **equívoco de capacidade** — modelo mental errado de como as
  camadas combinam).
- **C — errada:** é o erro clássico "**último-vence**", típico de quem confunde a
  concatenação de CLAUDE.md com a precedência de escopo de MCP servers (TS 2.4),
  que aí sim é `local > project > user` **sem merge** — memória de CLAUDE.md
  **concatena**, não faz last-writer-wins (arquétipo §4: **equívoco de
  capacidade**).
- **D — errada:** confunde mecanismos — `paths:` é frontmatter de
  **`.claude/rules/`** (escopo por glob de arquivo em foco), não um controle de
  precedência entre CLAUDE.md de projeto e a política managed (arquétipo §4:
  **camada/alvo errado** — aplica um mecanismo real ao alvo errado).

## Q3 — Resposta correta: **C** · (3.1)

Sim, é o comportamento esperado: CLAUDE.md de **subdiretório** carrega **sob
demanda** — só entra no contexto quando Claude efetivamente lê ou edita um arquivo
dentro daquela subárvore. Por isso `packages/api/CLAUDE.md` fica ausente enquanto
a sessão só toca `packages/web`, e aparece assim que um arquivo de `packages/api`
é aberto, no mesmo turno.

- **A — errada:** carregar todo CLAUDE.md de subdiretório no lançamento da sessão
  inverteria a economia de contexto que o carregamento sob demanda existe para dar

  à toa) — trata o mecanismo real como se fosse um bug (arquétipo §4: **equívoco
  de capacidade**).

  depende de um `@import` no root; funciona pela simples localização do arquivo

  atribui o efeito a um mecanismo diferente do que de fato atua).
- **C — correta.**
- **D — errada:** não existe necessidade de registrar o arquivo em
  `.claude/settings.json` para o carregamento sob demanda funcionar — é uma

## Q4 — Resposta correta: **D** · (3.1)

Dois fatos de `@import`: (1) caminhos relativos resolvem em relação ao **arquivo
que faz o import**, não ao cwd de lançamento — por isso mover o repo para outro
caminho absoluto não quebra nada, já que as referências são todas relativas entre
os próprios arquivos; (2) a cadeia tem um **teto de 4 hops** — o 5º arquivo da
cadeia nunca é carregado porque o limite foi excedido, não por erro de digitação.

- **A — errada:** inverte o mecanismo — se a resolução fosse relativa ao cwd de
  lançamento, mover o repo para outro caminho absoluto **teria** quebrado a
  cadeia; o enunciado diz que nada muda, o que só faz sentido com resolução
  relativa ao arquivo importador (arquétipo §4: **camada/alvo errado** — atribui
  a resolução ao alvo errado, cwd em vez do arquivo).
- **B — errada:** "sem limite de hops" é falso — existe teto de 4; é exatamente
  esse teto que explica o 5º arquivo faltando, não um typo (arquétipo §4:
  **equívoco de capacidade** — crença errada sobre um limite real do mecanismo).
- **C — errada:** falso — `@import` aceita caminhos relativos (o caso comum,

  teriam falhado, contradizendo o enunciado (arquétipo §4: **equívoco de

## Q5 — Resposta correta: **C** · (3.1)

Rule com `paths:` é **path-scoped**: só entra no contexto quando um arquivo em
foco casa com o glob. `services/api/**` não casa com
`services/api-gateway/handlers.py` (são diretórios-irmãos diferentes,
`api` ≠ `api-gateway`) — por isso a rule nunca carrega para esse arquivo. A
correção é ajustar o glob (`services/api-gateway/**` ou um padrão mais amplo como
`services/api*/**`) para de fato cobrir o diretório pretendido.

- **A — errada:** copiar a convenção para o system prompt é enforcement por
  **prompt manual** — contorna a causa raiz (glob errado) em vez de corrigi-la, e
  não escala para outras rules com o mesmo tipo de erro (arquétipo §4:
  **probabilístico onde precisa ser determinístico**).
- **B — errada:** criar um hook que reescreve respostas depois do fato é mais
  complexo e mais tardio (reativo) do que simplesmente consertar um glob que já
  deveria ter funcionado de forma determinística antes (arquétipo §4:
  **over-engineering**).
- **C — correta.**
- **D — errada:** remover o `paths:` e confiar que Claude "vai lembrar" da
  convenção troca configuração determinística por um sinal que não é confiável —
  memória implícita de conversa (arquétipo §4: **proxy plausível não confiável**).

## Q6 — Resposta correta: **A** · (3.1) — quebra-automatismo

Aqui o "certo" é justamente **modularizar**: dividir o CLAUDE.md de 900 linhas em
arquivos `.claude/rules/*.md` com `paths:` (ex.: regras de teste só entram quando o
arquivo em foco está em `tests/**`), usando `@import` no root apenas para o que é
de fato transversal. Isso resolve os dois sintomas relatados: regras de deploy
"vazando" para edição de testes (porque hoje tudo está sempre no contexto,
misturado) e fadiga de onboarding (ninguém lê 900 linhas de uma vez). É um
quebra-automatismo: modularizar aqui não é over-engineering, é a correção
determinística e proporcional ao problema.

- **A — correta.**
- **B — errada:** é o erro clássico "**monolito por determinismo**" — manter tudo
  junto não é mais determinístico, é só mais ruído sempre presente; scoping por
  `paths:` é tão determinístico quanto (o glob roda sempre, sem depender do
  modelo) e ainda reduz o que é irrelevante em cada turno (arquétipo §4:
  **equívoco de capacidade**).
- **C — errada:** um classificador dinâmico decidindo qual seção usar é
  exatamente o tipo de peça extra que a prova pune quando ajustar a
  config/estrutura de arquivo já resolve (arquétipo §4: **over-engineering**).
- **D — errada:** mover o conteúdo para o system prompt não resolve a
  modularidade nem a relevância por tipo de arquivo — continua sendo um bloco
  monolítico sempre presente, só que em outro lugar; não corta o "vazamento" de
  regras de deploy para testes (arquétipo §4: **camada/alvo errado** — muda o
  contêiner, não a estrutura que causa o problema).
