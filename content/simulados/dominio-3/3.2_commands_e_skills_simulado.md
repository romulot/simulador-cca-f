## Q1
In a 200-person engineering org, the shared `analyze-codebase` skill is invoked automatically by Claude whenever a developer asks a broad architecture question, and it produces a structural report — dependency graphs, package summaries, per-file notes — that used to run inline and land directly in the main conversation. Over the last two weeks, three developers reported that after invoking it once, Claude started losing track of earlier turns only 4-5 exchanges later in the same session. The team still wants the skill to run automatically whenever it's relevant, but wants only a short synthesized takeaway to land in the main conversation, not the full multi-page scan. Which configuration change accomplishes this?

- **A)** Have the developer run `/branch` (or call `fork_session=True` in the Agent SDK) before invoking the skill, forking the entire conversation into a new session for the scan.
- **B)** Turn the scan into a dedicated custom subagent invoked via the Task tool, built solely to run this one report and nothing else.
- **C)** Add `context: fork` to the skill's frontmatter, so the skill's execution runs in an isolated sub-agent and only a summary is returned to the main conversation.
- **D)** Add a line to the skill body asking the model to "keep the report brief and summarize concisely before responding."

## Q2
A team's `/deploy` command expects a target environment and version as its first two positional arguments; roughly 30% of invocations by newly onboarded engineers omit both, because they don't yet know an argument is expected, and the command body expands `$0` and `$1` as empty strings before failing several steps later with a confusing error. The team doesn't want to reject or validate the missing argument programmatically — they just want the `/` autocomplete menu to visibly show the expected shape (e.g. `<environment> <version>`) before the engineer finishes typing, so the mistake is caught before Enter is pressed. Which frontmatter field achieves exactly this, and only this?

- **A)** `argument-hint`, since it only surfaces the expected argument shape in the `/` autocomplete menu — it doesn't validate, reject, or block execution based on what the user types.
- **B)** `argument-hint`, configured so the command automatically refuses to run and raises a validation error whenever `$0` or `$1` come back empty.
- **C)** `allowed-tools`, restricting the command so that it cannot execute at all unless at least one argument is supplied.
- **D)** Hardcode a single fixed environment name directly into the command body, removing the need for any argument.

## Q3
In a CI-integrated pipeline, a `lint-fix` skill runs automatically on every pull request to auto-fix style violations. Over the last 40 PRs, it has twice also modified files entirely outside the linting scope via the `Write` tool — once touching a deployment config file that broke a later stage. The platform team wants a guarantee, enforced at the configuration level, that this skill can never call `Write` while it runs, a guarantee that holds regardless of what the model infers is "in scope" on a given PR, and that doesn't depend on the model's judgment at all. What should they add to the skill?

- **A)** Add a line to the skill body instructing the model: "Never call Write here — only report suggested changes."
- **B)** Replace the skill with a `PostToolUse` hook that detects any file written outside the lint scope and reverts it after the fact.
- **C)** Continue trusting the model's judgment about what counts as in-scope, since it has gotten it right in 38 of the last 40 PRs.
- **D)** Add `disallowed-tools: Write` to the skill's frontmatter, so `Write` is deterministically unavailable to it while it runs, regardless of what the model infers as "in scope."

## Q4
A project's `./CLAUDE.md` is already sizable, and the team is debating where two new pieces of guidance belong: a ~150-line database-migration checklist that's only relevant on the roughly 2 times per quarter someone runs a migration, and a short "always use Conventional Commits" rule that applies to literally every commit message Claude writes, in every session. An engineer proposes moving both into `.claude/skills/` to "keep CLAUDE.md lean." Given that CLAUDE.md loads into every session's context automatically while a skill only loads once Claude decides to invoke it, what is the best split of the two pieces of guidance?

- **A)** Put the full 150-line migration checklist directly into `./CLAUDE.md` next to the commit rule, so both stay present in every session's context by default.
- **B)** Move the migration checklist into a skill, loaded on demand only when relevant, and keep the Conventional Commits rule in `./CLAUDE.md`, loaded every session automatically.
- **C)** Move the Conventional Commits rule into a skill instead, and leave the full migration checklist sitting in `./CLAUDE.md`, since skills are the newer, more capable mechanism for holding important guidance.
- **D)** Register both the migration checklist and the commit rule as resources inside `.mcp.json`, since that file also governs what Claude Code loads into context.

## Q5
A developer wants a personal `deploy` helper that always adds a `--dry-run` flag by default, for their own habit of double-checking before a real release — but they still need the team's canonical `deploy` skill, defined in the project's `.claude/skills/deploy/SKILL.md`, to remain available on their own machine for actual deploys, since the dry-run variant is a personal convenience, not a replacement. If they create the personal version at `~/.claude/skills/deploy/SKILL.md` using the exact same skill name, what happens on their machine, and how should they name the personal skill instead to get what they actually want?

- **A)** Commit the personal skill file into the project's shared `.claude/skills/` directory under version control, so the whole team automatically gets the dry-run behavior too.
- **B)** Set up an internal sync service that copies the developer's personal `~/.claude/skills/deploy/` directory to every teammate's home directory on a schedule.
- **C)** Name the personal skill `deploy` too, since personal scope overrides project scope with no merge — on that developer's own machine, the personal version becomes the one Claude resolves to for `/deploy` or model-invocation.
- **D)** Give the personal skill a different name, e.g. `deploy-dryrun`, so it coexists with the project's `deploy` skill instead of replacing it on that developer's machine.

## Q6
A CI-integrated `rollback-prod` skill reverts the most recent production deployment. Twice in the last sprint, Claude invoked this skill on its own mid-session, without anyone typing `/rollback-prod`, after inferring from a failing post-deploy test that a rollback "seemed like the right move" — and one of those two times it actually executed the rollback before an engineer could intervene. The team wants a configuration-level guarantee that this skill only ever runs when a human explicitly types `/rollback-prod`, while Claude remains free to discuss and reason about deployments and rollbacks in conversation. What should they change?

- **A)** Rely on the skill's `description` field being written narrowly and cautiously enough that the model naturally avoids invoking it except when truly warranted.
- **B)** Set `disable-model-invocation: true` on the skill, so `/rollback-prod` becomes user-invoked only and the model can never trigger it on its own.
- **C)** Set `user-invocable: false` on the skill, hiding it from the `/` menu so that only the model, not a human, can invoke it going forward.
- **D)** Restrict the skill's `allowed-tools` down to a minimal read-only set (e.g., just `Read`), so it can no longer take destructive action even if it runs.
