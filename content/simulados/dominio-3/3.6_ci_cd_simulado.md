# Simulado — 3.6 Integrate Claude Code into CI/CD pipelines (CCA-F, Domínio 3)

**Tópico:** CI/CD com Claude Code — print mode (`-p`), `--output-format json` e `structured_output` via `--json-schema`, reprodutibilidade com `--bare` e devolução de contexto por `--append-system-prompt-file`, desfecho do run como parte do contrato do gate, e revisão independente × sessão continuada
**Exercício relacionado:** `exercicios/dominio-3/3.6_ci_cd_claude_code.py`
**Formato:** múltipla escolha — 1 correta + 3 distratores (formato oficial da prova; questões em inglês)

6 questões. Uma única melhor resposta por questão.

> Responda antes de consultar o gabarito em `3.6_ci_cd_gabarito.md`.

## Q1
A CI review job runs on 5 repositories and finishes with exit 0 on every run, yet the pipeline posts no comments at all. The step that builds the comments runs `jq '.structured_output.findings'` over the CLI output and gets `null` each time. The call is `claude -p "<review prompt>" --output-format json`, and the prompt asks for findings carrying file, line, and severity. Inspecting the raw output shows the findings are there, written as prose paragraphs, inside the `result` field. Which change is most effective at making the parsing step work?

- **A)** Extract the findings out of the `result` field with a regex that matches file, line, and severity per paragraph.
- **B)** Add `"reply with JSON only, no text around it"` to the review prompt, so that the `result` field parses cleanly.
- **C)** Pass `--json-schema` with a schema for the findings, so the validated object lands in `structured_output`.
- **D)** Add `--strict-json` next to `--output-format json`, so the run emits strictly valid JSON instead of prose.

## Q2
A team moved its review job from a developer laptop to a shared CI runner and added `--bare` so that the job gives the same result on every machine. Since that change, none of the posted comments cite the team's review criteria, and 3 comments in the last batch flag patterns that the repository's `CLAUDE.md` documents as accepted conventions. The reviews are still well formed, and the job exits 0. Which change is most effective at getting the team's criteria back into the review?

- **A)** Keep `--bare` and pass `--append-system-prompt-file CLAUDE.md`, so the criteria enter the run explicitly.
- **B)** Drop `--bare`, so that auto-discovery picks `CLAUDE.md` back up along with the rest of the runner's setup.
- **C)** Pass `--claude-md ./CLAUDE.md` so the memory file is loaded explicitly while `--bare` stays in place.
- **D)** Add an instruction to the prompt telling Claude to read `CLAUDE.md` at the repository root before reviewing.

## Q3
A review gate posts inline comments on pull requests. Re-triggered by two new commits, the job posted 4 comments whose text is identical to comments the previous run had already posted on the same pull request. The prompt already carries the previous run's findings plus an instruction to report only what is new or still open. The reviewed diff is `base...HEAD`. The team's requirement is that a finding is never posted to the same pull request twice. What is the most effective way to satisfy that requirement?

- **A)** Reinforce the prompt with examples of findings already reported, so that the model reliably skips them.
- **B)** Review only the incremental diff between the two new commits instead of the full `base...HEAD` range.
- **C)** Run the review twice per trigger and post only the findings that both of the two runs report.
- **D)** Fingerprint each finding in the gate and drop the ones already posted, keeping the prompt instruction as a cost reducer.

## Q4
A code-generation pipeline turns a prose requirement into an implementation, then asks Claude to review the diff it just produced, in the same session via `--resume`. Across 20 pull requests that review came back `"no issues found"` on 18. A human reviewer later found that on 4 of those 18 the code contradicts the requirement: a field documented as optional is validated as mandatory. The generation step itself is sound. Which change is most effective at catching this class of divergence?

- **A)** Raise `--max-turns` and resend the whole requirement in the resumed session, so there is room to compare the two.
- **B)** Run the review as an independent instance whose only context is the requirement and the diff under review.
- **C)** Add an instruction to the resumed prompt to be critical of its own work and to assume that bugs are present.
- **D)** Use `--fork-session` so that the review runs on a branch of the generating session rather than on the trunk.

## Q5
A CI gate posted `"0 blockers, merge cleared"` on 3 pull requests last week and exited 0 on all three; one of them shipped an authentication bug to production. The logs for those runs show the review produced no structured output at all — the JSON carries `subtype: "success"` with no `structured_output` field — and the gate's comment builder reads a missing findings array the same way it reads an empty one. Which change is most effective at making the gate's verdict trustworthy?

- **A)** Fail the gate under its own exit code, not the blocker one, when the run returns an error subtype or success with no `structured_output`.
- **B)** Post a warning comment and clear the merge anyway, since a review that failed to produce output is not evidence that a defect exists.
- **C)** Retry the review up to three times and clear the merge as soon as one of the three attempts comes back reporting zero blocking findings.
- **D)** Mark every property of the JSON schema as `required`, so that the model is unable to come back with an empty findings array for the diff.

## Q6
A test-generation job opens one pull request per module. In the latest batch each pull request carries 12 tests, and review of one of them found that 9 of the 12 restate scenarios the existing suite already covers. All 12 build their setup inline rather than using the shared fixtures that live in `conftest.py`. The team has started closing these pull requests without reading them. Which change is most effective at making the generated tests worth reviewing?

- **A)** Add a second Claude pass that scores each generated test and discards the ones that score below a threshold.
- **B)** Raise the bar in the prompt: write only high-value tests, never duplicate a scenario the existing suite already covers, and reuse the shared fixtures.
- **C)** Document the shared fixtures, the test patterns and what counts as a valuable test in `CLAUDE.md`, and give the job the existing test files.
- **D)** Use `--tools` to take Write away from the job, so that it only proposes tests in prose for a human to write.
