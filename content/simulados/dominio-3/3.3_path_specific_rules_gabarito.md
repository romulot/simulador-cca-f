## Q1 — Resposta correta: **B** · (3.3)

O requisito é uma convenção que se aplica a um **tipo de arquivo** (`*.test.tsx`) espalhado por várias pastas, carregando só quando relevante. Uma path-rule com `paths: ["**/*.test.tsx"]` casa esse padrão exatamente: `**` cruza qualquer profundidade de diretório, então a mesma rule cobre `packages/web/`, `apps/admin/` e qualquer pacote futuro, e só entra em contexto quando Claude lê ou edita um arquivo que casa o glob.

- **A — errada:** um `CLAUDE.md` por pacote resolve os pacotes que já existem hoje, mas exige lembrar de criar mais um arquivo idêntico a cada novo pacote — a convenção fica amarrada a **subárvores específicas**, não ao tipo de arquivo que ela realmente mira; qualquer pacote esquecido fica sem a convenção (arquétipo §4: **camada/alvo errado** — escopo por subárvore para um problema que é por tipo).
- **B — correta.**
- **C — errada:** mover a convenção para o `./CLAUDE.md` raiz garante que ela esteja sempre presente, mas contraria exatamente a segunda metade do requisito ("sem adicionar ao contexto-base de sessões que não tocam teste") — carrega em toda sessão, mesmo as que nunca leem um `.test.tsx` (arquétipo §4: **equívoco de capacidade** — tratar "sempre carregado" como se não tivesse custo).
- **D — errada:** `paths: "*.test.tsx"` sem `**` só casa dentro de UM segmento — um `Button.test.tsx` na raiz do repo casaria, mas `packages/web/Button.test.tsx` (aninhado) não. É o glob quebrado clássico do 3.3: a rule "nunca ativa" para os arquivos reais do cenário (arquétipo §4: **equívoco de capacidade** — confundir `*` com `**`).

## Q2 — Resposta correta: **D** · (3.3)

A economia de contexto vem do **timing de carga**: uma rule com `paths:` só entra no contexto quando Claude efetivamente lê/edita um arquivo que casa o glob — não no início da sessão, não a cada tool use qualquer. Por isso as 44 sessões que nunca tocam `infra/**` nunca pagam o custo de tokens da seção de Terraform, ao contrário de conteúdo sem `paths:` (rule global ou `CLAUDE.md`), que carrega sempre, na primeira mensagem de toda sessão.

- **A — errada:** trata uma rule com `paths:` como se carregasse sempre, igual ao `CLAUDE.md` — é exatamente o equívoco que o mecanismo existe para evitar; a ativação é condicionada ao arquivo lido, não ao fato de o texto estar em `.claude/rules/` (arquétipo §4: **equívoco de capacidade**).
- **B — errada:** `/compact` sumariza o histórico da conversa para economizar contexto — não é o mecanismo certo para uma seção que sequer deveria entrar em contexto quando irrelevante; resolve outro problema, e ainda mantém a seção sempre carregada por padrão em cada sessão até então (arquétipo §4: **over-engineering** — camada extra de operação onde o path-scoping nativo já resolveria na raiz).
- **C — errada:** mover para escopo `user` (`~/.claude/rules/`) muda **quem** herda a rule (aquele desenvolvedor, em qualquer projeto), não **quando** ela carrega dentro de uma sessão — continuaria carregando em toda sessão daquele usuário, independente de tocar `infra/**` ou não; não ataca o mecanismo de timing que o problema pede (arquétipo §4: **camada/alvo errado**).
- **D — correta.**

## Q5 — Resposta correta: **B** · (3.3) — quebra-automatismo

O critério certo é casar cada convenção ao seu **padrão de espalhamento**, não empurrar tudo para o mecanismo "mais moderno": a regra de ticket-ID é **universal** (toda mensagem de commit, sempre) — pertence a uma rule global (sem `paths:`) ou ao `CLAUDE.md`; a convenção de `*.graphql` é **por tipo, cross-dir** — pertence a uma path-rule com glob; o padrão legado de `services/billing-legacy/` é **local a uma única subárvore** — pertence a um `CLAUDE.md` de subdiretório, sem precisar de glob algum. É quebra-automatismo porque a resposta certa **não** é "path-rule para tudo, porque é a mecanismo mais novo" — a peça universal fica melhor numa rule global/`CLAUDE.md`, exatamente o oposto do instinto de modernizar tudo para `paths:`.

- **A — errada:** seguir a proposta com `paths: ["**"]` funciona no sentido de que `**` sozinho casa qualquer arquivo — mas isso não é diferente, na prática, de uma rule global sem `paths:` alguma; a única coisa que muda é a ilusão de estar "path-scoped" no papel, sem ganho real e com uma dependência frágil (se alguém restringir aquele glob mais tarde sem perceber, a convenção universal some silenciosamente) (arquétipo §4: **equívoco de capacidade** — tratar `paths: ["**"]` como equivalente-e-mais-moderno a global, quando é só equivalente e mais frágil).
- **B — correta.**
- **C — errada:** `.mcp.json` configura servidores **MCP** (tools/resources externos) — não é um mecanismo para hospedar texto de convenção de workflow; aplica um arquivo real ao propósito errado (arquétipo §4: **camada/alvo errado**).
- **D — errada:** escrever um script customizado para decidir dinamicamente qual texto injetar a cada sessão reconstrói, com infraestrutura própria e manutenção adicional, exatamente o que o path-scoping nativo (`paths:` em `.claude/rules/`) já resolve de forma declarativa (arquétipo §4: **over-engineering**).

## Q6 — Resposta correta: **D** · (3.3)

O fato travado é que a negação `!` **não existe** nesse formato de `paths:` — ao contrário de `.gitignore`, que suporta `!` para excluir. O segundo padrão (`!**/*.generated.ts`) é inerte: não exclui nada, e o primeiro padrão (`**/*.ts`) continua casando qualquer arquivo `.ts`, gerado ou não — exatamente o sintoma observado (`output/schema.generated.ts` ainda ativa a rule). Sem um mecanismo de exclusão, a solução é reestruturar o glob **positivo** para mirar só a árvore que precisa da convenção (ex.: `paths: ["src/**/*.ts"]`), mantendo o código gerado isolado em seu próprio diretório (`output/generated/**`), fora desse glob.

- **A — errada:** assume que rules do Claude Code espelham a sintaxe de `.gitignore`, incluindo `!` — é uma feature verossímil (existe em outro contexto real, `.gitignore`) mas que não existe neste formato de `paths:`; a recorrência do sintoma não é "cache", é o comportamento documentado do glob engine (arquétipo §4: **feature inexistente porém verossímil**).
- **B — errada:** trocar a rule por uma skill mantendo o mesmo `paths` com `!` não resolve nada — o campo `paths` de uma skill usa o **mesmo formato de glob** da rule (mesma ausência de negação); trocar o mecanismo de config não muda a sintaxe do glob nem cria uma capacidade que nenhum dos dois tem (arquétipo §4: **feature inexistente porém verossímil**, aplicado à ponte rule×skill do 3.3/3.2 — confundir "mecanismo diferente" com "capacidade diferente de glob").
- **C — errada:** manter os dois padrões e complementar com uma instrução em prosa no corpo da rule pedindo para "pular" arquivos gerados troca uma garantia de configuração por uma sugestão que o modelo pode ou não seguir de forma consistente (arquétipo §4: **probabilístico onde precisa ser determinístico**).
- **D — correta.**
